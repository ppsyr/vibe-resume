### 1. Redis 缓存击穿是什么，用什么解决

```
【缓存击穿是什么】

定义：某个热点 Key 在过期瞬间，大量并发请求同时未命中缓存，全部打到数据库，
DB 瞬时承受高并发压力，可能被打垮。

关键词：单个 Key、热点、过期瞬间。
和另外两个区分：
- 穿透：查的是数据库里也不存在的数据，请求每次都打到 DB（用空对象/布隆过滤器解决）。
- 雪崩：大量 Key 同时过期或 Redis 宕机，DB 承受全量请求（用 TTL 随机、高可用解决）。
- 击穿：就一个热点 Key 过期，但并发全压上来。

【危害】
热点 Key 本来承载高并发，失效瞬间 DB 要接住全量请求，
连接池打满、行锁竞争、慢查询堆积，严重时拖垮整个数据库。

【解决方案：两种主流 + 一个变体】

方案1：互斥锁（Mutex）
- 思路：缓存未命中时，先抢锁（SETNX），抢到的请求去查 DB 重建缓存，
  没抢到的自旋/休眠等待，重建完成后读缓存。
- 优点：保证一致性，DB 只有一个请求在查。
- 缺点：等待带来可用性下降，抢锁失败要重试，高并发下等待时间可能较长；
  还要处理锁超时、误删（UUID 校验）、重建失败释放锁等问题。
- 适用：一致性要求较高、并发不是极端高的场景。

方案2：逻辑过期（Logical Expire）
- 思路：Key 不设 Redis TTL（永不过期），value 里额外存一个 expireTime 字段。
  请求读到后发现逻辑过期，不是阻塞等待，而是抢锁后开异步线程重建缓存，
  当前请求先返回旧数据。
- 优点：高可用，请求不阻塞，始终能快速返回。
- 缺点：返回的是短暂旧数据，牺牲强一致；实现更复杂（异步线程池、锁、缓存重建）。
- 适用：高并发、能容忍短暂不一致的热点数据（如商品详情、店铺信息）。

方案3（变体）：热点 Key 永不过期 + 后台定时刷新
- 对确定的热点 Key 不设 TTL，后台任务定期主动更新缓存。
- 简单可靠，但需要能提前识别热点 Key，且刷新间隔内数据可能旧。

【项目落地】
黑马点评店铺查询用的是互斥锁方案：
- 缓存未命中 → SETNX 抢锁 → 抢到查 DB 回填缓存并释放锁 → 没抢到休眠重试。
- 选它是因为店铺信息一致性要求相对高、并发没秒杀极端，互斥锁实现简单、能保证一致。
- 锁的细节：SETNX + 过期时间防死锁，value 存 UUID 防误删，finally 里释放。

【一句话总结】
击穿是"单热点 Key 过期瞬间并发打 DB"；
要一致用互斥锁（牺牲可用性），要可用用逻辑过期（牺牲短暂一致）；
项目里按数据一致性和并发量选型，黑马点评店铺查询选了互斥锁。
```

#### 1.1. 缓存击穿的逻辑过期是什么意思；逻辑过期时间存在哪、比 TTL 好在哪

```
【问题1：逻辑过期是什么意思】

核心一句话：Key 在 Redis 里永不过期（不设 TTL），"过期"由 value 内部的 expireTime 字段
在业务代码里判断，发现逻辑过期后异步重建缓存，当前请求先返回旧数据。

完整流程：
1. 写缓存时，value 里除了业务数据，还存一个 expireTime（逻辑过期时间戳）。
   Redis 层不设 TTL，所以这个 Key 永远不会被 Redis 自动删除。
2. 请求读缓存：
   a) 缓存 miss（Key 不存在）：说明从没加载过，走互斥锁查 DB 回填（或直接返回空）。
   b) 缓存 hit：取出 value，判断 expireTime 是否已过。
      - 没过期：直接返回业务数据，正常路径。
      - 已过期：说明需要重建，但当前请求不阻塞——
        抢锁成功后开一个异步线程去查 DB 重建缓存并更新 expireTime，
        当前请求直接返回旧数据；抢锁失败也直接返回旧数据。
3. 效果：任何时刻请求都能快速拿到数据（哪怕是旧的），不会因缓存过期而阻塞或全量打 DB。

和 TTL 的本质区别：
- TTL：过期由 Redis 控制，到期 Key 被删，缓存出现"真空"，请求必须等重建或打 DB。
- 逻辑过期：Redis 层永不过期，缓存永远有值，过期判断和重建都在业务层异步做，
  用"短暂旧数据"换"高可用 + 请求不阻塞"。

【问题2：逻辑过期时间存在哪】

存在 value 的字段里，不是 Redis 的 TTL，也不是单独的 key。

典型结构（黑马点评的 RedisData 包装类）：
- value 用 Hash 或 JSON 存，包含两部分：
  a) data：真正的业务数据（如店铺信息）；
  b) expireTime：逻辑过期时间戳（LocalDateTime / long）。
- 读取时先取整个 value，解析出 expireTime 和 data，再判断是否过期。

为什么这么设计：
- Redis 的 TTL 是 Key 级别的元数据，客户端读不到具体过期时间，也无法"过期了还保留值"。
- 把过期时间放进 value，客户端就能自己控制"什么时候算过期、过期后怎么处理"，
  从而支持"过期了先返回旧值、异步重建"的语义。

【问题3：比 TTL 好在哪】

核心优势：高可用、请求不阻塞、DB 压力平缓。

1. 不会出现缓存真空
   - TTL 到期 Key 被删，缓存 miss，请求要么等锁重建（互斥锁方案，阻塞），
     要么全量打 DB（无保护）。逻辑过期 Key 永在，永远有旧值可返回。

2. 请求不阻塞
   - 逻辑过期发现过期后，异步线程重建，当前请求立即返回旧数据，响应时间稳定。
   - 互斥锁方案没抢到锁的请求要休眠重试，高并发下等待时间可能很长。

3. DB 压力平缓
   - 重建由抢到锁的单个异步线程做，DB 只有一个请求在查，不会被并发打爆。
   - 且重建是后台异步，不占用用户请求线程。

4. 适合高并发热点数据
   - 商品详情、店铺信息这类"能容忍短暂不一致、但要求高可用"的场景很合适。

代价（要诚实说，体现取舍）：
- 牺牲强一致：返回的是旧数据，有短暂不一致窗口。
- 实现更复杂：需要异步线程池、抢锁、缓存重建逻辑，还要处理重建失败。
- 额外内存：value 里多存一个 expireTime 字段。
- 缓存 miss 场景仍需兜底：Key 从没加载过时，逻辑过期不适用，要配合互斥锁或预热。

【一句话总结】
逻辑过期 = Key 永不过期 + value 里存 expireTime + 业务层判断过期后异步重建、先返回旧值；
expireTime 存在 value 字段（RedisData 的 data + expireTime 结构）；
相比 TTL，它用"短暂旧数据"换"缓存永不真空、请求不阻塞、DB 压力平缓"，
适合高并发可容忍短暂不一致的热点数据。
```

#### 1.2. 不可接受短暂不一致怎么做

```
【不可接受短暂不一致怎么做】

先明确约束：不可接受短暂不一致 = 不能返回旧值，逻辑过期、延迟双删这类"最终一致"方案
直接排除。要在"读到就是最新"的前提下做缓存，本质是拿性能或可用性换一致性。

一、先排除不可行的方案
- 逻辑过期：返回旧值，排除。
- 先删缓存再更新 DB / 延迟双删：仍有不一致窗口，排除。
- 异步重建：重建完成前读到的还是旧值，排除。

二、可行方案及代价（没有免费的一致）

方案1：互斥锁 + 同步重建（最常用）
- 缓存 miss 时，抢锁的请求同步查 DB 重建缓存，重建完成才返回；
  没抢到锁的请求阻塞等待，直到缓存可用。
- 保证：读到的要么是缓存新值，要么是刚重建的新值，不会返回旧值。
- 代价：请求阻塞、响应变慢、可用性下降；锁要防死锁和误删。
- 适用：一致性要求高、并发不极端的热点数据。

方案2：读写锁 / 分布式读写锁
- 读加读锁、写加写锁，读写互斥，保证写的过程中读不到中间态。
- 保证：读写不交叉，缓存和 DB 更新原子可见。
- 代价：并发度低，写锁期间读被阻塞；分布式读写锁实现复杂（Redisson 支持）。
- 适用：写少读多但写时必须强一致的场景。

方案3：写穿透（Write Through）+ 锁/事务保证原子
- 写操作同时更新 DB 和缓存，用分布式锁或事务保证两者原子。
- 保证：缓存和 DB 始终同步。
- 代价：写性能差（每次写都碰缓存和 DB），实现重，锁竞争。
- 适用：写少、数据量小、强一致要求高的配置类数据。

方案4：缓存只做只读副本 + 版本号校验
- 缓存 value 带版本号，读时比对 DB 当前版本（或一个全局版本 Key），
  版本旧就回源并更新缓存。
- 保证：不会长期读到旧版本，但比对本身要读 DB/版本 Key，有开销。
- 适用：能接受"比对开销"换"不返回旧值"的场景。

三、工程上的分级选型（面试重点，体现取舍）
1. 核心强一致字段（余额、库存扣减结果、支付状态）：干脆不走缓存，直接读 DB，
   用索引和读写分离扛；缓存只用于非核心展示字段。
2. 必须缓存且强一致：用互斥锁 + 同步重建，把不一致窗口压到 0；
   写时"先更新 DB 再删缓存"，读时 miss 阻塞重建。
3. 写操作加分布式锁：保证同一 key 的写串行，避免并发写导致缓存与 DB 错乱。
4. 兜底：即使做到上述，极端故障（Redis 主从切换丢数据）仍可能不一致，
   用版本号校验 + 定时对账 + 告警做最后防线，发现差异以 DB 为准修缓存。

四、一句话总结
不可接受短暂不一致，就不能用逻辑过期/延迟双删这类最终一致方案；
要么核心数据不走缓存直接读 DB，要么用"互斥锁同步重建 + 写删缓存 + 分布式锁串行写"
把窗口压到最小，代价是性能和可用性；
绝对强一致在缓存架构里代价极高，工程上按业务分级，核心走 DB、非核心才用缓存。
```

### 2. Redis 缓存穿透是什么，用什么解决

```
【缓存穿透是什么】

定义：客户端请求的数据在缓存和数据库中都不存在，缓存永远 miss，
每次请求都打到数据库，缓存失去保护作用。

关键词：数据不存在、每次都打 DB。
和三剑客区分：
- 穿透：查不存在的数据，缓存和 DB 都没有，请求每次打 DB。
- 击穿：单个热点 Key 过期瞬间，大量并发打 DB。
- 雪崩：大量 Key 同时过期或 Redis 宕机，DB 承受全量请求。
区别核心：穿透是"数据不存在"，击穿是"热点 Key 过期"，雪崩是"大面积失效"。

【危害】
正常缓存能挡住大部分请求，但穿透场景下缓存形同虚设。
如果是恶意攻击（用随机不存在的 ID 高频查询），DB 会被直接打满，
连接池耗尽、慢查询堆积，可能拖垮整个服务。

【解决方案：两种主流 + 辅助手段】

方案1：缓存空对象
- 思路：查 DB 结果为空时，也把这个 key 缓存起来，value 存空字符串或特殊标记，
  设置较短的 TTL（如 2~5 分钟）。
- 优点：实现简单，对业务代码侵入小，能挡住重复的无效查询。
- 缺点：
  a) 会额外占用内存，大量随机 key 攻击可能撑爆缓存；
  b) 数据后续被创建时，缓存里还是空值，存在短暂不一致（可插入时主动删缓存缓解）。
- 适用：无效 key 重复率较高、数据量可控的场景。

方案2：布隆过滤器（Bloom Filter）
- 思路：在缓存前加一层位图，把所有可能存在的 key 提前 hash 映射进去。
  请求先过布隆过滤器，判断"可能存在"才查缓存/DB，"一定不存在"直接拒绝。
- 优点：极省内存（位数组），判断 O(k) 很快，能挡住大量不存在的 key。
- 缺点：
  a) 有误判率（可能把不存在判成存在，但不会把存在判成不存在）；
  b) 不支持删除元素（删除会影响其他 key 的位，需用计数布隆过滤器变体）；
  c) 需要预热，数据新增要同步更新过滤器。
- 适用：数据集合相对固定、能接受少量误判、无效请求量大的场景。

辅助手段：
- 参数校验：ID 格式、范围非法直接拒绝，不进缓存。
- 接口限流/鉴权：限制单 IP/用户请求频率，挡恶意刷。
- 热点 key 监控：发现异常查询模式及时告警。

【项目落地】
黑马点评店铺查询用的是缓存空对象方案：
- 查缓存 miss → 查 DB → DB 也为空 → 缓存空字符串并设短 TTL（如 2 分钟）→ 返回空。
- 选它是因为实现简单、店铺 ID 范围可控、无效重复查询能被挡住；
  代价是可能占一点内存，但店铺数据量不大，可接受。
- 如果面对恶意随机 ID 攻击，单靠空对象不够，要配合布隆过滤器 + 限流。

【一句话总结】
穿透是"查不存在的数据，缓存和 DB 都 miss，请求每次打 DB"；
要简单用缓存空对象（占内存、可能不一致），要省内存用布隆过滤器（有误判、不支持删除）；
项目里店铺查询用空对象 + 短 TTL，生产上再叠加参数校验和限流做纵深防御。
```

#### 2.1. 布隆过滤器的原理

```
【布隆过滤器的原理】

核心一句话：位数组 + 多个哈希函数，用"一定不存在 / 可能存在"的不对称判断，
以极小内存代价挡掉大量不存在的 key。

一、数据结构
- 一个长度为 m 的位数组（bit array），初始全 0。
- k 个相互独立的哈希函数，每个把元素映射到 [0, m-1] 的一个位置。

二、插入流程
- 元素 x 插入时，用 k 个哈希函数算出 k 个位置 h1(x)~hk(x)，
  把这 k 个位全部置 1。
- 注意：多个元素可能共享某些位，位是"或"的关系。

三、查询流程
- 查询元素 y 时，同样算 k 个位置：
  a) 只要有任意一个位置是 0 → y 一定不存在（因为如果插入过，它的位一定都是 1）。
  b) 如果 k 个位置全是 1 → y 可能存在（也可能是别的元素把这些位置置 1 了）。
- 这就是核心特性：不会漏判（假阴性），但可能误判（假阳性）。

四、为什么会有误判
- 不同元素哈希到相同位，位被别的元素置 1 了。
- 查询一个没插入过的元素，它的 k 个位置恰好都被其他元素置 1，
  就会误判为"存在"。
- 误判率由 m、k、n（元素数量）决定：
  m 越大、k 越合适，误判率越低；元素越多，位越拥挤，误判率越高。
  工程上按预期元素量和可接受误判率反推 m 和 k。

五、为什么不支持删除（标准布隆过滤器）
- 一个位可能被多个元素共享，删除元素时把位清零，
  会影响其他映射到该位的元素，导致它们被误判为"不存在"（出现假阴性）。
- 要支持删除，用计数布隆过滤器：每位用计数器代替 0/1，
  插入 +1、删除 -1，计数为 0 才视为不存在。代价是内存成倍增加。

六、在缓存穿透里的用法
- 系统启动/数据初始化时，把 DB 中所有可能存在的 key 预热进布隆过滤器。
- 请求进来先过布隆过滤器：
  a) 判"一定不存在" → 直接拒绝，不查缓存和 DB，挡住恶意/无效请求。
  b) 判"可能存在" → 正常查缓存，miss 再查 DB。
- 局限（要诚实说）：
  a) 有误判率，少量不存在的 key 仍会穿透，需配合缓存空对象兜底；
  b) 数据新增要同步更新过滤器，删除要靠计数版或重建；
  c) 需要预热，冷启动阶段保护有限；
  d) 布隆过滤器本身要做高可用（如 Redis 的 Bloom 模块或本地 + 重建机制）。

【一句话总结】
布隆过滤器 = 位数组 + k 个哈希函数，插入置位、查询查位；
判 0 一定不存在，判 1 可能存在，只误判不漏判；
省内存但不可删除、有误判率、需预热；
缓存穿透里做前置拦截，配合空对象和限流做纵深防御。
```

#### 2.2. 怎么降低误判率？

```
【怎么降低布隆过滤器误判率】

先给公式：误判率近似 P ≈ (1 - e^(-kn/m))^k
m = 位数组长度，k = 哈希函数个数，n = 已插入元素数量。
降低误判率，本质就是调这三个变量 + 工程手段兜底。

一、参数层：调 m、k、n

1. 增大位数组 m
   - m 越大，位越稀疏，不同元素撞位的概率越低，误判率下降。
   - 代价：内存占用线性增加。这是最直接但最耗资源的手段。

2. 选最优哈希函数个数 k
   - k 不是越大越好。k 太小，每个元素置位少，区分度不够；
     k 太大，位被置 1 的比例快速上升，查询时更容易全 1 误判。
   - 给定 m 和 n，误判率最低时 k = (m/n) * ln2 ≈ 0.693 * (m/n)。
   - 工程上先定位数组大小和元素量，再按这个公式算 k。

3. 控制已插入元素数 n
   - n 越大位越拥挤，误判率越高。布隆过滤器有容量上限，
     超过预期元素量后误判率会明显恶化。
   - 手段：按峰值元素量预留 m；数据量增长后定期重建更大的过滤器；
     超大规模可分片成多个布隆过滤器，按 key 路由，降低单个 n。

二、架构层：参数之外的手段

4. 用计数布隆过滤器（Counting Bloom Filter）
   - 每位用计数器代替 0/1，支持删除，避免"删不掉导致只能重建"，
     间接让 n 可控、误判率稳定。代价是内存成倍增加。

5. 多层/分级布隆过滤器
   - 用多个不同参数的过滤器分级判断，或结合本地 + Redis 两层，
     降低单层误判带来的穿透。实现更复杂。

6. 换更均匀的哈希函数
   - 哈希分布不均会让某些位过热，实际误判率高于理论值。
     选高质量、独立性的哈希（如 MurmurHash、xxHash）保证均匀。

7. 配合缓存空对象 + 限流兜底
   - 布隆过滤器只能把误判率降到很低，不能到 0。
     误判穿透的那部分用缓存空对象接住，恶意流量用限流挡，
     做纵深防御，而不是指望单点零误判。

三、工程落地方法（按可接受误判率反推）
- 先定业务可接受的误判率（如 1% 或 0.1%）和预期元素量 n。
- 用公式反推 m 和 k：
  m ≈ -n * lnP / (ln2)^2，k = (m/n) * ln2。
- 例：n = 100 万、P = 1%，算出来 m 约 960 万位（约 1.2MB），k 约 7。
- 按算出的参数建过滤器，并监控实际元素量，接近上限时扩容重建。

【一句话总结】
降低误判率 = 增大位数组 m + 按 k=(m/n)ln2 选最优哈希个数 + 控制元素量 n；
参数之外用计数布隆、分片重建、均匀哈希、空对象和限流兜底；
核心是按可接受误判率反推参数，并接受"只能降低不能消除"的事实。
```

#### 2.3. 布隆过滤器的 key 可以删除吗？

```
【布隆过滤器的 key 是什么】

要分两层说，避免混淆：

1. Redis 层面的 key
   - 布隆过滤器在 Redis 里是一个数据结构，用 BF.ADD / BF.EXISTS 操作。
   - 命令里的 key 是这个布隆过滤器实例的名字，比如 "shop:bloom"，
     类似一个集合的名字，用来定位这个位数组。

2. 真正被哈希的元素（业务上的"key"）
   - BF.ADD shop:bloom 1001 里的 1001 才是被哈希的元素，
     也就是你要判断存在性的业务 ID（店铺 ID、用户 ID、商品 ID）。
   - 每个元素经 k 个哈希函数映射到位数组的 k 个位置。
   - 所以严格说布隆过滤器存的不是 key-value，而是一组元素的"存在性指纹"。

面试回答时点一句：Redis 命令的 key 是过滤器名，被哈希的是元素本身，
判断存在性判断的是元素，不是 Redis key。

【可以删除吗】

标准布隆过滤器：不支持删除。

1. 为什么不能删
   - 位是共享的：一个位可能被多个元素映射。删除元素时把它的 k 个位清零，
     会连带影响其他映射到这些位的元素，导致它们被误判为"不存在"（假阴性）。
   - 假阴性比假阳性更严重：本来存在的数据被判不存在，业务会出错（比如误拒合法请求）。
   - 所以标准布隆过滤器只支持插入和查询，不支持删除。

2. 要删除怎么办
   方案1：计数布隆过滤器（Counting Bloom Filter）
   - 每位用计数器代替 0/1，插入时对应位 +1，删除时 -1，计数为 0 才视为不存在。
   - 优点：支持删除，不产生假阴性。
   - 代价：内存成倍增加（计数器通常 4 bit 或更多），计数器还有溢出风险。

   方案2：重建过滤器
   - 数据删除后，新建一个布隆过滤器，把当前仍存在的元素重新灌进去，再切换。
   - 适合删除不频繁、能接受重建成本的场景；重建期间可双写过渡。

   方案3：分片 + 定期重建
   - 按 key 分片成多个过滤器，删除只影响对应分片，重建成本可控。

3. 工程建议
   - 如果业务删除极少（如店铺 ID 基本不删），用标准布隆过滤器 + 定期重建即可。
   - 如果删除频繁（如商品上下架、用户注销），用计数布隆过滤器，
     或改用其他支持删除的结构（如 Redis Set，但内存开销大得多）。

【一句话总结】
Redis 命令的 key 是过滤器名，被哈希的是业务元素本身；
标准布隆过滤器位共享、不能删除（删了会产生假阴性），
要删除用计数布隆过滤器（内存翻倍）或重建过滤器。
```

#### 2.4. 布隆过滤器定义的「恶意用户」怎么测试？

```
【布隆过滤器"恶意用户"怎么测试】

先澄清概念：布隆过滤器不定义也不识别"恶意用户"，它只判断"元素是否可能存在"。
缓存穿透语境下的"恶意用户"，指的是用大量不存在的 ID 高频查询、试图绕过缓存打垮 DB 的请求方。
布隆过滤器拦截的是这些非法 ID 请求，不是识别"人"。
所以测试目标不是"识别恶意用户"，而是"验证布隆过滤器对非法请求的拦截效果"。

一、测试目标（测什么）
1. 拦截正确性：对确定不存在的 ID，布隆过滤器应返回"不存在"，请求被挡在缓存和 DB 之前。
2. 误判率：少量不存在 ID 可能被误判为"存在"（假阳性），统计实际误判率是否在预期内（如 1%）。
3. DB 保护效果：高并发非法请求下，DB 的 QPS 是否被抑制在低位。
4. 边界与异常：元素量接近容量上限时误判率是否恶化；过滤器不可用/重建时降级是否正常。

二、功能测试（构造非法 ID 验证拦截）
1. 构造非法 ID 集合：
   - 负数 ID（如 -1、-999）；
   - 超出最大 ID 范围的数值（如 999999999）；
   - 随机生成的、DB 中确实不存在的 ID。
2. 对每个 ID 调用布隆过滤器 mightContain(id)：
   - 返回 false → 正确拦截（一定不存在）；
   - 返回 true → 可能是误判（假阳性），记录。
3. 统计：
   - 拦截率 = 返回 false 的次数 / 总次数；
   - 误判率 = 返回 true 的次数 / 总次数，对比配置的可接受阈值。
4. 对误判的 ID 继续走缓存/DB，验证缓存空对象能否兜住，不产生脏数据。

三、压测（模拟恶意流量看保护效果）
1. 用 JMeter / wrk 等工具，脚本生成大量随机不存在 ID，并发请求店铺查询接口。
2. 观察指标：
   - DB QPS 是否被抑制在低位（说明非法请求被挡在 DB 之前）；
   - Redis 是否没有产生大量无效空值缓存（说明拦截生效，没走到缓存空对象）；
   - 接口响应时间是否稳定（布隆过滤器判断是 O(k)，很快）。
3. 对比开关布隆过滤器前后的 DB QPS，量化保护效果。

四、边界与异常测试
1. 容量边界：灌入接近预期上限的元素，测误判率是否明显上升，验证容量预留是否合理。
2. 重建场景：模拟数据新增/重建过滤器，验证重建期间双写过渡、查询不中断。
3. 降级场景：模拟布隆过滤器不可用（Redis 故障/过滤器未加载），验证系统降级到
   "直接查缓存 + 空对象兜底"是否正常，不会因过滤器挂掉导致请求全打 DB。

五、项目落地与指标
- 黑马点评店铺查询用缓存空对象防穿透，如果加布隆过滤器，测试重点是对不存在店铺 ID 的拦截率
  和误判率，以及压测下 DB QPS 的下降幅度。
- 关键指标：拦截率、误判率（≤ 预期）、DB QPS 抑制效果、接口 P99 响应时间、降级可用性。

【一句话总结】
布隆过滤器不识别"恶意用户"，只挡"不存在的 ID"；
测试 = 构造非法 ID 验证拦截率和误判率 + 压测看 DB 保护效果 + 边界/异常验证降级；
核心指标是拦截率、误判率、DB QPS 抑制效果，而不是"抓出谁是恶意用户"。
```

### 3. Redis 缓存雪崩是什么，用什么解决

```
【缓存雪崩是什么】

定义：大量缓存 Key 在同一时间集中失效，或者 Redis 整体不可用（宕机/网络故障），
导致原本被缓存挡住的请求全量打到数据库，DB 瞬时承受全量流量，可能被压垮。

关键词：大量 Key、同时失效、缓存整体不可用。
和三剑客区分：
- 穿透：查不存在的数据，缓存和 DB 都 miss，请求每次打 DB。
- 击穿：单个热点 Key 过期瞬间，大量并发打 DB。
- 雪崩：一片 Key 同时过期，或 Redis 整体挂掉，DB 承受全量请求。
一句话：穿透是"数据不存在"，击穿是"一个 Key 过期"，雪崩是"一片 Key 或整个缓存失效"。

【危害】
缓存层整体失去保护作用，DB 瞬时承受全量流量：
连接池打满、行锁竞争、慢查询堆积，DB 可能宕机；
DB 挂了又反向影响上层服务，形成系统性雪崩。

【解决方案：按两类成因分别对应】

成因1：大量 Key 同时过期
- TTL 加随机值：在基础过期时间上加一个随机偏移（如 30 分钟 ± 5 分钟），
  打散过期时间，避免同一时刻集中失效。最常用、最简单。
- 热点数据永不过期 + 后台刷新：对确定的热点 Key 不设 TTL，后台任务定期更新。
- 多级缓存：本地缓存（Caffeine）+ Redis，Redis 失效时本地还能挡一层。
- 缓存预热：系统启动/活动前提前把热点数据加载进缓存，避免冷启动全量打 DB。

成因2：Redis 整体不可用
- 高可用架构：主从复制 + 哨兵自动切主，或 Redis Cluster 分片 + 故障转移，
  保证单节点挂掉能快速恢复服务。
- 持久化：RDB + AOF，重启后数据可恢复，减少冷启动压力。
- 限流降级熔断：Redis 不可用时，对 DB 访问限流（令牌桶），
  非核心功能降级返回兜底数据，熔断器快速失败保护 DB。
- 服务降级兜底：缓存 miss 且 DB 压力大时，返回默认值/静态页，保证核心链路可用。

辅助手段：
- 监控告警：Key 过期速率、Redis 可用性、DB QPS 异常及时告警。
- 压测评估：提前评估缓存失效时的 DB 承载能力，设置合理限流阈值。

【项目落地】
黑马点评原版没做雪崩防护：数据量小、单机 Redis、TTL 也没加随机，
严格说存在雪崩风险。如果生产化，我会补：
- 店铺缓存 TTL 加随机偏移，打散过期时间；
- Redis 上主从 + 哨兵保证高可用；
- 入口加限流，DB 前加降级兜底；
- 热点店铺预热 + 本地缓存做多级。

【一句话总结】
雪崩是"大量 Key 同时过期或 Redis 整体挂掉，DB 承受全量流量"；
Key 集中过期用"TTL 随机 + 永不过期 + 多级缓存 + 预热"，
Redis 不可用用"主从哨兵/Cluster + 持久化 + 限流降级熔断"；
项目里按成因组合使用，核心是别让 DB 裸奔。
```


### 4. 多级缓存的缓存一致性

```
【多级缓存的缓存一致性】

先明确难点：多级缓存 = L1 本地缓存（Caffeine/本地 Map）+ L2 分布式缓存（Redis）+ DB。
Redis 是共享的，删一次全节点生效；但 L1 在每个服务节点各有一份内存副本，
节点 A 更新了数据，节点 B 的 L1 还是旧值，用户落到 B 就读到脏数据。
所以多级缓存一致性的核心不是“怎么更新 Redis”，而是“怎么让所有节点的 L1 失效”。

一、基础方案：Cache Aside + 广播失效 L1

写操作流程（以更新店铺为例）：
1. 先更新数据库（DB 是最终数据源）。
2. 删除 Redis 中对应的 Key（Cache Aside，先更 DB 再删缓存，避免脏数据）[citation:2][citation:3]。
3. 通过广播通道通知所有服务节点：“key = shop:1001 的 L1 缓存失效了”。
4. 各节点收到广播后，删除自己 JVM 里的 L1 缓存项。
5. 下次读请求：L1 miss → 查 Redis（也 miss）→ 查 DB 回填。

广播通道的选择：
- Redis Pub/Sub：轻量，适合中小规模，但消息不持久，节点短暂离线可能漏消息。
- MQ 广播模式（RabbitMQ fanout / RocketMQ 广播消费）：可靠，有重试，适合生产。
- 专用配置中心/一致性通知组件：如 Nacos 配置变更推送思路，较重量级。

为什么是“先更 DB 再删缓存”：
- 如果先删缓存再更 DB，并发读可能在 DB 更新前把旧值重新回填缓存，产生脏数据[citation:2]。
- 先更 DB 再删缓存，即使删缓存失败，也只是短暂不一致（TTL 兜底），不会产生长期脏数据。

二、进阶方案：Canal 监听 binlog + MQ 广播（业务零侵入）

流程：
1. 业务代码只更新 DB，不关心缓存。
2. Canal 伪装成 MySQL 从库，订阅 binlog，捕获数据变更[citation:1][citation:4]。
3. Canal 把变更事件发到 MQ。
4. 一个“缓存同步服务”消费消息：删 Redis 对应 Key + 广播通知各节点清 L1。
5. 各节点收到广播清 L1。

优点：
- 业务代码零侵入，不需要在每个写方法里写“删缓存 + 发广播”。
- 实时性较好（毫秒到秒级），可靠（MQ 持久化 + 重试）。

代价：
- 部署 Canal、MQ，架构复杂度上升。
- 需要 MySQL 开启 binlog（ROW 格式），有约 1% 性能损耗[citation:13]。
- 有短暂延迟，不是强一致。

三、L1 自身的补充手段（降低不一致窗口）
1. L1 设置短 TTL：即使广播漏了，过期后自然失效，兜底最终一致。
2. 只把“极少变更”的数据放 L1：如店铺类型、配置项；频繁变更的数据（店铺详情、库存）只放 Redis，不放 L1[citation:2]。
3. 版本号/时间戳校验：L1 value 带版本，读时比对 Redis 版本（轻量查询），旧版本回源。代价是多一次 Redis 读，收益有限，一般不用。

四、黑马点评的落地思考
- 原版黑马点评是单级 Redis，没有 L1，所以原版一致性问题就是“先更 DB 再删 Redis” + TTL 兜底[citation:2]。
- 如果面试官问“加 Caffeine 做多级缓存怎么保证一致”，答：
  a) 写操作走“更 DB → 删 Redis → Redis Pub/Sub 广播清 L1”；
  b) 只有店铺类型这类几乎不变的数据进 L1，店铺详情仍以 Redis 为准；
  c) L1 设短 TTL（如 5 分钟）兜底；
  d) 如果要求更高，上 Canal + MQ 做零侵入同步。
- 诚实说：多级缓存追求的是最终一致，不是强一致；强一致代价太高，不适合缓存场景。

【一句话总结】
多级缓存一致性的核心是“L1 本地副本怎么失效”；
基础方案 = Cache Aside（更 DB 删 Redis）+ 广播通知各节点清 L1 + 短 TTL 兜底；
进阶方案 = Canal 监听 binlog + MQ 广播，业务零侵入；
黑马点评原版是单级 Redis，加 L1 时要按“数据变更频率”决定谁进 L1，并接受最终一致。
```

#### 4.1. Caffeine 本地缓存，为什么删除缓存而不是更新缓存？

```
【为什么删除缓存而不是更新缓存】

结论先行：删除是幂等、无时序问题、惰性回填、避免无效更新；
更新缓存有并发覆盖风险、计算代价、写多读少时纯浪费。

一、核心原因

1. 并发写时的时序问题（最关键）
   - 更新缓存：两个写请求并发，请求 A 先更新 DB（值=1），请求 B 后更新 DB（值=2），
     但 B 先写缓存、A 后写缓存，最终缓存是 1，DB 是 2，缓存和 DB 不一致。
   - 删除缓存：两个请求都只是删 Key，删是幂等的，谁先谁后结果都是“缓存为空”，
     下次读时从 DB 回填最新值，不会出现旧值覆盖新值。

2. 更新缓存有计算代价
   - 缓存 value 可能是多表聚合/复杂计算的结果。每次写都重新算一遍再写缓存，
     如果这个值之后没人读，计算就白费了。
   - 删除是惰性的：等真正有人读时再回填，按需计算，不浪费。

3. 写多读少时更新缓存纯浪费
   - 如果一个数据写频率远高于读频率，每次写都更新缓存，大部分更新都不会被读到。
   - 删除则只在读时回填，减少无效写。

4. 删除更简单、更不容易出错
   - 删除只需知道 key，不关心 value 怎么算。
   - 更新要保证算出来的新值正确、字段完整，逻辑更重。

二、删除方案的并发坑与补丁（要主动说，体现深度）

删除不是银弹，Cache Aside 有两种时序：

时序1：先删缓存，再更新 DB
- 坑：删完缓存、DB 还没更新时，并发读 miss 查 DB 读到旧值，回填缓存，
  之后 DB 更新，缓存却是旧值。
- 解法：延迟双删——先删缓存 → 更新 DB → 延迟几百毫秒再删一次缓存，
  把中间回填的旧值删掉。

时序2：先更新 DB，再删缓存（推荐）
- 坑：读请求在删缓存前读到旧值并回填，删缓存后缓存是旧值。
  但这个窗口极小（读+回填比写 DB 快），概率低。
- 解法：TTL 兜底 + 延迟双删；极端场景用 binlog 订阅（Canal）异步删。

结论：先更新 DB 再删缓存是主流，配合 TTL 兜底和延迟双删，追求最终一致。

三、Caffeine 本地缓存场景的特殊性

1. Caffeine 原生支持删除
   - invalidate(key) / invalidateAll() 是原生 API，语义清晰；
     更新要用 put 覆盖，反而要自己保证 value 正确。

2. L1 删除必须广播
   - Caffeine 在每个服务节点各一份，删本节点不够，要广播通知所有节点 invalidate，
     否则节点 B 的 L1 还是旧值（呼应多级缓存一致性）。
   - 广播可用 Redis Pub/Sub 或 MQ 广播模式。

3. L1 设短 TTL 兜底
   - 即使广播漏了，TTL 过期后自然失效，把不一致窗口控制在 TTL 内。

4. 只把极少变更的数据放 L1
   - 变更频繁的数据只放 Redis，不放 Caffeine，从源头减少一致性维护成本。

【一句话总结】
删除缓存 = 幂等、无并发覆盖、惰性回填、避免无效更新、实现简单；
更新缓存有“旧值覆盖新值”的时序风险和计算浪费；
删除方案要配合“先更 DB 再删 + 延迟双删 + TTL 兜底”处理并发坑；
Caffeine 场景下删除要广播通知所有节点 invalidate + 短 TTL 兜底。
```

#### 4.2. 本地缓存删了之后怎么同步给其他节点

```
【本地缓存删了之后怎么同步给其他节点】

先明确问题：Caffeine 是 JVM 进程内缓存，每个服务节点各一份，天然不共享。
节点 A 删了自己的 L1，节点 B/C 的 L1 还是旧值，请求落到 B 就读到脏数据。
所以需要一个"跨节点失效通知"机制，把"删 key"这个动作广播给所有节点。

一、同步通道的三种选择（按可靠性/重量级排序）

方案1：Redis Pub/Sub（轻量，中小规模）
- 做法：写操作删完本节点 L1 后，向 Redis 频道 publish 一条失效消息；
  所有节点订阅该频道，收到消息后 invalidate 自己的 L1。
- 优点：实现简单、延迟低（毫秒级）、不引入新中间件。
- 缺点：消息不持久，节点重启/网络抖动期间会漏消息；无重试、无 ACK。
- 适用：节点数不多、能接受偶发漏消息并用 TTL 兜底的场景。

方案2：MQ 广播模式（可靠，生产推荐）
- 做法：用 RabbitMQ 的 fanout 交换机，或 RocketMQ 的广播消费模式，
  每个节点作为一个消费者组内的独立消费者，都能收到同一条消息。
- 优点：消息持久化、有重试、有 ACK，节点短暂离线后能补收；
  可靠性远高于 Pub/Sub。
- 缺点：引入 MQ，架构变重；广播消费要注意每个节点都要消费到（不是集群消费）。
- 适用：生产环境、节点多、对一致性要求较高的场景。

方案3：配置中心/注册中心推送（偏重量级）
- 做法：用 Nacos 配置变更推送、ZooKeeper watcher 等机制通知节点。
- 优点：复用现有基础设施，适合配置类、极低频变更数据。
- 缺点：不适合高频缓存失效场景，语义偏"配置"而非"缓存事件"。
- 适用：店铺类型、开关配置这类几乎不变的数据。

二、消息体设计（发什么）
- key：要失效的缓存 key（如 shop:1001）。
- 操作类型：invalidate / update（一般只发 invalidate，让各节点删）。
- 版本号/时间戳：用于消费端判断消息新旧，防止乱序导致旧消息覆盖新状态。
- 发送方标识（可选）：便于排查问题。

三、消费端逻辑（怎么收）
1. 收到消息 → 解析 key → 调用 Caffeine.invalidate(key) 删除本地缓存。
2. 幂等处理：重复收到同一条消息，重复 invalidate 是无害的（删不存在的 key 不报错），
   天然幂等。
3. 乱序处理：用版本号/时间戳比较，只处理比本地更新的失效事件，
   避免旧消息把新缓存删掉（虽然删了也会回源，但减少无效回源）。
4. 失败处理：invalidate 本身很少失败；如果消费逻辑复杂（如要重新加载），
   失败要重试或记录告警。

四、兜底手段（漏消息怎么办，面试重点）
广播机制再可靠也可能漏，必须有兜底：
1. L1 设短 TTL：即使漏了广播，TTL 过期后自然失效，把不一致窗口控制在 TTL 内。
2. 版本号校验：L1 value 带版本号，读时比对 Redis 中的版本（轻量查询），
   版本旧就回源。代价是多一次 Redis 读。
3. 定时全量刷新：定时任务定期清空/刷新 L1，兜底极端遗漏。
4. 启动预热：节点启动时从 Redis 重新加载 L1，避免带着旧数据上线。

五、黑马点评场景的落地思考
- 原版黑马点评是单级 Redis，没有 L1，所以原版不存在这个问题。
- 如果加 Caffeine 做多级缓存，我会这样设计：
  a) 写操作：更新 DB → 删 Redis → 通过 Redis Pub/Sub（或 MQ 广播）发失效消息；
  b) 各节点订阅消息，收到后 invalidate 本地 Caffeine；
  c) L1 设短 TTL（如 3~5 分钟）兜底；
  d) 只把店铺类型这类极少变更的数据放 L1，店铺详情仍以 Redis 为准；
  e) 如果要求更高，上 Canal 监听 binlog + MQ 广播，业务零侵入。
- 诚实说：多级缓存追求最终一致，广播 + TTL 兜底是工程常态，不追求强一致。

【一句话总结】
本地缓存删除后，靠"Redis Pub/Sub（轻量）或 MQ 广播（可靠）"把失效消息推给所有节点，
各节点收到后 invalidate 自己的 L1；
消息体带 key + 版本号，消费端幂等 + 防乱序；
再用"L1 短 TTL + 版本校验 + 定时刷新 + 启动预热"兜底漏消息；
多级缓存是最终一致，不是强一致。
```

#### 4.3. 分布式锁，Redisson 相对于 SETNX 好在哪

```
【Redisson 相对于 SETNX 好在哪】

结论先行：SETNX 是一个裸的互斥命令，Redisson 是在它之上做了生产级封装，
把分布式锁的续期、可重入、安全释放、重试、原子性全部内置了。
不是“功能更多”，而是“把 SETNX 方案在线上会踩的坑都填了”。

逐项对比：

1. 锁续期（最核心的差异）
   - SETNX 方案：必须自己估一个过期时间，业务跑超了就锁提前释放，并发穿透。
     要续期得自己写后台线程定时 EXPIRE，复杂且容易出错。
   - Redisson：内置看门狗（Watchdog）。用无参 lock() 时默认锁 30 秒，
     后台每 10 秒（租期的 1/3）检查一次并续期到 30 秒，
     业务没跑完锁就不会丢；释放锁时自动取消续期任务[citation:1][citation:2]。
   - 注意：调 lock(leaseTime) 显式指定时间会关闭看门狗，要小心[citation:12]。

2. 可重入性
   - SETNX 方案：同一线程再次获取同一把锁，SETNX 直接失败，自己把自己锁死。
   - Redisson：用 Hash 结构存“线程 ID → 重入次数”，同一线程重入时次数 +1，
     释放时 -1，减到 0 才真正删锁，语义和 ReentrantLock 一致[citation:1][citation:3]。

3. 锁释放安全性
   - SETNX 方案：业务超时后锁已过期，别的线程拿到了锁，
     原线程执行完再 DEL，就把别人的锁删了。
   - Redisson：释放锁用 Lua 脚本，先校验锁的持有者是不是当前线程，
     是才删，不是直接返回，原子且不会误删[citation:1][citation:6]。

4. 获取失败后的重试机制
   - SETNX 方案：失败即返回，调用方自己 while 循环重试，简单粗暴、浪费 CPU。
   - Redisson：tryLock(waitTime, ...) 支持等待，底层基于 Redis Pub/Sub——
     获取失败后订阅锁释放频道，别人释放时收到通知再竞争，
     而不是无脑自旋[citation:3]。

5. 原子性
   - SETNX 方案：早期 SETNX + EXPIRE 是两条命令，中间宕机就死锁；
     现在用 SET NX PX 一条命令解决加锁原子性，但释放和续期仍要自己写 Lua。
   - Redisson：加锁、续期、释放全部封装成 Lua 脚本，单线程原子执行，
     调用方不用关心底层命令组合[citation:1]。

6. 附加能力（体现工程化）
   - 公平锁、读写锁（RReadWriteLock）、联锁（MultiLock）、红锁（RedLock）等，
     SETNX 方案全部要自己实现[citation:1]。

边界（要诚实说，体现深度）：
- Redisson 也没解决 Redis 主从异步复制导致切主丢锁的极限问题。
  主节点加锁成功但未同步就宕机，从节点升主后锁丢失，其他客户端可重复加锁。
  需要 RedLock（多独立节点）或业务层唯一索引/乐观锁兜底[citation:6]。
- 所以 Redisson 是“工程上够用”，不是“理论绝对安全”。

【一句话总结】
SETNX 只给你“互斥”这个原语，续期、重入、安全释放、重试全要自己写；
Redisson 把这些用 Lua + 看门狗 + Hash 结构封装好了，
是 Java 分布式锁的事实标准[citation:8]；
但它不解决主从丢锁的极限，强一致场景仍需业务兜底。
```
