### 1. Redis 集群；怎么选新主节点？怎么做流量分发和路由？

```
【问题1：Redis Cluster 怎么选新主节点】

结论：从节点发现主节点故障后，发起选举，获得超过半数 master 节点投票的从节点当选新主。

流程分四步：

1. 故障判定
   - 集群节点通过 Gossip 协议互相通信。
   - 当某个 master 被多数 master 标记为 FAIL（经过 cluster-node-timeout 判定），进入故障转移流程。

2. 从节点发起选举
   - 故障 master 的从节点发现主节点 FAIL 后，将自己的 currentEpoch 加 1，
     向集群广播 FAILOVER_AUTH_REQUEST 请求投票[citation:12]。
   - 其他 master 收到请求后，校验合法性，每个 epoch 只投一票，
     返回 FAILOVER_AUTH_ACK[citation:12]。

3. 延迟机制（谁先发起有讲究）
   - 从节点不是立刻选举，而是延迟：
     500ms + random(0~500ms) + SLAVE_RANK * 1000ms[citation:12]。
   - SLAVE_RANK 越小，表示该从节点复制的数据越新，延迟越短、越先发起选举，
     理论上持有最新数据的从节点优先当选，减少数据丢失。

4. 过半当选
   - 从节点收集到**超过半数 master** 的 ACK 后，成为新 master，广播通知集群[citation:12]。
   - 这也是为什么集群至少需要 3 个 master：2 个 master 挂一个只剩 1 个，凑不够半数。

补充：Redis Cluster 的选举和哨兵类似，但投票者是 master 节点，不是独立的 sentinel 进程。

---

【问题2：怎么做流量分发和路由】

结论：Redis Cluster 用 16384 个哈希槽做数据分片，客户端根据槽位映射直接访问对应节点，重定向时更新本地路由缓存。

1. 数据分片：哈希槽
   - 整个 key 空间划分为 16384 个 slot。
   - 每个 master 节点负责一部分 slot（如 3 节点：0-5460 / 5461-10922 / 10923-16383）。
   - key 到 slot 的映射：CRC16(key) % 16384。

2. 客户端路由
   - 客户端启动时连接集群任意节点，获取 slot 与节点的映射关系并缓存。
   - 访问 key 时，客户端先算 slot，查本地缓存，直接发往对应节点。
   - 如果缓存过期或 key 迁移了，目标节点返回 MOVED 重定向（携带正确节点地址），
     客户端更新缓存后重试。

3. 为什么是客户端路由而不是代理
   - 原生 Redis Cluster 没有中心代理，路由逻辑在客户端（JedisCluster/RedisTemplate 的集群支持）。
   - 好处：无单点、少一跳；代价：客户端需要维护路由表，跨 slot 的多 key 操作受限。
   - 如果业务需要代理层（如 Codis），那是另一套方案。

4. 跨 slot 的限制
   - 多 key 操作（MGET/MSET/Lua 操作多个 key）要求所有 key 在同一个 slot。
   - 用 hash tag 解决：key 中用 {} 包裹相同子串，如 user:{1001}:name 和 user:{1001}:age，
     强制映射到同一 slot。

【一句话对比】
哨兵解决“主从切换 + 通知客户端”，Cluster 解决“数据分片 + 自动故障转移 + 客户端路由”。
Cluster 的选举靠 master 投票过半，路由靠 CRC16 映射 16384 槽 + MOVED 重定向。
```

### 2. Redis 宕机怎么办，一致性怎么保证？

```
【问题1：Redis 宕机怎么办】

分两层：数据别丢（持久化）、服务别断（高可用）。

1. 持久化：防止重启后数据全丢
   - RDB：定时快照，恢复快，但两次快照之间的数据会丢。
   - AOF：记录每条写命令，everysec 策略最多丢 1 秒数据，更安全但文件更大。
   - 生产建议 RDB + AOF 混合，兼顾恢复速度和数据安全。

2. 主从复制：数据有副本
   - 主节点写，从节点同步。主挂了，从节点还有一份数据[citation:2]。
   - 全量同步 + 增量同步（基于 offset 和复制积压缓冲区）。

3. 哨兵 / Cluster：自动切主
   - 哨兵监控主节点，主观下线 → 多个哨兵确认客观下线 → 选举从节点升主[citation:9]。
   - 客户端通过哨兵获取新主地址，服务恢复。
   - 如果是 Cluster，故障转移由 master 投票完成。

秒杀场景的补充：库存预热在 Redis，宕机后从节点升主，库存数据还在（前提是主从同步没丢太多）。如果用的是 AOF everysec，极端情况丢 1 秒的扣减记录，靠 DB 对账补偿。

---

【问题2：一致性怎么保证】

先定性：秒杀追求最终一致性，不是强一致。强一致（分布式事务）扛不住秒杀性能，业务上允许“Redis 扣了、DB 稍后落”的窗口。

我分三层保证：

第一层：Redis 内部的一致性（防超卖/防重复）
- Lua 脚本把“判库存 + 扣库存 + 记录用户”原子执行，Redis 单线程保证不被打断。
- 这一层保证 Redis 自己的库存和用户 Set 不会出现半扣、重复扣。

第二层：Redis 与 MySQL 的一致性（异步落库的可靠性）
- 生产端：Lua 校验通过后发 MQ，用 confirm 机制确保消息到达 Broker；发送失败回滚 Redis 预扣。
- Broker：持久化 + 副本，防丢消息。
- 消费端：手动 ACK，处理成功才确认；失败重试，多次失败进死信队列。
- 消费幂等：以订单号/用户券 ID 为唯一键，依赖 DB 唯一索引，重复消费直接忽略。
- DB 层兜底：乐观锁 update ... where stock > 0，影响行数为 0 说明库存异常，回滚 Redis。

第三层：对账补偿（最终兜底，面试一定要提）
- 这是秒杀一致性的“保险丝”。因为上面的链路再严密，也可能有极端情况：应用在发 MQ 后、消费前挂了；消费重试一直失败；Redis 主从切换丢了一点数据。
- 方案：定时任务/独立对账服务，比对 Redis 库存、DB 库存、订单表三者。
- 发现不一致：以 DB 为准修正 Redis，或对缺失订单补单/退款，并告警。
- 更工程化的做法是订阅 MySQL binlog，实时解析后与 Redis 对比，发现差异触发补偿[citation:5][citation:13]。

【一句话总结】
宕机靠“持久化 + 主从 + 哨兵”保数据和可用性；
一致性靠“Lua 原子防内部竞态 + MQ 可靠投递 + 消费幂等防落库丢失/重复 + 对账兜底防极端情况”。
秒杀不追求强一致，追求的是“正常链路大概率一致、异常链路最终收敛”。
```

### 3. Redis 数据结构，Zset 和 Set 区别

```
【Redis 数据结构有哪些】

先说清楚：Redis 对外有 9 种数据类型，底层还有多种编码实现，面试先答对外类型。

常用 5 种基础类型：
1. String：最基础，存字符串/数字/二进制，用于缓存对象、计数器（INCR）、分布式锁（SETNX）。
2. Hash：键值对集合，存对象属性，可单独读写字段，用于用户信息、购物车。
3. List：双向链表，有序可重复，用于消息队列（LPUSH+BRPOP）、时间线。
4. Set：无序去重集合，用于点赞去重、共同关注（SINTER）、抽奖。
5. ZSet（SortedSet）：带 score 的有序去重集合，用于排行榜、延迟队列、点赞按时间排序。

进阶 4 种：
6. BitMap：位图，按位存储，用于签到、活跃用户统计，极省内存。
7. HyperLogLog：基数统计，用于 UV 去重计数，误差约 0.81%，极省内存。
8. GEO：地理坐标，用于附近的人/店。
9. Stream：消息队列，支持消费组、ACK，用于异步下单。

底层编码（被追问时说）：
- String：int / embstr / raw
- Hash：listpack / hashtable
- List：quicklist
- Set：intset / listpack / hashtable
- ZSet：listpack / skiplist + dict
编码随元素数量和大小自动转换，小数据用紧凑编码省内存，大了转哈希表/跳表。

---

【ZSet 和 Set 的区别】

核心一句话：Set 无序去重，ZSet 有序去重，区别在“有没有 score 以及是否按 score 排序”。

1. 语义
   - Set：只存 member，无序，自动去重。判断“在不在”。
   - ZSet：存 member + score，按 score 升序排列，member 去重，score 可重复。
     score 相同时按 member 字典序排列。判断“在不在 + 排第几”。

2. 底层实现
   - Set：小数据 intset/listpack，大数据 hashtable，只保证 O(1) 判断存在。
   - ZSet：小数据 listpack，大数据 skiplist + dict 双结构：
     a) dict：member → score，O(1) 查分数；
     b) skiplist：按 score 有序，支持 O(log N) 范围查询和排名。
     双结构是空间换时间，兼顾“按 member 查分”和“按 score 范围/排名”。

3. 常用命令与复杂度
   - Set：SADD / SISMEMBER / SINTER / SCARD，判断和集合运算 O(1)~O(N)。
   - ZSet：ZADD / ZSCORE / ZRANGE / ZREVRANGE / ZRANK / ZINCRBY，
     插入和范围查询 O(log N)，按 member 查分 O(1)。

4. 项目场景
   - 点赞：用 Set，SADD 去重，SISMEMBER 判断是否点过，SCARD 统计点赞数。
   - 点赞排行榜/按时间排序：用 ZSet，score 存时间戳，ZREVRANGE 按时间倒序取 Top N。
   - 共同关注：用 Set 的 SINTER 求交集，比 ZSet 更直接。

【一句话总结】
Set 解决“去重 + 存在性判断”，ZSet 在去重基础上加 score 排序，
底层用 skiplist + dict 兼顾范围查询和单点查分；
选型看业务要不要“排序/排名”，要排序就用 ZSet，只判重就用 Set。
```

### 4. ZSet 底层数据结构和原理

```
【ZSet 底层数据结构和原理】

结论先行：ZSet 不是单一结构，而是按数据量在"紧凑编码"和"跳表 + 字典"之间自动切换，
核心目标是内存和性能的权衡。

一、整体设计：两种形态，按阈值切换
- 触发条件：元素数量 ≤ 128 且每个元素长度 ≤ 64 字节
  （配置项 zset-max-listpack-entries / zset-max-listpack-value，7.0 前叫 ziplist 版本）。
- 满足条件：用紧凑编码，一块连续内存存数据，省指针开销。
- 超过阈值：自动转成"跳表 + 字典"组合结构，保证大数据量下的查询性能。

二、小数据量：紧凑编码（ZipList / ListPack）
- Redis 7.0 之前用 ZipList，7.0 及之后用 ListPack。
- 存储方式：按 [member1, score1, member2, score2 ...] 紧挨着存，整体按 score 升序。
- 查找是线性遍历，但数据量小、内存连续、对 CPU 缓存友好，实际够用。
- 为什么 7.0 换成 ListPack：ZipList 每个节点记录前一个节点长度，修改中间节点可能引发
  连锁更新（cascade update），ListPack 改成只记录自身长度，避免这个问题。

三、大数据量：跳表 + 字典（双结构配合）
- 字典 Dict：存 member → score 映射。
  作用：ZSCORE 按成员查分数 O(1)，不用遍历。
- 跳表 SkipList：按 score 有序的多层链表。
  作用：ZRANGE / ZRANK 范围查询和排名 O(logN)。
- 关键点：字典的 value 和跳表节点指向同一个 member/score 对象，共享数据，不重复存储。
- 为什么需要两个结构：单一结构无法同时做到"按 member O(1) 查分"和"按 score 有序范围查询"，
  双结构是空间换时间，各司其职。

四、跳表原理（面试重点）
1. 多层索引：底层 Level1 是完整有序链表，上层是稀疏"快车道"，用空间换时间。
2. 查找过程：从最高层开始，目标比当前节点大就往右，小就下降一层，逐层缩小范围，
   最终在底层定位。平均 O(logN)，类似二分。
3. 随机层数：插入时随机决定层数，Redis 每层晋升概率约 25%，最高 32 层。
   随机保证结构平衡，插入删除只改局部指针，不需要旋转。
4. span（跨度）：每层指针记录跨越的节点数，ZRANK 靠累加 span 快速算排名。

五、为什么用跳表而不是红黑树（高频追问）
1. 范围查询更高效：跳表底层是链表，定位起点后顺序遍历，对 CPU 缓存友好；
   红黑树范围查询要中序遍历，指针跳转多，缓存不友好。
2. 实现更简单：跳表插入删除只改指针；红黑树要旋转 + 变色，维护复杂。
3. 内存更可控：跳表可通过概率参数调整索引内存占比；红黑树每节点固定两个指针 + 颜色位。

六、一句话总结
ZSet 小数据用 ListPack 紧凑编码省内存，大数据用"字典保 O(1) 查分 + 跳表保 O(logN) 范围查询"
双结构兼顾性能；跳表凭范围查询友好、实现简单成为有序性支撑，span 支撑排名计算。
```

### 5. Redis 秒杀券用什么数据结构？

```
【秒杀券用什么数据结构】

结论：不是一个结构，而是多个结构组合，按业务动作各司其职，最后用 Lua 串成原子操作。

1. 库存：String
   - Key：seckill:stock:{voucherId}，Value：剩余库存数。
   - 为什么用 String：库存就是一个数字，String 的 DECR / INCRBY 原子且轻量，
     配合 Lua 做"判断 > 0 再扣减"，是最直接的选择。
   - 为什么不用 Hash：Hash 适合存对象多字段，库存只是单值，String 更省更简单。

2. 一人一单：Set
   - Key：seckill:order:{voucherId}，Member：已成功下单的 userId。
   - 为什么用 Set：需要"去重 + O(1) 判断是否已下单"，SISMEMBER 正好，
     SADD 天然去重，比 String 存列表再遍历高效得多。
   - 为什么不用 ZSet：一人一单不需要排序，ZSet 的 skiplist 开销多余，Set 更省内存。

3. 订单/资格信息：Hash 或 MQ 消息体
   - 校验通过后，订单信息（userId、voucherId、订单号）封装成消息投递 MQ，
     消息体本身可用 JSON/String 承载。
   - 如果要在 Redis 里暂存订单详情，可用 Hash 存多字段（订单号、用户、券、时间），
     方便单独读写字段。
   - 黑马点评里主要是"Set 记录用户 + MQ 消息传订单信息"，DB 落库后才是订单表。

4. 辅助信息：String
   - 活动状态/开始结束时间可用 String 存，或在 Java 侧判断后作为 Lua 参数传入。
   - 如果要做库存流水/对账，可另用 List 或 Stream 记录扣减日志。

5. 为什么这些结构能协同
   - 库存 String + 用户 Set 在同一个 Lua 脚本里被原子操作：
     先读库存判断，再 SISMEMBER 判重，最后 INCRBY 扣减 + SADD 记录。
   - 多结构组合 + Lua 原子执行 = 防超卖 + 一人一单，且请求不打 DB。

【一句话总结】
库存用 String（原子扣减），一人一单用 Set（去重判重），订单信息走 MQ/Hash，
辅助状态用 String；多结构各司其职，Lua 把它们串成一个原子校验单元。
```
