### 1. 对 MySQL 事务的了解

```
【对 MySQL 事务的了解】

我按"ACID → 隔离级别 → MVCC 和锁 → 日志"四层讲。

一、事务的 ACID 及实现机制
- 原子性（A）：事务要么全成功要么全回滚。靠 undo log 实现——回滚时按 undo log 反向操作。
- 一致性（C）：事务前后数据满足约束，是最终目标，靠 AID 共同保证。
- 隔离性（I）：并发事务互不干扰。靠锁 + MVCC 实现。
- 持久性（D）：提交后数据不丢。靠 redo log 实现——先写 redo log 再刷盘，崩溃可恢复。
一句话：A 靠 undo，D 靠 redo，I 靠锁和 MVCC，C 是它们共同的结果。

二、隔离级别与并发问题
四种隔离级别（从低到高）：
1. 读未提交（RU）：能读到别的事务未提交的数据，有脏读。
2. 读已提交（RC）：只能读已提交的，解决脏读，但有不可重复读。
3. 可重复读（RR）：同一事务内多次读结果一致，解决不可重复读，MySQL InnoDB 默认级别。
4. 串行化（Serializable）：完全串行，解决所有问题，但性能最差。

三类并发问题：
- 脏读：读到未提交数据（RU 有）。
- 不可重复读：同一事务两次读同一行结果不同（RC 有）。
- 幻读：同一事务两次范围查询，第二次多了/少了行（RR 下用间隙锁 + MVCC 基本解决）。

RR 下解决幻读的两条路：
- 快照读：MVCC 保证同一事务读的是同一个 ReadView，看不到别的事务新插入的行。
- 当前读：用 Next-Key Lock（记录锁 + 间隙锁）锁住范围，防止别的事务插入。

三、MVCC（多版本并发控制，重点）
- 目的：让读不加锁，读写不阻塞，提高并发。
- 实现三要素：
  a) 隐藏字段：每行有 trx_id（最后修改的事务 ID）、roll_pointer（指向 undo log 版本链）。
  b) undo log 版本链：每次修改生成一个旧版本，roll_pointer 串成链。
  c) ReadView：事务读时生成一个快照，记录当前活跃事务 ID 列表，
     据此判断版本链中哪个版本对当前事务可见。
- 快照读 vs 当前读：
  - 快照读：普通 SELECT，走 MVCC，读历史版本，不加锁。
  - 当前读：SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE，
    读最新版本并加锁。
- RC 和 RR 的关键区别：
  - RC：每次 SELECT 都生成新 ReadView，所以能读到别的事务已提交的新数据（不可重复读）。
  - RR：只在第一次 SELECT 生成 ReadView，后续复用，所以同一事务读结果一致。

四、日志与两阶段提交
- undo log：逻辑日志，记录反向操作，用于回滚和 MVCC 版本链。
- redo log：物理日志，记录"某页某偏移改了什么"，循环写，保证持久性（WAL：先写日志再刷盘）。
- binlog：Server 层逻辑日志，记录 SQL 语句或行变更，用于归档和主从复制。
- 两阶段提交：为了保证 redo log 和 binlog 一致——
  先写 redo log 置 prepare → 写 binlog → redo log 置 commit。
  崩溃恢复时：redo 是 prepare 但 binlog 没写，回滚；binlog 写了，提交。

五、项目落地（秒杀扣库存）
- 秒杀落库时，扣库存 + 插订单放在一个事务里，保证原子性。
- 扣库存用乐观锁：update ... set stock = stock - 1 where id = ? and stock > 0，
  影响行数为 0 说明库存不足，回滚事务。
- 唯一索引 (user_id, voucher_id) 防重复下单，插入冲突抛异常回滚。
- 这里用乐观锁而不是 SELECT FOR UPDATE，是因为秒杀并发高，悲观锁行锁等待会拖垮 DB。

【一句话总结】
ACID 靠 undo/redo/锁和 MVCC 实现；InnoDB 默认 RR，用 MVCC 解决快照读幻读、
间隙锁解决当前读幻读；MVCC 靠隐藏字段 + undo 版本链 + ReadView；
redo/undo/binlog 分工保证持久性、回滚和主从一致，两阶段提交保证 redo 和 binlog 一致。
```

#### 1.1. 怎么用事务去满足两个表的校验

```
【怎么用事务满足两个表的校验】

结论先行：两个表的写操作放进同一个事务保证原子性；
但事务只保证"要么都成要么都回滚"，不保证并发正确，
所以校验要靠"条件更新（乐观锁）+ 唯一索引"在事务内完成，事务是兜底。

以秒杀下单为例：扣库存表 seckill_voucher + 插订单表 voucher_order。

一、事务边界：两个写操作包在一个事务里
- 用 @Transactional 注解（或编程式 TransactionTemplate）包住"扣库存 + 插订单"。
- 任一步失败抛异常，整个事务回滚，不会出现"扣了库存没订单"或"有订单没扣库存"。
- 注意回滚条件：默认只对 RuntimeException 回滚，
  受检异常要 @Transactional(rollbackFor = Exception.class) 显式指定。

二、两类校验分别放在哪

校验1：库存是否充足（业务校验 + 扣减，合成一条 SQL）
- 不要"先 SELECT 查库存，再 UPDATE 扣减"——两步之间并发请求会插进来，超卖。
- 用条件更新把校验和扣减合成原子操作：
  update seckill_voucher set stock = stock - 1
  where voucher_id = ? and stock > 0;
- 影响行数为 0 说明库存不足（校验失败），直接抛异常回滚事务。
- 这就是乐观锁：where stock > 0 是 CAS 条件，数据库行锁保证单条 UPDATE 原子。

校验2：是否重复下单（靠唯一索引兜底）
- 订单表建唯一索引 (user_id, voucher_id)。
- 插入订单时如果已存在，抛 DuplicateKeyException，事务回滚，库存扣减也回滚。
- 为什么不用"先查订单再插入"：查和插之间并发会插进来，唯一索引是数据库层原子约束，最可靠。

三、并发安全：事务 + 乐观锁 + 唯一索引三者配合
- 事务：保证扣库存和插订单原子，失败一起回滚。
- 乐观锁 where stock > 0：保证并发扣减不超卖。
- 唯一索引：保证并发插入不重复。
- 三者缺一不可：光有事务，两个并发请求都通过校验会超卖；
  光有乐观锁，订单插入失败库存已扣会不一致；唯一索引让冲突回滚，事务保证回滚彻底。

四、事务里的坑（体现真用过）
1. 不要在事务里做远程调用/发 MQ：事务未提交时发消息，消息可能先被消费读到未提交数据；
   且远程调用耗时长，导致长事务、锁持有久。
   - 做法：事务提交后再发 MQ（用 TransactionSynchronization 的 afterCommit 回调），
     或本地消息表保证最终一致。
2. @Transactional 自调用失效：同类内部方法调用不走代理，事务不生效。
   - 做法：拆到另一个 Bean，或注入自身代理。
3. 异常被 catch 吞掉：catch 了没重新抛，事务感知不到异常，不回滚。
   - 做法：catch 后要么重新抛，要么手动 setRollbackOnly。
4. 事务尽量短：只包 DB 写操作，校验前置、远程调用后置，减少锁持有时间。

五、落到秒杀完整链路
- Redis + Lua 做前置校验（库存、一人一单），挡掉绝大部分请求；
- 通过校验的请求异步落库，落库时：
  a) 开事务；
  b) 乐观锁扣库存，影响行数 0 则回滚；
  c) 插订单，唯一索引冲突则回滚；
  d) 事务提交后发 MQ/更新缓存（afterCommit）。
- 事务是最后一道一致性保障，前面 Redis 挡并发，DB 事务 + 约束兜底。

【一句话总结】
两个表的写放同一事务保证原子性；
校验靠"条件更新 where stock > 0（乐观锁）+ 唯一索引"在事务内完成，
事务负责失败一起回滚；
并发正确性靠乐观锁和唯一索引，事务只是兜底；
注意长事务、自调用失效、异常吞掉、事务内发 MQ 这几个坑。
```

#### 1.2. 实现可重复读会有什么问题

```
【实现可重复读会有什么问题】

先讲机制，再讲问题——RR 的问题都来自它的实现方式。
RR 的实现：快照读靠 MVCC（ReadView + undo 版本链），当前读靠 Next-Key Lock（记录锁 + 间隙锁）。
由此带来三类问题：幻读残留、性能运维代价、并发度下降。

一、隔离性上的残留：幻读没有被彻底根除
1. 快照读：MVCC 让事务看不到别的事务新插入的行，读层面避免幻读。
2. 当前读：Next-Key Lock 锁住范围，阻止范围内插入，当前读层面避免幻读。
3. 但混合场景仍有残留：
   - 事务先快照读（看到旧数据），再当前读（UPDATE / SELECT FOR UPDATE），
     当前读读的是最新已提交数据，可能"看到"快照读没见过的行，出现幻读。
   - 所以 RR 是"基本解决"幻读，不是"完全杜绝"。
   - 严格说，只有串行化才能完全避免，但性能代价太大。

二、性能和运维代价（核心，面试重点）

问题1：长事务导致 undo log 膨胀
- ReadView 在事务第一次读时创建，贯穿整个事务。
- 只要事务不结束，数据库就必须保留它可能需要的所有旧版本，undo log 不能 purge。
- 后果：
  a) undo 表空间持续膨胀，可能撑爆磁盘；
  b) 版本链变长，快照读遍历成本上升，查询变慢；
  c) 数据库关闭、备份变慢。
- 一个没提交的长只读事务，就能让整个库的 undo 无法回收，这是生产大坑。

问题2：间隙锁导致并发度下降和死锁
- RR 用间隙锁防当前读幻读，锁住了本可以不锁的"间隙"。
- 后果：
  a) 两个事务在相邻间隙插入，容易锁等待甚至死锁；
  b) 扫描到的行锁通常持有到事务结束，锁持有时间长，并发度低；
  c) 相比 RC 的 semi-consistent read（不匹配的行提前释放锁），RR 锁冲突明显更多。

问题3：版本链遍历开销
- 事务越久、修改越多，undo 版本链越长，快照读要沿链找可见版本，成本越高。
- 高并发长事务下，这个开销会累积。

三、业务层面的取舍：RR 不是唯一选择
- 很多互联网公司把默认隔离级别从 RR 改成 RC，原因：
  a) RC 无间隙锁，并发度高、死锁少；
  b) RC 每次 SELECT 生成新 ReadView，undo 回收快，不易膨胀；
  c) 业务层用乐观锁（where stock > 0）+ 唯一索引防超卖/防重复，
     不依赖 RR 的间隙锁也能保证正确性。
- 代价：RC 有不可重复读，同一事务两次读可能不同；对多数互联网业务可接受。
- 结论：隔离级别按业务选，RR 适合需要事务内一致性视图的场景，
  RC 适合高并发、能接受不可重复读的场景。

四、落到秒杀场景
- 秒杀扣库存是当前读：update ... where id = ? and stock > 0。
- 如果依赖 RR 的间隙锁锁 id 范围，并发度极差，秒杀扛不住。
- 实际方案：
  a) 主键/唯一索引的行锁 + 乐观锁条件，锁粒度小；
  b) Redis + Lua 在入口挡掉绝大部分并发；
  c) 数据库事务尽量短，避免长事务导致 undo 膨胀和锁持有久。
- 所以秒杀高并发下，不依赖 RR 的间隙锁防超卖，靠乐观锁 + 唯一索引 + 短事务。

【一句话总结】
RR 的问题：幻读只"基本解决"（混合场景仍残留）；
长事务让 undo log 无法回收、膨胀撑盘；
间隙锁降低并发度、增加死锁；
所以很多互联网业务改用 RC + 业务层乐观锁/唯一索引；
秒杀高并发不依赖 RR 间隙锁，靠短事务 + 乐观锁 + 唯一索引。
```

#### 1.3. 快照只有 Read View 就够了吗？还有什么其他的机制去实现这个视图？

```
【快照只有 ReadView 就够了吗？还有什么其他机制】

结论先行：不够。ReadView 只是"可见性判断规则"，它不存数据；
快照读是一套组合机制：隐藏字段标识版本 + undo log 版本链存历史版本 +
ReadView 判断可见性 + 遍历版本链找可见版本 + 隔离级别控制 ReadView 生成时机 +
purge 线程清理版本链。缺一不可。

一、ReadView 的定位：只是规则，不是数据
- ReadView 记录：当前活跃事务 ID 列表、最小活跃事务 ID（up_limit_id）、
  下一个事务 ID（low_limit_id）、创建者事务 ID。
- 作用：判断版本链上某个版本的 trx_id 对当前事务是否可见。
- 它本身不存储任何行数据，也不存历史版本，只是一个"判断依据"。
- 所以光有 ReadView，没有版本数据，什么也读不出来。

二、版本标识：行记录的隐藏字段
- 每行有两个关键隐藏字段：
  a) DB_TRX_ID：最后一次修改该行的事务 ID；
  b) DB_ROLL_PTR：回滚指针，指向 undo log 中该行的上一个版本。
- 没有这两个字段，系统不知道"当前版本是谁改的""怎么找到旧版本"，
  ReadView 判断出"不可见"后也无处可去。

三、版本存储：undo log 版本链
- 每次 UPDATE/DELETE，InnoDB 把修改前的旧值写入 undo log。
- 通过 DB_ROLL_PTR 把新旧版本串成链表，形成版本链。
- ReadView 判断当前版本不可见时，沿版本链往回找，直到找到可见版本。
- 版本链是快照读的"历史数据仓库"，没有它就没有可回溯的旧版本。

四、读取过程：遍历版本链 + 可见性判断
- 快照读（普通 SELECT）拿到行后：
  1. 取当前版本，用 ReadView 判断是否可见；
  2. 不可见则沿 roll_ptr 找上一个版本，再判断；
  3. 直到找到第一个可见版本，返回。
- 可见性判断规则（简化）：
  a) trx_id < up_limit_id：已提交，可见；
  b) trx_id >= low_limit_id：ReadView 之后的事务，不可见；
  c) trx_id 在活跃列表中：未提交，不可见；
  d) 否则可见。
- 这是"规则 + 数据"的配合：ReadView 给规则，版本链给数据。

五、生命周期：隔离级别控制 ReadView 生成时机
- RC：每次 SELECT 都生成新 ReadView，所以能读到别的事务已提交的新数据（不可重复读）。
- RR：只在第一次 SELECT 生成 ReadView，后续复用，所以同一事务读结果一致。
- 这个时机差异是"可重复读"成立的关键，属于事务系统对 ReadView 生命周期的管理。

六、清理：purge 线程控制版本链膨胀
- 版本链不能无限增长，否则 undo 表空间撑爆、遍历变慢。
- purge 线程清理"比最老活跃事务还早"的 undo log——
  这些版本已经不可能被任何活跃事务看到，可以安全删除。
- 长事务会阻止 purge，导致 undo 膨胀，这是 RR 的典型代价。

七、还有快照读 vs 当前读的路由
- 快照读：普通 SELECT，走 MVCC，不加锁。
- 当前读：SELECT FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE，
  读最新版本并加锁（Next-Key Lock）。
- 系统要能根据语句类型路由到不同读取逻辑，否则快照读隔离性无法保证。

【一句话总结】
ReadView 只是"判断规则"，不存数据；
快照读 = 隐藏字段（DB_TRX_ID/DB_ROLL_PTR）标识版本 +
undo log 版本链存历史版本 + ReadView 判断可见性 + 遍历版本链找可见版本 +
隔离级别控制 ReadView 生成时机（RC 每次、RR 首次）+ purge 线程清理版本链 +
快照读/当前读路由；
这几者合起来才构成完整的快照读实现。
```

#### 1.4. MVCC 底层是怎么实现的？

```
【MVCC 底层是怎么实现的】

结论先行：MVCC 不是单一机制，而是"隐藏字段 + undo log 版本链 + ReadView +
遍历判断规则 + purge 清理"的组合，目的是让读不加锁、读写不阻塞。

一、MVCC 的定位和目标
- 多版本并发控制：同一行数据保留多个历史版本，读操作读快照，不阻塞写，写也不阻塞读。
- 解决的是"读写并发"问题，靠版本链 + 可见性判断实现，而不是靠锁。

二、组件1：行记录的隐藏字段（版本标识）
- 每行有两个关键隐藏字段：
  a) DB_TRX_ID（6 字节）：最后一次插入/修改该行的事务 ID；
  b) DB_ROLL_PTR（7 字节）：回滚指针，指向 undo log 中该行的上一个版本。
- 作用：标识"当前版本是谁改的""怎么找到旧版本"。
- 没有它们，ReadView 判断出不可见后也无处回溯。

三、组件2：undo log 版本链（历史版本存储）
- 每次 UPDATE/DELETE，把修改前的旧值写入 update undo log，
  通过 DB_ROLL_PTR 把新旧版本串成链表。
- 一条记录被多次修改，就形成多版本链，最新版本在行上，旧版本在 undo 里。
- insert undo log 提交后可丢弃；update undo log 快照读还要用，不能立即删。
- 作用：给快照读提供可回溯的历史数据。

四、组件3：ReadView（可见性判断规则）
- ReadView 是快照读时生成的"判断依据"，包含四个字段：
  a) m_ids：当前活跃（未提交）事务 ID 集合；
  b) min_trx_id：活跃事务中最小 ID；
  c) max_trx_id：下一个将分配的事务 ID（当前最大 + 1）；
  d) creator_trx_id：创建该 ReadView 的事务 ID。
- 注意：ReadView 只存规则，不存行数据，不是"快照数据"本身。

五、读取过程：遍历版本链 + 可见性判断
- 快照读拿到一行后，从最新版本开始沿 DB_ROLL_PTR 往旧遍历，
  对每个版本的 DB_TRX_ID 按规则判断：
  1) DB_TRX_ID == creator_trx_id：本事务修改，可见；
  2) DB_TRX_ID < min_trx_id：ReadView 创建前已提交，可见；
  3) DB_TRX_ID >= max_trx_id：ReadView 创建后才开启的事务，不可见；
  4) DB_TRX_ID 在 m_ids 中：未提交，不可见；不在则已提交，可见。
- 找到第一个可见版本就返回，不再继续遍历。
- 本质：ReadView 给规则，版本链给数据，遍历把两者结合。

六、隔离级别决定 ReadView 生成时机（RC vs RR 的根因）
- RC（读已提交）：每次快照读都生成新 ReadView，
  所以能读到别的事务已提交的新数据 → 不可重复读。
- RR（可重复读）：只在事务第一次快照读生成 ReadView，后续复用，
  所以同一事务读结果一致 → 可重复读。
- 这是两者行为差异的根本原因，不是靠锁实现的。

七、purge 线程：清理版本链，防膨胀
- 版本链不能无限增长，否则 undo 表空间撑爆、遍历变慢。
- purge 线程清理"比最老活跃 ReadView 还早"的 undo 记录——
  这些版本已不可能被任何活跃事务看到，可安全删除。
- 长事务会阻止 purge，导致 undo 膨胀，这是 RR 长事务的典型代价。

八、补充：快照读 vs 当前读
- 快照读：普通 SELECT，走 MVCC，不加锁。
- 当前读：SELECT FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE，
  读最新版本并加锁（Next-Key Lock）。
- 系统根据语句类型路由到不同读取逻辑。

【一句话总结】
隐藏字段标识版本，undo log 版本链存历史数据，ReadView 给可见性规则，
遍历版本链找第一个可见版本返回；
RC 每次生成 ReadView、RR 首次生成复用，决定隔离行为差异；
purge 线程清理旧版本防膨胀，长事务会阻止 purge 导致 undo 膨胀。
```
