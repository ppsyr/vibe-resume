### 1. 进程、线程、协程

```
【进程、线程、协程是什么】

结论先行：进程是资源分配的最小单位，线程是 CPU 调度的最小单位，
协程是用户态的轻量级线程。
递进关系：进程包含线程，线程可以复用协程；隔离性递减，切换开销递减，并发密度递增。

一、定义与本质
1. 进程：操作系统分配资源（内存、文件句柄、CPU 时间）的基本单位。
   - 每个进程有独立地址空间，进程间隔离，一个崩溃不影响另一个。
2. 线程：CPU 调度的基本单位，是进程内的执行流。
   - 同一进程的线程共享地址空间和资源，只独占栈、寄存器和程序计数器。
3. 协程：用户态调度的轻量级线程，也叫"用户态线程"。
   - 由程序自己的调度器管理，不经过操作系统内核调度。
   - 一个线程可以跑成千上万个协程。

二、资源与开销对比（核心差异）
1. 地址空间：
   - 进程：独立地址空间，隔离性强。
   - 线程：共享进程地址空间，通信方便但需同步。
   - 协程：共享所属线程的栈和资源，更轻。
2. 创建/切换开销（从大到小）：
   - 进程：最大。创建要分配地址空间、页表；切换要换页表、刷 TLB、内核态切换。
   - 线程：中等。切换在内核态完成，要保存/恢复寄存器和栈，但不用换地址空间。
   - 协程：极小。切换在用户态完成，只保存少量寄存器上下文，不陷入内核。
3. 并发密度：
   - 进程/线程受系统资源限制，几千个线程就到瓶颈（每个线程栈默认 MB 级）。
   - 协程栈可以很小（KB 级），单机轻松几十万协程。

三、调度方式与通信
1. 调度者：
   - 进程/线程：由操作系统内核调度（抢占式）。
   - 协程：由用户态调度器调度（协作式或运行时调度，如 Go 的 GMP、Java 虚拟线程）。
2. 通信方式：
   - 进程间：IPC——管道、消息队列、共享内存、Socket、信号。
   - 线程间：共享内存 + 锁（synchronized/ReentrantLock）、volatile、并发容器。
   - 协程间：channel（Go）、共享变量 + 协程安全的同步原语。

四、适用场景与取舍
1. 进程：隔离性要求高。如浏览器多进程（一个标签页崩溃不影响其他）、
   服务多实例部署（故障隔离）。
2. 线程：CPU 密集计算、需要共享数据的并发。
   如 Java 线程池处理业务请求、并行计算。
3. 协程：I/O 密集、高并发、大量阻塞等待的场景。
   如网关、RPC 框架、高并发网络服务——用少量线程跑大量协程，
   避免线程上下文切换和栈内存开销。

五、落到秒杀/Java 场景
- Tomcat 默认用线程池处理请求，一个请求占一个线程。
  高并发下线程数暴涨，上下文切换和栈内存成为瓶颈。
- 如果换成协程（Java 21 虚拟线程 / Go goroutine）：
  I/O 等待（查 Redis、查 DB、发 MQ）时协程让出，线程去跑其他协程，
  少量线程就能扛高并发，减少切换开销。
- 但协程不是银弹：CPU 密集场景协程没优势；
  协程里做阻塞调用（如 JDBC 老驱动）会卡住底层线程，需要配套的非阻塞驱动。

【一句话总结】
进程是资源分配单位（隔离强、开销大），线程是 CPU 调度单位（共享地址空间、开销中），
协程是用户态轻量线程（用户态调度、开销极小、并发密度高）；
调度者从内核到用户态，开销从大到小，隔离性从强到弱；
进程适合隔离，线程适合 CPU 密集和共享数据，协程适合 I/O 密集高并发；
秒杀高并发下协程能用少量线程扛更多请求，但 CPU 密集和阻塞调用场景要谨慎。
```

### 2. TCP 三次握手、四次挥手

```
【TCP 三次握手、四次挥手】

一、三次握手（建立连接）

流程：
1. 客户端发 SYN（seq=x），进入 SYN_SENT，表示"我想建连接，我的初始序号是 x"。
2. 服务端回 SYN-ACK（seq=y, ack=x+1），进入 SYN_RCVD，
   表示"我收到了，我也要建连接，我的初始序号是 y，确认你的 x"。
3. 客户端回 ACK（ack=y+1），进入 ESTABLISHED；
   服务端收到 ACK 也进入 ESTABLISHED，连接建立。

为什么是三次，不是两次或四次：
1. 两次不够：服务端发完 SYN-ACK 就认为连接建立，但它无法确认客户端收到了
   SYN-ACK（客户端的 ACK 没到）。如果这个 SYN-ACK 丢了，服务端会空等，
   客户端却不知道，造成资源浪费。
2. 防止历史重复连接：网络中滞留的旧 SYN 到达服务端，两次握手会让服务端
   直接建立无效连接；三次握手下客户端不会对旧 SYN 回 ACK，服务端不会建立连接。
3. 四次多余：服务端的 SYN 和 ACK 可以合并在一个报文（SYN-ACK）里发，
   所以三次是保证"双方收发能力都确认"的最小次数。

本质：三次握手让双方都确认"我的发送能力、你的接收能力、你的发送能力、我的接收能力"都正常，
并同步双方的初始序列号（ISN）。

二、四次挥手（断开连接）

流程：
1. 客户端发 FIN（seq=u），进入 FIN_WAIT_1，表示"我没数据要发了"。
2. 服务端回 ACK（ack=u+1），进入 CLOSE_WAIT；
   客户端收到进入 FIN_WAIT_2。此时是"半关闭"：客户端不能再发数据，但还能收。
3. 服务端把剩余数据发完后，发 FIN（seq=w），进入 LAST_ACK，表示"我也没数据要发了"。
4. 客户端回 ACK（ack=w+1），进入 TIME_WAIT，等 2MSL 后进入 CLOSED；
   服务端收到 ACK 进入 CLOSED。

为什么是四次，不是三次：
- TCP 是全双工，两个方向要分别关闭。
- 客户端发 FIN 只表示"我没数据发了"，服务端可能还有数据要发，
  所以服务端的 ACK（确认收到 FIN）和 FIN（我也发完了）不能合并，要分两次发。
- 如果服务端也没数据了，ACK 和 FIN 可以合并，就变成三次挥手。
- 核心：四次是因为"一方关闭"和"另一方关闭"是两个独立事件，中间隔着服务端发剩余数据的时间。

三、高频追问点

1. TIME_WAIT 为什么等 2MSL（最大报文段生存时间）
   - 保证最后一个 ACK 能到达服务端：如果 ACK 丢了，服务端会重发 FIN，
     客户端在 2MSL 内还能收到并重发 ACK。
   - 让旧连接的报文在网络中消失：2MSL 后旧连接的所有报文都过期，
     新连接不会收到旧连接的干扰报文。
   - 2MSL = 一来一回的最大时间。

2. CLOSE_WAIT 过多说明什么
   - 服务端收到 FIN 回了 ACK，但应用层一直没调用 close() 发 FIN。
   - 通常是代码 bug：连接用完没关闭、异常路径漏了 close、连接池泄漏。
   - 排查：查应用代码和连接池配置，不是调内核参数能解决的。

3. TIME_WAIT 过多怎么办
   - 主动关闭方才会进入 TIME_WAIT。服务端大量 TIME_WAIT 说明服务端主动关连接多。
   - 手段：开启 tcp_tw_reuse（复用 TIME_WAIT 连接发新请求）、
     调整 tcp_max_tw_buckets、用长连接减少频繁短连接。
   - 注意 tcp_tw_recycle 在新内核已移除，不要用。

4. SYN Flood 攻击
   - 攻击者发大量 SYN 但不回 ACK，服务端半连接队列（SYN 队列）被占满，
     正常连接进不来。
   - 防御：SYN Cookie（不立即分配资源，用 cookie 验证）、
     调大半连接队列、限流。

四、工程排障视角（加分）
- 服务端出现大量 CLOSE_WAIT → 查应用是否漏 close，连接池是否泄漏。
- 服务端出现大量 TIME_WAIT → 看是否短连接过多，考虑长连接或 tcp_tw_reuse。
- 连接建立慢 → 看 SYN 重传、半连接队列是否满、是否有 SYN Flood。
- 连接断开异常 → 看 FIN_WAIT_2 是否堆积（对端没发 FIN）、LAST_ACK 是否卡住。

【一句话总结】
三次握手：SYN → SYN-ACK → ACK，三次是确认双方收发能力、同步 ISN、防旧连接的最小次数；
四次挥手：FIN → ACK → FIN → ACK，四次因为全双工两个方向要分别关闭，中间隔着服务端发剩余数据；
TIME_WAIT 等 2MSL 保证最后 ACK 到达和旧报文消失，CLOSE_WAIT 过多是应用没 close 的代码 bug；
排障看状态堆积定位是内核参数还是应用代码问题。
```

### 3. Async IO/epoll

```
【Async IO / epoll】

结论先行：epoll 不是异步 I/O，是 Linux 下的 I/O 多路复用（同步 I/O）；
异步 I/O（AIO/io_uring）是另一套机制，内核完成全部工作后才通知用户。
两者解决的问题不同，不能混为一谈。

一、epoll 是什么（I/O 多路复用，同步 I/O）
1. 定位：和 select/poll 同类，解决"单线程/少量线程如何高效管理大量连接"的问题。
2. 三个系统调用：
   - epoll_create：创建 epoll 实例（内核中建立红黑树 + 就绪链表）。
   - epoll_ctl：增删改要监听的 fd（插入/删除红黑树，并注册回调）。
   - epoll_wait：等待就绪事件，返回就绪 fd 列表。
3. 核心数据结构（内核中）：
   - 红黑树：存储所有被监听的 fd，增删改 O(logN)，且只需注册一次，不用每次拷贝。
   - 就绪链表：当某个 fd 有事件时，内核回调把 fd 放入链表；epoll_wait 直接读链表。
4. 为什么高效（对比 select/poll）：
   - select：每次调用都要把全量 fd 集合从用户态拷贝到内核态 + 遍历所有 fd 判断就绪，O(N)。
   - poll：解决了 fd 数量上限，但仍需遍历，O(N)。
   - epoll：fd 只注册一次，不重复拷贝；就绪判断靠内核回调，epoll_wait 只返回就绪的 fd，
     复杂度 O(就绪 fd 数)，不随监听总数线性增长[citation:6]。
5. 触发模式：
   - LT（水平触发，默认）：fd 有数据就一直通知，直到读完。
   - ET（边缘触发）：只在状态变化时通知一次，必须一次读完（配合非阻塞 fd），效率更高但编程更复杂[citation:3]。

二、epoll 为什么不是异步 I/O
- epoll 只告诉你"哪个 fd 可以读了"，真正的 read/write（数据从内核缓冲区拷贝到用户空间）
  仍然由用户线程自己执行。
- 用户线程在数据就绪后仍然要阻塞/参与读写过程，所以它是同步 I/O[citation:3][citation:9]。
- 异步 I/O 的定义：用户发起请求后立即返回，内核完成"等待数据 + 拷贝数据"全部工作，
  完成后通知用户（信号/回调），用户完全不参与读写过程。

三、真正的异步 I/O：io_uring（Linux 5.1+）
- 背景：Linux 原生 AIO（POSIX AIO）限制多——只支持直接 I/O、每次操作两个系统调用、
  性能不佳，实际用得少[citation:4]。
- io_uring 的设计：用户态和内核态共享两个环形队列（提交队列 SQ + 完成队列 CQ），
  用户把请求放入 SQ，内核处理后把结果放入 CQ，用户从 CQ 取结果。
  整个过程可以做到零系统调用（批量提交/收割），大幅降低开销[citation:4][citation:14]。
- 这才是"真异步"：用户提交后完全不用管，内核负责全部 I/O 和拷贝。
- 适用场景：高性能存储 I/O（数据库、文件服务器），而不是普通网络服务。

四、落到 RocketMQ/Redis（面试加分）
1. RocketMQ 的 Netty 通信层在 Linux 上优先用 Epoll 原生传输：
   - Netty 的 EpollEventLoopGroup / EpollSocketChannel 基于 epoll，
     比 Java NIO 默认的 select/poll 实现更高效[citation:5][citation:11]。
   - 原因：消息中间件连接多、但每个连接活跃度不一定高，epoll 的 O(就绪数) 特性正好匹配。
2. Redis 单线程高性能的核心之一就是 epoll：
   - 单线程通过 epoll 监听所有客户端 socket，只在事件就绪时处理，
     避免了多线程切换和空转[citation:6][citation:12]。
   - 但 Redis 的读写仍然是同步的，epoll 只是让它"知道该处理谁"。
3. 为什么它们不用异步 I/O：
   - 网络服务的特点是"事件驱动、处理逻辑复杂"，epoll 提供就绪通知后用户态处理更灵活；
   - 异步 I/O 更适合"纯数据搬运"场景（如文件读写），网络协议解析、业务处理仍需用户态参与。

【一句话总结】
epoll 是 I/O 多路复用（同步），核心是"注册一次 + 内核回调 + 只返回就绪 fd"，O(就绪数)；
异步 I/O（io_uring）是内核完成全部工作后通知用户，用户完全不参与读写；
RocketMQ/Redis 用 epoll 是因为它们需要"高效知道谁就绪"然后自己处理，
而不是把读写完全交给内核；
epoll ≠ 异步，这是面试最容易被抓的误区。
```



### 4. 进程调度

```
【进程调度】

结论先行：进程调度是操作系统在"进程数多于 CPU 核数"时，
决定"哪个进程、什么时候、跑多久"的机制，核心是在公平性、吞吐量、
响应时间、周转时间之间做权衡。

一、调度的目标和时机
1. 目标（互相冲突，要取舍）：
   - 公平性：每个进程都能得到 CPU；
   - 吞吐量：单位时间完成的进程数；
   - 响应时间：交互式进程从提交到首次响应的时间；
   - 周转时间：进程从提交到完成的总时间；
   - 不让进程饿死。
2. 调度时机（进程从运行态让出 CPU）：
   - 时间片用完 → 运行变就绪；
   - 阻塞（等 I/O、等锁）→ 运行变阻塞；
   - 被更高优先级进程抢占 → 运行变就绪；
   - 主动 yield 或进程结束。
3. 进程三态：就绪、运行、阻塞。调度发生在"运行→就绪/阻塞"的转换点，
   调度器从就绪队列选下一个进程上 CPU。

二、经典调度算法及取舍（高频考点）

1. FCFS（先来先服务）
   - 按到达顺序执行，非抢占。
   - 优点：简单、公平（按到达顺序）。
   - 缺点：短作业排在长作业后面要等很久（护航效应），平均周转时间差。
   - 适用：批处理，不要求响应。

2. SJF / SPN（短作业优先）
   - 选预计运行时间最短的进程。
   - 优点：平均周转时间最优（理论最优）。
   - 缺点：长作业可能饿死；运行时间难以预知。
   - 适用：批处理，能预估运行时间。

3. 时间片轮转（RR）
   - 每个进程跑一个时间片，用完排到队尾。
   - 优点：公平、响应快，适合分时/交互系统。
   - 缺点：时间片太小切换开销大，太大退化成 FCFS；平均周转时间不如 SJF。
   - 适用：分时系统、交互式场景。

4. 优先级调度
   - 按优先级选进程，可分抢占/非抢占。
   - 优点：能体现重要性（实时任务优先）。
   - 缺点：低优先级可能饿死；解决用"老化"（等待越久优先级越高）。
   - 适用：实时系统、有明确优先级的场景。

5. 多级反馈队列（MLFQ）
   - 多个优先级队列，高优先级时间片短、低优先级时间片长；
     进程用完时间片降级，等待久了升级（老化）。
   - 优点：综合平衡——短作业在高优先级快速完成，长作业逐步降级，
     交互响应好，又不饿死。
   - 缺点：参数多、实现复杂。
   - 适用：通用 OS，现代调度器的思想来源。

三、现代 Linux 的实际调度：CFS（完全公平调度）
1. 核心思想：不设固定时间片，按"虚拟运行时间（vruntime）"选进程，
   谁的 vruntime 最小谁先跑，保证每个进程获得的 CPU 时间比例公平。
2. 关键机制：
   - vruntime 随实际运行时间增长，但按权重缩放：权重高的进程（nice 值小）
     vruntime 增长慢，获得更多 CPU。
   - 用红黑树按 vruntime 排序，选最左节点（vruntime 最小）运行，O(logN)。
   - 新进程/唤醒进程的 vruntime 做补偿，避免刚唤醒就抢占或长期得不到 CPU。
3. 实时进程：用 SCHED_FIFO / SCHED_RR，优先级高于普通进程。
4. 注意：Linux 内核不区分进程和线程，统一用 task_struct 调度，
   所以 CFS 调度的"单位"是线程（内核级线程）。

四、落到进程/线程/协程语境（呼应前面的问题）
- 操作系统调度的基本单位是线程（内核级线程），不是进程；
  进程是资源分配单位，线程共享进程资源但独立被调度。
- 协程是用户态调度，不经过内核调度器，由运行时（Go GMP、Java 虚拟线程）管理，
  所以协程切换不触发进程调度。
- 秒杀高并发下，Tomcat 线程池的线程由 OS 调度，线程多了 CFS 的切换开销上升；
  换协程后调度在用户态完成，减少内核调度压力。

【一句话总结】
进程调度在公平性/吞吐/响应/周转间取舍，发生在运行→就绪/阻塞的转换点；
FCFS 简单但短作业吃亏，SJF 周转最优但饿死长作业，RR 公平响应快，
优先级可能饿死用老化解决，MLFQ 综合平衡；
Linux 用 CFS，按 vruntime 红黑树选最小，权重由 nice 决定，保证公平不饿死；
OS 实际调度单位是线程，协程在用户态调度不经过内核。
```
