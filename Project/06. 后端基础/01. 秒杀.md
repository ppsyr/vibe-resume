### 1. 秒杀怎么防止不超卖；秒杀的难点和解决方案；怎么保证秒杀场景下的数据一致性

```
【问题1：秒杀怎么防止不超卖】

结论先行：单机靠锁，集群靠"Redis 原子校验 + 数据库乐观锁兜底"，两层防护。

第一层：Redis 预扣库存（挡掉绝大部分并发）
- 秒杀开始前把库存预热到 Redis。
- 用 Lua 脚本把"判断库存 > 0"和"扣减库存"合并成一个原子操作，
  Redis 单线程执行 Lua，天然不会出现读-改-写的竞态。
- 脚本里同时校验"一人一单"（用 Set 记录已下单用户），校验+扣减+记录一步完成。
- 只有 Lua 返回成功的请求，才允许进入后续下单流程，其余直接返回"已售罄/重复下单"。

第二层：数据库乐观锁兜底（防止 Redis 与 DB 不一致导致超卖）
- 落库时执行：
  update seckill_voucher set stock = stock - 1
  where voucher_id = ? and stock > 0;
- 用 stock > 0 作为 CAS 条件，影响行数为 0 说明库存已空，回滚/标记失败。
- 这一层是最后防线，即使 Redis 数据异常也不会把库存扣成负数。

补充：为什么不用悲观锁/分布式锁扣库存？
- 悲观锁（select for update）串行化，吞吐量太低，秒杀扛不住。
- 分布式锁（Redisson）也能做，但每个请求都要加锁解锁，性能不如 Lua 原子脚本；
  分布式锁更适合"一人一单"这种需要跨请求互斥的场景，库存扣减用 Lua 更轻量。

---

【问题2：秒杀的难点和解决方案】

我按四个维度来讲：流量、库存、幂等、可用性。

难点1：瞬时高并发打垮系统
- 方案：层层削峰。
  a) 前端：按钮置灰、验证码/答题、限流。
  b) 网关/Nginx：限流（令牌桶）、黑白名单。
  c) 服务层：Redis + Lua 做资格校验，把无效请求挡在 DB 之前。
  d) 异步化：校验通过后写入消息队列（Redis Stream / RabbitMQ），立即返回，
     后台消费者慢慢落库，把同步写 DB 变成异步削峰。

难点2：超卖（库存一致性）
- 方案：如上，Redis Lua 原子预扣 + 数据库 stock > 0 乐观锁兜底。

难点3：一人一单（重复下单/幂等）
- 方案：
  a) Redis Set 记录 userId，Lua 里判断是否已存在，存在直接拒绝。
  b) 数据库唯一索引（user_id + voucher_id）做最终兜底，重复插入抛异常捕获即可。
  c) 消息消费端做幂等：以订单号/用户券 ID 为唯一键，消费前查重或依赖唯一索引。

难点4：系统可用性与最终一致
- 方案：
  a) Redis 集群/哨兵保证高可用，库存热点可考虑分片。
  b) MQ 可靠投递：生产者确认 + 消费者手动 ACK + 失败重试 + 死信队列。
  c) 定时对账：比对 Redis 库存、DB 库存、订单表，发现不一致告警并补偿。
  d) 降级熔断：DB 压力过大时快速失败，保护核心链路。

一句话总结：秒杀的本质是"把并发挡在 Redis 层、把写操作异步化、用唯一约束和乐观锁兜底一致性"。

---

【问题3：怎么保证秒杀场景下的数据一致性】

先定性：秒杀追求的是"最终一致性"，不是强一致。
因为强一致（分布式事务）会带来巨大性能损耗，秒杀扛不住；
业务上允许"用户看到下单成功、订单稍后落库"这种短暂窗口。

不一致会出现在三个环节，逐个解决：

环节1：Redis 扣库存 vs 数据库落库
- Redis Lua 保证"校验+扣减+记录用户"原子执行，不会出现半扣。
- 数据库用 stock > 0 乐观锁 + 唯一索引兜底，即使 MQ 重复投递也不会超卖/重复单。
- 若 DB 扣减失败（影响行数 0），消费端捕获后回滚 Redis 库存（补偿）或标记订单失败。

环节2：消息队列的可靠投递
- 生产端：Lua 校验成功后发消息，用 MQ 的 confirm 机制确保消息到达 Broker；
  若发送失败，回滚 Redis 预扣（或记录本地消息表定时重发）。
- Broker：持久化 + 副本，防止宕机丢消息。
- 消费端：手动 ACK，处理成功才确认；失败进重试队列，多次失败进死信队列人工/定时补偿。

环节3：消费幂等
- 以"用户券唯一 ID / 订单号"作为幂等键。
- 消费前查订单是否已存在，或直接依赖数据库唯一索引，重复消费抛 DuplicateKey 捕获忽略。
- 保证"至少一次投递 + 幂等消费" = 效果上恰好一次。

最终兜底：定时对账
- 定时任务比对 Redis 库存、DB 库存、订单数量三者是否吻合。
- 发现差异：以 DB 为准修正 Redis，或对缺失订单补单/退款，并告警。
- 这一步是"最终一致性"的保险丝，面试时一定要提，体现你有闭环思维。

一句话总结：
Lua 原子性解决"扣减不半途"，乐观锁+唯一索引解决"落库不超卖不重复"，
MQ 可靠投递+幂等消费解决"消息不丢不重"，定时对账解决"最终兜底"。
```

### 2. 为什么不能直接用 MySQL？访问量小的数据是不是可以直接打到数据库？

```
【问题1：为什么不能直接用 MySQL 扛秒杀】

结论：不是 MySQL 不能用，是秒杀这种"瞬时高并发 + 热点行更新"的场景，
会精准踩中 MySQL 的几个物理瓶颈，导致吞吐骤降甚至雪崩。

具体瓶颈：

1. 连接数瓶颈
   - MySQL 单机连接数有限（几百到几千），秒杀瞬间几万请求，
     连接池瞬间打满，后续请求排队或直接拒绝。

2. 行锁竞争（最致命）
   - 秒杀扣库存本质是 update 同一行（同一个 voucher_id），
     InnoDB 行锁会让所有请求串行排队。
   - 高并发下大量请求等锁，出现锁等待超时（innodb_lock_wait_timeout），
     失败率飙升，用户体验极差。
   - 即使 stock > 0 乐观锁，也只是把"锁等待"变成"大量 update 影响行数为 0"，
     DB 依然要承受全量请求的 IO 和事务开销。

3. 事务与磁盘 IO 开销
   - 每次扣减都是事务：写 undo/redo log、刷盘、提交，
     单机 TPS 有限（普通配置几千级），秒杀峰值远超这个量级。

4. 热点行与页竞争
   - 同一行被高频更新，buffer pool 中该页反复加锁释放，
     还容易产生死锁重试，进一步放大开销。

所以秒杀用 Redis 的本质：
把"热点行并发扣减"从磁盘型数据库前移到内存型 Redis，
用 Lua 单线程原子执行把锁竞争消灭在内存里，
DB 只承接异步落库的"削峰后"流量。

---

【问题2：访问量小的数据是不是可以直接打到数据库】

结论：可以，而且很多场景就应该直接打 DB，不要为了用缓存而用缓存。

判断标准（满足以下再考虑缓存）：
1. 读多写少，且读 QPS 确实超过 DB 舒适区（一般单机几千 QPS 以上才值得考虑）。
2. 热点集中，缓存命中率高（命中率低反而放大 DB 压力）。
3. 能容忍短暂不一致（缓存与 DB 有同步窗口）。
4. 数据变更不频繁，缓存维护成本可控。

反例（不该缓存 / 直接打 DB 更好）：
- 低频访问数据：缓存命中率低，还多一层维护和一致性成本。
- 强一致要求数据：如账户余额、支付状态，缓存反而引入不一致风险。
- 数据量小、查询简单：DB 走索引毫秒级返回，加缓存是过度设计。
- 写多读少：缓存频繁失效，收益为负。

一句话：缓存是"用一致性换性能和 DB 保护"，
低流量场景直接打 DB 更简单、更可靠，符合 KISS 原则。
面试时点出"按量级选型、避免过度设计"，比无脑说"必须加缓存"更加分。
```

### 3. 抢购秒杀券的整条链路经过哪些过程？

```
【秒杀券抢购全链路】

我按请求流转顺序讲，一共七个阶段。

阶段1：前端层（防重 + 削峰第一道）
- 按钮置灰/倒计时，防止用户连点重复提交。
- 可选：验证码/答题，拉长请求间隔，过滤机器脚本。
- 静态资源 CDN，减少对后端压力。

阶段2：网关/Nginx 层（限流第二道）
- 令牌桶/漏桶限流，超过阈值的请求直接快速失败（429）。
- 黑白名单、IP 限流，挡掉恶意刷单。
- 目的：把洪峰削到服务层能承受的量级。

阶段3：服务层入口（登录校验 + 前置拦截）
- 拦截器校验登录态（从 Redis 取 Token 对应用户）。
- 校验活动时间（是否开始/结束）、活动状态。
- 这些无效请求在这一层就返回，不进核心逻辑。

阶段4：Redis + Lua 原子校验与预扣（核心，挡掉绝大部分并发）
- 一次 Lua 脚本内原子完成三件事：
  a) 判断库存是否 > 0（不够直接返回售罄）；
  b) 判断该 userId 是否已下单（Set 去重，一人一单）；
  c) 库存 -1，并把 userId 写入已下单集合。
- 为什么用 Lua：Redis 单线程执行脚本，"判断+扣减+记录"不会被打断，
  彻底消除读-改-写竞态，是防超卖的第一层。
- 校验不通过：直接返回"售罄/重复下单"，请求到此终止，不打 DB。
- 校验通过：进入下一阶段。

阶段5：发送消息队列 + 立即返回（同步转异步，性能拐点）
- 把"用户ID、券ID、订单号"封装成消息，投递到 MQ（Redis Stream / RabbitMQ）。
- 生产端用 confirm 机制确保消息到达 Broker；发送失败则回滚 Redis 预扣或走本地消息表重试。
- 投递成功后立即给用户返回"抢购成功，订单处理中"，不等待 DB 落库。
- 这一步把同步写库变成异步削峰，是吞吐量提升的关键。

阶段6：消费端异步落库（最终一致）
- 消费者从 MQ 拉消息，执行数据库下单：
  a) 乐观锁扣库存：update ... set stock = stock - 1 where id = ? and stock > 0；
  b) 插入订单记录，依赖唯一索引（user_id + voucher_id）防重复；
  c) 影响行数为 0 或唯一键冲突 → 捕获异常，标记失败并回滚 Redis 库存（补偿）。
- 手动 ACK，成功才确认；失败重试，多次失败进死信队列。
- 消费幂等：以订单号/用户券ID 为幂等键，重复消费直接忽略。

阶段7：兜底与监控
- 定时对账：比对 Redis 库存、DB 库存、订单表，发现不一致告警并补偿（以 DB 为准修 Redis 或补单/退款）。
- 监控：库存余量、MQ 积压、消费失败率、DB 慢查询，异常及时降级。

【一句话串起来】
前端防重 → 网关限流 → 登录/活动校验 → Redis+Lua 原子预扣（防超卖+一人一单）
→ MQ 异步投递并立即返回 → 消费端乐观锁+唯一索引落库 → 对账兜底。
流量逐层递减，DB 只承接削峰后的成功订单量，一致性问题由 Lua 原子性、
MQ 可靠投递、消费幂等、定时对账四道保障闭环。
```

### 4. 登录怎么实现；如何获取用户登录信息

```
【问题1：登录怎么实现】

结论：不用传统 Session，用"随机 Token + Redis 集中存储"实现分布式登录态。

1. 为什么放弃 Session
   - Tomcat 集群下 Session 不共享，用户请求落到不同机器登录态就丢了。
   - 解决方式：把登录态从"单机内存"搬到"分布式缓存 Redis"，多机共享。

2. 登录流程
   a) 用户提交手机号 + 验证码（或密码）。
   b) 服务端校验验证码/密码通过后，生成一个随机 Token（UUID，保证不可猜测）。
   c) 把用户信息写入 Redis：
      Key   = 登录 Token（随机串）
      Value = Hash 结构，存 id、nickName、icon 等字段
      TTL   = 30 分钟（可配）
   d) 把 Token 返回给前端，前端存起来（如 localStorage），后续请求带上。

3. 为什么 Value 用 Hash 而不是 String+JSON
   - Hash 可以单独读写某个字段（如只取昵称），不用像 String+JSON 那样全量序列化/反序列化。
   - 更新单个字段时 Hash 只改一个 field，节省空间和带宽，操作更灵活。

4. TTL 与续期
   - 设置过期时间防止 Token 永久有效带来安全风险。
   - 每次请求校验通过后，刷新 TTL（滑动过期），用户活跃期间不掉线；
     长期不活跃自然过期，符合安全预期。

【问题2：如何获取用户登录信息】

结论：请求携带 Token → 拦截器校验并查 Redis → 用户信息放 ThreadLocal → 业务层直接取。

1. 请求携带 Token
   - 前端每次请求在 Header（如 authorization）里带上 Token。

2. 拦截器两层设计（关键）
   - 第一层拦截器（所有请求）：从 Header 取 Token，查 Redis 拿用户 Hash，
     查到了就刷新 TTL，并把用户信息存入 ThreadLocal。
   - 第二层拦截器（需登录的接口）：判断 ThreadLocal 里是否有用户，
     没有则返回 401 拦截；有则放行。
   - 分层好处：通用逻辑（取 Token、刷新 TTL）和鉴权逻辑解耦，配置灵活。

3. ThreadLocal 存取
   - 用 ThreadLocal 存当前请求的用户信息，同一个请求线程内任何业务代码
     都能直接 UserHolder.getUser() 取到，避免层层传参。
   - 本质是用线程隔离换传递便利。

4. 请求结束必须清理（防内存泄漏 + 防串号）
   - 在拦截器的 afterCompletion 里调用 ThreadLocal.remove()。
   - 原因：Tomcat 线程池复用线程，不清理会导致下一个请求读到上一个用户的
     信息（数据串号），同时 ThreadLocal 强引用不释放会内存泄漏。

【一句话总结】
登录：校验通过发随机 Token，用户信息以 Hash 存 Redis 并设 TTL，前端持有 Token；
获取信息：请求带 Token → 拦截器查 Redis 刷新 TTL → 存入 ThreadLocal → 业务直接取
→ 请求结束 remove 清理。整套设计把登录态从单机 Session 搬到 Redis，天然适配集群。
```

### 5. Redis+Lua 为什么是原子的；Redis 本身就单线程，为什么要 lua

```
【问题1：Redis + Lua 为什么是原子的】

原子性来自两层保证：

1. Redis 命令执行是单线程的
   - 所有客户端命令在一个线程里串行执行，任意时刻只有一个命令在跑，
     所以单条命令天然原子，不会被打断。

2. Lua 脚本被当作"一个整体命令"执行
   - 客户端把整个脚本发给 Redis，Redis 把脚本作为一个命令单元调度，
     脚本执行期间不会插入其他客户端的任何命令。
   - 脚本内部的多个 redis.call 连续执行，对外表现为一个不可分割的整体。
   - 所以"判断库存 + 扣减 + 记录用户"三步在脚本里是连续完成的，中间不会被别的请求插队。

需要说清的一个边界（加分点）：
- 这里的"原子"指"不被中断地连续执行"，不等于关系型数据库的"事务回滚"。
- Lua 脚本如果执行到一半报错，前面已执行的写命令不会回滚。
- 所以脚本要保证逻辑正确、参数校验前置，避免中途异常。

【问题2：Redis 本身单线程，为什么还要 Lua】

核心一句话：单线程只保证"单条命令"原子，保证不了"多条命令组合"原子。

1. 多命令组合的竞态问题
   - 秒杀要"查库存 → 判断 > 0 → 扣减 → 记录用户已下单"，这是多条命令。
   - 不用 Lua 时，命令逐条发送，两条命令之间可能插入其他客户端请求：
     两个请求都读到库存=1，都判断通过，都去扣减 → 超卖。
   - 单线程解决不了这个问题，因为单线程保证的是"每条命令不被打断"，
     不是"你这一组命令连续执行"。

2. Lua 把多命令打包成一个原子单元
   - 脚本内所有操作连续执行，中间不插入其他请求，组合操作具备原子性。
   - 这正是秒杀"校验 + 扣减 + 去重"需要的语义。

3. 额外收益：减少网络往返（RTT）
   - 不用 Lua 要发多条命令、多次 RTT；用 Lua 一次发送、一次返回，
     高并发下显著降低网络开销和延迟。

4. 可复用
   - 脚本可用 EVALSHA 缓存，后续只传 SHA1 摘要，减少传输体积。

补充（防反问）：
- Redis 6.0 之后是"网络 IO 多线程 + 命令执行单线程"，
  命令执行仍然是单线程，所以上述原子性结论不变。
- 注意 Lua 脚本要短小，避免长脚本阻塞整个 Redis（单线程下会卡住所有请求）。
```

### 6. Redis 是什么，为什么使用 Redis？Lua 的原理是怎样的？

```
【问题1：Redis 是什么】

Redis 是一个开源的、基于键值对的 NoSQL 内存数据结构存储系统。
它的全称是 REmote Dictionary Server。

核心特征：
- 数据主要放在内存中，读写速度极快；
- 值不只是字符串，还支持 Hash、List、Set、SortedSet、BitMap、GEO 等数据结构；
- 常被用作缓存、会话存储、排行榜、消息队列等场景；
- 支持持久化（RDB/AOF），重启后数据可以恢复，不是纯易失的。

一句话定位：它是以内存换速度、以丰富数据结构适配业务场景的“高性能数据中间件”。

---

【问题2：为什么使用 Redis】

我从两个维度讲：性能和数据结构。

1. 性能：内存操作带来的数量级优势
   - Redis 数据在内存中，命令执行路径短，读写可达 10 万 QPS 级别[citation:2]。
   - 对比 MySQL：一次 Redis GET 可能 0.1ms，而磁盘数据库走索引可能 5ms 以上[citation:2]。
   - 在高并发场景（秒杀、热点查询）下，Redis 能把请求挡在数据库之前，避免连接池打满和行锁竞争。

2. 数据结构：精准匹配业务形态
   - Hash 存对象属性，可以单独读写某个字段，不用全量序列化；
   - SortedSet 做排行榜，score 存时间戳，天然按序范围查询；
   - BitMap 做签到，极大节省内存；
   - Lua 脚本把多步操作打包原子执行。
   这些是普通 KV 缓存不具备的，Redis 的价值在于“用对的结构做对的事”。

3. 补充：单线程命令执行
   - 命令执行单线程，避免多线程锁竞争，也让单条命令天然具备原子性[citation:9]。
   - 配合 Lua，可以把多命令组合成原子单元，这是秒杀扣库存的基础。

在项目里用 Redis，本质是：热点数据前置到内存挡并发，用数据结构替代笨重的 SQL 逻辑，用原子命令解决并发竞态。

【问题3：Lua 的原理是怎样的】

核心机制：Redis 内置 Lua 解释器，脚本被当作一个整体命令执行。

1. 执行入口
   - 客户端通过 EVAL 命令把 Lua 脚本发给 Redis。
   - Redis 内部用嵌入的 Lua 5.1 解释器解析执行脚本。
   - 脚本里通过 redis.call() 调用 Redis 命令，访问 KEYS 和 ARGV 传入的键与参数。

2. 为什么具备原子性
   - Redis 命令执行是单线程的，EVAL 脚本在执行期间被视为一个命令单元。
   - 脚本内部的所有 redis.call 连续执行，中间不会插入其他客户端的命令[citation:4]。
   - 所以“判断库存 → 扣减 → 记录用户”在脚本里是一气呵成的，不会被其他请求插队。

3. 必须说清的边界（加分点）
   - 这里的“原子”是并发编程语义的“不可中断”，不是数据库 ACID 的“出错回滚”。
   - 如果脚本中途报错，前面已执行的写命令不会撤销[citation:4]。
   - 所以脚本逻辑要保证正确，参数校验前置，避免依赖回滚。

4. 额外优化：EVALSHA
   - 脚本可以先加载到 Redis 缓存，后续只传 SHA1 摘要执行，减少网络传输。
   - Spring Data Redis 默认就是先 EVALSHA 再回退 EVAL[citation:14]。

一句话：Lua 的原理不是 Redis 额外做了什么复杂事务，而是利用“单线程 + 脚本整体调度”把多条命令的连续执行权锁定给一个客户端，从而在多命令组合层面获得原子性。
```

### 7. 秒杀校验的具体逻辑？

```
【秒杀校验的具体逻辑】

我按"前置准备 → 脚本内校验 → 结果处理 → 兜底"四部分讲。

一、前置准备：库存和用户集合预热到 Redis
- 秒杀开始前，把库存写入 String：key = seckill:stock:{voucherId}，value = 剩余库存。
- 已下单用户用 Set：key = seckill:order:{voucherId}，member = userId。
  选 Set 是因为 SISMEMBER 判断 O(1)，且天然去重，一人一单判断最合适。
- 库存用 String 是因为 DECR/INCRBY 原子且轻量，配合 Lua 足够。

二、Lua 脚本内校验（核心，原子执行）
脚本接收 KEYS[1]=库存key、KEYS[2]=用户集合key、ARGV[1]=userId，按顺序做三步：

第1步：库存校验
- 读取库存值，如果 <= 0，直接 return 1（库存不足）。
- 放在最前，因为最便宜、能挡掉绝大多数无效请求。

第2步：一人一单校验
- 用 SISMEMBER 判断 userId 是否已在已下单集合。
- 如果已存在，return 2（重复下单），请求终止。
- 放在扣减之前，避免给重复用户扣库存。

第3步：资格锁定（扣减 + 记录）
- 前两步都通过，说明有资格：
  a) INCRBY 库存 -1（扣减）；
  b) SADD 把 userId 加入已下单集合。
- 两步和前面的判断在同一个脚本内连续执行，Redis 单线程保证脚本整体不被其他请求插入，
  所以"判断 + 扣减 + 记录"不会出现读-改-写竞态，这是防超卖和防重复的第一道闸门。
- 完成 return 0（校验成功）。

三、Java 侧根据返回值处理
- 返回 1：直接给前端"库存不足"。
- 返回 2：直接给前端"不能重复下单"。
- 返回 0：校验通过 → 生成订单号 → 把下单信息投递到 MQ（或阻塞队列）
  → 立即返回"抢购成功，处理中"，不等待 DB 落库。
- 只有返回 0 的请求才进入异步落库，DB 只承接削峰后的成功订单量。

四、兜底（第二道闸门）
- Redis 校验只是第一层，DB 落库时还有：
  a) 乐观锁：update ... set stock = stock - 1 where id = ? and stock > 0；
  b) 唯一索引 (user_id, voucher_id) 防重复插入。
- 即使 Redis 数据异常或 MQ 重复投递，DB 层也不会超卖/重复单。
- 消费失败或扣减影响行数为 0 时，回滚 Redis 预扣库存（补偿）。

【一句话总结】
校验 = 秒杀前预热库存和用户 Set → Lua 内按"库存 → 一人一单 → 扣减记录"三步原子执行
→ 返回码驱动 Java 侧失败返回或异步下单 → DB 乐观锁 + 唯一索引兜底。
核心是：判断和扣减必须在一个原子单元里，不能拆到 Java 代码里分步做。
```
