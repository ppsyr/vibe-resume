### 1. 压缩以后到底有什么影响

1. **为什么要压缩（动机层）**：LLM 上下文窗口有限，长任务（多轮 ReAct + 工具调用）必然膨胀。不压 → 超窗报错或模型"中间遗忘"（lost in the middle）；压太狠 → 关键信息丢失、任务跑偏。所以压缩本质是**在"窗口容量"和"信息保真"之间做取舍**。
2. **压缩带来哪些影响（机制层）**：业界的压缩手段大致几类——
    - **截断**（硬截 N 行/字符）：简单但不可逆，丢了就没了；
    - **外化/落盘**（超长内容搬到文件，消息留 preview + path）：可回读，信息不丢，但多一次工具调用；
    - **摘要**（LLM 把旧消息压成一段）：省 token 但**不可逆**，摘要质量决定信息保真度；
    - **结构化裁剪**（按 turn/角色/工具类型选择性保留）。  
		每种手段的影响不同：截断伤召回、摘要伤细节、外化伤延迟。
3. **怎么衡量影响（评测层）**：压缩效果不能只说"感觉省了"，要能落到指标——**token 节省率、关键事实保留率、任务成功率/轮次、压缩触发频率、摘要后模型是否还要回读**。面经里"关键事实保留率是负向的怎么处理"就是在追这一层。

```
"压缩的影响我分两头看：**为什么压**和**压完怎么样**。

为什么压——长任务多轮 ReAct + 工具调用，上下文必然膨胀，不压会超窗或者模型中间遗忘。但压缩本质是拿'窗口容量'换'信息保真'，压太狠会丢关键信息、任务跑偏，所以我的策略不是一刀切截断，而是**按 token 占用分阶段、用不同手段**。
```

### 2. 压缩内容是哪些，把什么送去压缩，结构化摘要指的是什么？

压缩发生在 **`state.messages`** 上（LangGraph 的 checkpoint 状态），不是发生在 `request.messages`（那是渲染层临时改的，request-scoped 不持久）。你的 P4 产出 `messages_patch=[RemoveAll, summary_msg, *preserved]`，**这个 patch 写回的是 `state.messages`**，下一轮 checkpoint 里就是压缩后的消息。而 ①② 两步的 `request.override` 只影响"本次送 LLM 的渲染结果"，**不回写 state**——这是你要主动讲清的边界。

```
我先区分一个边界：我的压缩发生在 **`state.messages`** 上，也就是 LangGraph checkpoint 里的对话历史，**不是** system prompt、工具 schema 或 governance 状态；渲染层对 request 的改写是**请求级、临时的**，只影响本次送 LLM，**不回写 state**。

**压的是哪些**：两类。一类是**旧轮次消息**，走 P4 摘要；一类是**超长工具返回**，走 P1 外化和工具返回时的即时外化——外化就是**把正文换成预览、原文落盘、打上"已外化 + 路径"标记**，配一个读取快照的工具可以回读。SystemMessage、工具 schema、治理元数据都不压。

**送什么去压**：P4 时按"**待摘要段 + 保留段**"切分，**保留最近 6 轮**；切分点会**前移到工具调用与结果配对完整的位置**，防止把"带工具调用的 AI 消息"和"工具返回消息"拆开；保留段里**没有配对的工具返回**移到待摘要段，待摘要段里**孤立的工具返回**先外化、把路径写进摘要。所以送去摘要的是"**旧轮次 + 配对完整 + 孤立工具结果已外化**"的一段历史，拼成"**每条消息取类型 + 内容前 500 字**"交给摘要模型。

**结构化摘要指什么**：我的摘要模板要求摘要模型按"**每轮：用户意图 + 执行结果 + 执行依据**"输出，这是**提示词层面的结构化**，比自由摘要更可读、更不容易漏掉执行结果和依据。但我要说清楚：**代码里拿到的是模型返回的字符串，没有做 JSON schema 强校验**，所以它是"**模板约束的结构化**"，不是"代码强校验的结构化对象"——这是当前的一个边界。
```

#### 2.2. 结构化摘要有没有逐字段校验

1. **代码层面没有 JSON schema 校验**：摘要模板要求"每轮：意图 + 结果 + 依据"，但拿到的是 LLM 返回的**自由字符串**，直接作为 `summary_msg` 拼进 `messages_patch`，**没有解析、没有逐字段检查、没有缺字段回退**。
2. **没有"摘要质量门"**：如果 LLM 漏了"执行依据"或把某轮压成一句话，**系统不会发现**，直接进下一轮上下文。
3. **唯一的间接保护是 `_snap_to_pairing` 和孤立工具外化**——但那保的是**配对结构**，不是**摘要字段完整性**。
4. **你评测里 L1 能过，是"标准答案全字段比对"过的，但那是判产物，不是判摘要**——摘要本身有没有三段，你没验。

#### 2.3. preserved 最近 6 轮，跨轮约束怎么保

1. **"LLM 识别 + LLM 抽取"**，不是规则钉住。LLM 漏识别一条约束，它就不在栏目里——**没有硬保证，只有概率提升**。
2. **栏目本身也要进上下文**，如果约束越积越多，它会成为新的膨胀源，**需要自己的淘汰/优先级策略**（比如按重要性/时间排序、超限时保留高优先级）。
3. **"未完成 todo"有生命周期**——完成后要从栏目移除，否则会误导模型。这个状态同步机制你要能说清。

- **真实状态**
```
"这块我做过一次改进。原来我的保留段判据是**最近 6 轮**，纯按时间新近度，跨轮约束如果不在最近 6 轮里，就会进待摘要段，能不能活下来取决于摘要模型有没有恰好写进'依据'栏——**而逐轮摘要的 schema 是'意图/结果/依据'，跨轮约束天然没有归宿**。

所以我加了一个**独立的'约束/禁止项/未完成 todo'栏目**：由模型做意图识别，把用户明确说的禁止项、硬约束、未完成待办抽出来，**放在单独栏目里，不塞进逐轮结构化摘要**。这样跨轮约束有了**专属归宿**，不再依赖它是否恰好被写进某一轮的'依据'。这个栏目会随摘要一起注入后续上下文，模型每轮都能看到当前生效的约束清单。

但我要说清楚**三个边界**：**第一，这仍是模型识别 + 模型抽取，不是规则钉住**——模型漏识别一条约束，它就不在栏目里，所以是'概率提升'不是'硬保证'；**第二，栏目本身也占上下文**，约束越积越多会变成新的膨胀源，我需要对它做优先级和淘汰，比如按重要性、时间排序，超限时保留高优先级；**第三，未完成 todo 有生命周期**，完成后要从栏目移除，否则会误导模型，这个状态同步要单独处理。

下一步我会补的是：**压缩前后对'约束栏目'做召回率对比**——压缩前抽一组约束做基准，压缩后看栏目里还在不在，让'约束保留'从'靠模型识别'变成'可度量'；以及**对栏目做容量上限 + 优先级淘汰**，防止它自己膨胀。"
```
#### 2.4. P1 外化后模型怎么知道去读

**"外化留了 preview + 路径标记，模型能看到去哪读；但会不会主动读，靠提示词引导 + 模型判断，不是系统强制；评测里是有明确读回指引下的结果，不能证明无指引也主动恢复。"**

1. **外化后消息里留了标记和路径**（`POIROT_EXTERNALIZED / PATH / META`，content 是 preview），所以模型**能看到"这里被外化了、原文在哪个路径"**——这是它"知道去哪读"的基础。
2. **但"知道路径"不等于"会主动去读"**。你的评测文档自己写了：中任务是**"有明确读回指引"**的结果（提示词明确指导用不超过 400 字符的尾部切片），**不能证明没有指引也一定主动恢复**。这是最关键的诚实边界。
3. **没有"缺细节自动触发回读"的机制**——回读靠模型自己判断"preview 不够、需要读全文"，或者靠提示词引导，**不是系统强制**。

```
"分两层说：**模型怎么知道去哪读**，和**模型会不会主动去读**。

**怎么知道去哪读**：外化的时候不是把内容删了，是**把正文换成预览、原文落盘、在消息上打'已外化 + 路径'标记**。所以模型在上下文里能看到'这条工具结果被外化了、原文在哪个路径、预览是什么'，它**知道去哪读**，配一个读取工具就能取回原文。
```

```
**但我有中任务的证据**：中任务上**token 使用确实减少了**；更重要的是，**有了 40% 外化阶段之后，进入 80% 摘要的频次明显更少**。这个观察恰好说明分阶段的价值——**40% 和 80% 不是同一件事调两档，而是两种性质不同的动作**：40% 外化是**可逆的机械开销剥离**，把超长工具结果搬到磁盘、留预览和路径，它提前把上下文占用降下来，于是**很多任务在 80% 之前就被 40% 阶段化解了，根本不需要触发不可逆的摘要**。如果没有 40% 这一档，这些任务会直接冲到 80%，被迫做有损摘要。所以 40% 的存在，本质是**用可逆操作给不可逆操作减负**。

90% 收尾则是第三种性质——它不是压缩，是**防超窗的熔断**，剥工具调用、插收尾提示、强制模型收敛。三档对应的是‘可逆剥离 / 不可逆压缩 / 安全熔断’三种不同动作，不是同一个动作的三个阈值。

阈值具体是 40/80/90 还是别的值，我**没有实验依据，是经验值**，可被配置覆盖。如果要做完整消融，我会设计三组：只做外化、只做摘要、三档全开，在同样长任务上比完成率、token 占用、进入摘要的频次和关键事实保留率；另外单独构造能触发 90% 的 case，验证收尾这一档。当前我能说的是：**中任务上 token 减少、进入 80% 的频次降低，这支持分阶段有实际收益；但完整的消融和 P5 验证还没做。**”
```

#### 3.4. 你的外化和 CC 的“文件只回路径”本质是不是一样

1. **触发时机不同**：CC 是**读文件时**就决定“超 5000 token 只回路径不回内容”，属于**输入侧裁剪**；你是**工具结果返回后**判断“超阈值就外化”，属于**输出侧处理**。这是本质差异之一。
2. **但“留路径”这个结果形态确实相似**——都是“上下文里只留索引，原文在磁盘”。所以你不能说“完全不一样”，要承认**结果形态相似，但机制、时机、可控性不同**。
3. **CC 有自动重注入兜底**，你没有（3.2 已承认）；**CC 的路径是“文件系统路径”，你的路径是“外化文件路径 + 预览”**，你的预览比 CC 的纯路径多给了模型一点上下文。
4. **你的外化是“可配置阈值 + 工具元数据调整”**（`_get_threshold` 按工具典型 token 调），CC 是固定 5000 token 规则。你的粒度可能更细，但你没有 CC 的“自动重注入”。

所以这题的正确答法是：**承认“结果形态相似（都留路径）”，但说清“触发时机（输入侧 vs 输出侧）、触发判据（固定规则 vs 可配置+工具元数据）、有没有自动兜底（CC 有重注入、你没有）、预览粒度（CC 纯路径 vs 你 preview+path）”四个差异**，最后落到“相似的是形态，不同的是机制和保真闭环”。

```
“结果形态上确实像——都是上下文里只留索引、原文放磁盘。但**本质不完全一样，差在四个地方**。

**第一，触发时机不同。** CC 是**读文件的时候**就判断‘这个文件超过 5000 token，只回路径不回内容’，属于**输入侧裁剪**——内容还没进上下文就被挡掉了。我是**工具结果返回之后**判断‘这条结果超阈值就外化’，属于**输出侧处理**——内容先进了上下文，再被搬到磁盘。一个是‘不让它进来’，一个是‘进来后再搬走’。

**第二，触发判据不同。** CC 是**固定 5000 token 规则**。我是**可配置阈值加工具元数据调整**——按工具的典型 token 量动态算阈值，不同工具阈值可以不同。粒度上我更细，但这也意味着我依赖配置，CC 的规则更简单直接。

**第三，保真闭环不同。** CC 外化之后有**自动重注入**兜底——压缩后自动把最近读改的文件、规则、skill 重新加载回来，不依赖模型判断。我**没有自动重注入**，回读靠模型按需触发加提示词引导。这是我和 CC 最大的差距，不是形态差距，是**兜底机制差距**。

**第四，预览粒度不同。** CC 超限文件基本只回路径。我是**留预览加路径**，模型在上下文里能看到一段 preview，知道这条结果大概是什么，再决定要不要读全文。这算我的一个微小优势，但也意味着 preview 本身占一点 token。

所以准确说：**形态相似，机制不同**——CC 是输入侧固定规则裁剪加自动重注入，我是输出侧可配置外化加引导回读。我的下一步是把‘每次都需要的内容’改成自动重注入，补上 CC 那层兜底，那时候才更接近 CC 的保真闭环。”
```

#### 3.5. 你说模板约束比自由摘要好，有没有对比过模板摘要 vs 自由摘要的效果？

```
“**没有直接做过‘模板摘要 vs 自由摘要’的对照**——我的对照是‘开治理 vs 关治理’，不是两种摘要方式的对比。这是我要承认的。

但为什么选模板而不是自由摘要，我有设计上的理由。**自由摘要的问题有三个**：第一，LLM 自由摘要时有压缩偏好，它倾向于保留结论、丢掉过程，会把‘用户要求 A，但强调不能动 B’压成‘用户要求 A’；第二，自由摘要的输出是一段散文，**不可审计**，你没法问‘这轮的执行依据保留了吗’，因为没有‘依据’这个独立单元；第三，业界共识是自由摘要容易‘越压越短’，信息坍塌。**模板摘要针对这三点**：用‘意图/结果/依据’固定字段给信息锚点，让‘依据’不能并进‘结果’；每个字段可定位、可检查；固定字段相当于最小信息量约束，抵抗坍塌。另外我把跨轮约束单独放一个栏目，也是因为自由摘要里约束没有专属归宿。

但采用模板是要付出成本的：它**强制固定结构，某些轮次不适合三段式时可能失真**；而且**模板只约束‘有字段’，不约束‘字段填得对’**——没有 schema 强校验时，LLM 可以填一个空洞的‘依据：无’。所以准确说，模板摘要是**在‘不可审计’和‘过度约束’之间选了可控的一侧**，不是绝对更优。

如果要做这个对照，我会设计两组：同一批长任务，一组用模板摘要、一组用自由摘要，比**关键事实保留率、摘要后可读性、下游任务完成率、摘要长度稳定性**。当前我只能说设计动机上模板更可控，**没有实验证明它比自由摘要好**。”
```

### 4. context 里包含不相关信息有做处理吗

- **准入侧**：你有子 Agent 隔离（专家独立上下文 + 结果摘要），这是真处理；
- **淘汰侧**：记忆召回有相关性排序 + 预算裁剪，这是真处理；
- **压缩侧**：P4 保留是**时间判据不是相关性判据**，摘要保留“每轮记录”不是“相关片段”——**这一层没有按相关性处理**；
- **工具结果侧**：外化是**长度判据不是相关性判据**。

所以准确说法是：**“不相关”的处理在“记忆召回”和“子 Agent 隔离”两层有真实机制，在“压缩保留”和“工具外化”两层是按时间/长度而不是按相关性——后者是我当前的缺口。**

```
“我分几个来源看，因为不同来源的处理方式不一样。

**第一，长期记忆、分层报告召回里的不相关信息**——这层我做了相关性处理。每轮召回走 BM25，复合分数是相似度加权加记忆强度，然后按 token 预算裁剪，不是全量注入。但边界是：**检索是纯 BM25，没有语义向量**，词面不匹配的相关记忆召回不到，词面匹配的不相关记忆可能进来，这是我下一步要补向量的地方。

**第二，子 Agent 和专家协作里的不相关信息**——这层是**准入侧隔离**。每个专家调用有独立上下文，探索过程不进主 Agent，只回摘要结果。所以专家读了一堆无关文件、试错回滚，这些都不会污染主上下文。

**第三，压缩保留里的不相关信息**——这层我要诚实说，**当前不是按相关性处理的**。P4 保留段判据是‘最近 6 轮’，是**时间判据不是相关性判据**；摘要把旧轮次按‘意图/结果/依据’结构化记录，保留的是**每轮记录**，不是‘与当前 goal 相关的片段’。所以旧轮次里和当前无关的内容，只要在最近 6 轮内就保留，在 6 轮外就进摘要——**没有做相关性筛选**。

**第四，工具结果里的不相关信息**——外化是**按长度阈值**触发，不是按相关性。一条相关但短的结果不处理，一条不相关但长的结果会被外化。外化本身是省 token，不是筛相关性。

所以准确说：**‘不相关’在记忆召回和子 Agent 隔离两层有真处理，在压缩保留和工具外化两层是按时间/长度而不是按相关性——后者是我当前的缺口**。如果要补，我会在 P4 保留段加一层‘与当前 goal 的相关性打分’，而不是只按最近 6 轮；工具外化也可以加‘是否与当前 todo 相关’的判断，而不是只看长度。”
```

#### 4.1. 你说压缩保留是“时间判据不是相关性”，那“不相关但很新”的内容怎么办

```
**相关性打分不该由我在全局做，原因有两层，而外部判断只该用在“模型看不到”的边界上。**

**第一层，新内容默认相关。** 用户刚说的话、刚返回的工具结果，很可能就是任务的最新输入，任务不是一成不变的，新内容默认保留，**不打分、不淘汰**——拿相关性去筛新内容，很可能误杀任务转向后的关键信息。

**第二层，压缩前的完整对话，模型自己会按位置和语义判断重要性。** LLM 有近因效应、有 lost in the middle，它本来就会根据内容在上下文里的位置去权衡；我如果再叠一层外部相关性打分，是**多此一举，而且可能和模型自己的注意力判断冲突**——我判它不相关想压掉，模型其实正需要它；我判它相关想保留，模型其实已经忽略它。所以对“模型能看到的完整对话”，我不做额外打分。

**那外部判断该用在哪？用在“模型看不到”的那一刻。** P4 要把旧历史压成摘要，压完模型就看不到原文的位置信息了，这时候才需要外部机制兜底，决定旧历史**保留多少、压多狠**：高相关的，摘要时保留更多细节、甚至提回保留段；低相关的，压得更狠或直接外化成 path。所以**打分不是替模型判断整段对话谁重要，而是在“必须压缩、模型即将失去原文”的边界上做取舍**——它决定的是“旧历史怎么压”，不是“新内容要不要留”。

**这里有个边界：“当前任务”是动态的。** 任务可能转向，旧历史里和“旧 goal”相关的内容，和“新 goal”可能不相关。所以打分的参照系要用**当前最新的 goal 或 query**，不是任务初始的 goal，否则任务转向后会把该保留的旧历史误判成不相关。

**最后补一句：不打分不等于不观测。** 模型的位置判断是隐式的、没有可观测输出，所以我会保留快照、压缩日志和 trace 用于事后归因——出了 bad case，能判断是模型注意力问题，还是压缩丢了信息。**不额外打分，但要保留可归因的证据。**

所以准确说：**新内容默认保留不打分；完整对话交给模型自己的位置和语义判断；外部相关性打分只用于“待摘要的旧历史”这个模型即将看不到原文的边界，决定旧历史保留多少、压多狠；参照系用当前最新任务；同时保留快照、日志、trace 做归因。** 这样既不会误杀新输入，也不会和模型的判断打架，还能让旧历史的压缩跟着当前任务走。
```

#### 4.2. 相关性判断本身谁来做，LLM judge 的成本你算过吗

```
“先诚实说：**这个‘待摘要旧历史的相关性打分’我目前还没实现**，P4 的切分判据还是‘最近 6 轮’，所以严格说我**没有实测成本可以报**。但我可以讲如果做，我会怎么控制成本，因为这件事的触发结构决定了它不该很贵。

**第一，它是低频触发，不是每轮做。** 相关性打分只在 **P4 触发的那一刻**做一次，判的是“待摘要段的那批旧消息”，不是每轮对话都判。P4 本身在任务里可能只触发一两次，所以打分次数是**个位数级别**，不是每轮一次。这是成本可控的前提。

**第二，分层判断，不是所有消息都上 LLM judge。** 我会先做**便宜的一层**：用 embedding 相似度或 BM25 对‘旧消息 vs 当前 goal’做一个粗排，把明显低相关的先筛出来；只有**粗排后处于中间地带、拿不准的**，才送 LLM judge 精判。这样 LLM 调用量被压到少数‘模糊样本’上，而不是全量。

**第三，低分不直接丢，而是降级。** 不管是 embedding 还是 LLM judge，判低了都不直接删，而是**降级到‘压得更狠/外化成 path’**，保留可回读。这样即使判断误判，信息还在磁盘上，不会因为一次打分错误就永久丢失。这既是成本控制，也是误判兜底。

**第四，成本可以离线标定。** 我可以离线用一批历史任务，人工标‘哪些旧消息对当前任务重要’，再看 embedding 粗排和 LLM 精判的召回/误判，**用离线数据定阈值和分层比例**，而不是在线拍脑袋。在线只跑标定过的策略。

所以准确说：**我还没实现，没有实测成本；但设计上它是低频触发（只在 P4）、分层判断（粗排 + 少数精判）、低分降级不丢弃、阈值离线标定——成本结构上是可控的，不是每轮全量 LLM judge。** 如果面试官要具体数字，我现在给不出，这是下一步要实测的。”
```

#### 4.3. 工具外化按长度不按相关性：一条又长又相关的结果被外化，模型读不回怎么办

```
“这个场景确实是我当前的一个真实风险。

**第一层，外化的触发条件确实只看长度，不看相关性。** 一条又长又相关的结果，只要超阈值就会被外化，留 preview 和路径。它没有被删，原文在磁盘上，但**上下文里只剩预览**。

**第二层，读回靠模型判断加提示词引导，不是系统强制。** 模型能看到‘这条被外化了、原文在哪’，但读不读、读多少，靠它自己判断。我的评测里中任务能读回，是**提示词明确指导了怎么读**，不能证明没有指引也会主动读。所以‘模型没读回’是可能发生的，而且**系统当前不会发现**——外化了、模型没读、任务失败，这个链路没有检测点。

**第三层，如果要把这个风险兜住，我会做三件事**：**第一，外化前加一道‘相关性/关键性’判断**——如果这条结果和当前 todo 或 goal 强相关，**不外化，或者只外化尾部、头部保留**；**第二，外化后加检测**——如果后续若干轮模型没有读回这条外化内容，而任务又依赖它，就在上下文里**强制回注一段‘你有一条外化结果未读回，路径是 X，请先读取’的提示**；**第三，对‘必须用的长结果’，外化时在预览里保留关键字段**，而不是只留开头几百字，让模型即使不读全文也能拿到核心信息。

所以准确说：**外化按长度不按相关性，读回靠引导不是强制，系统当前不检测‘外化未读回’——这是缺口。补法是外化前判关键性、外化后检测未读回并强制回注、预览里保留关键字段。** 当前我只做到‘留了路’，没做到‘确保走这条路’。”
```

#### 4.4. 压缩过程中怎么识别哪些相关、哪些不相关？

```
我的压缩过程里没有显式的相关性识别。P4 的切分按最近 6 轮，保留段看时间，待摘要段整段交给摘要模型，没有逐条判断“这条相关、那条不相关”；P1 外化按长度阈值，也不是按相关性。所以压缩时的相关性，目前是交给摘要模型在生成时自己把握，我没有在外面再做一层筛选。

但这条线我之前和您对齐过看法，我把它串一下。

所以准确说：压缩过程中我没有显式的相关性识别，相关性目前交给摘要模型自己把握；按我的立场，外部相关性判断只该用在待摘要旧历史这个模型即将看不到原文的边界上，参照系用当前最新目标，低相关降级不删除，同时保留快照、日志和 trace 做归因。这套判断我还没有实现，是下一步。
```

#### 4.5. 有没有出现过删掉不该删的东西？有没有做一些设计去优化这个问题？

```
先分清一个概念：我的机制里没有物理删除。外化是把正文搬到磁盘、留预览和路径，摘要是把旧消息替换成摘要，但摘要前落了完整快照。所以原文都还在，只是当前轮次看不到。

但“移出上下文”在效果上就是“当前看不到了”，所以该留的没留确实会发生。这些设计保证的是“原文不丢、可回放”，不保证“模型一定会去找回”；而且摘要输入截断 500 字、保留段按最近 6 轮不按重要性，这两个仍然是该留的没留的风险点。下一步我会补摘要输入的头部加尾部截断、约束栏目的校验、以及关键事实保留率的统计，让“该留的没留”从不可观测变成可度量。

我做了外化可回读、摘要前快照、配对保护、孤立工具外化、回归测试这些设计，但保证的是可回放不是一定会找回，截断和按时间保留仍是风险，下一步补头尾截断、约束校验和关键事实保留率统计。
```

#### 4.6. 关键信息被丢弃基本发生在什么情况下？为什么会被踢出去？有没有办法保留下来？

```
你没有物理删除，所以“丢弃”实际是“移出当前上下文、后续轮次看不到”。按你的机制，关键信息被移出基本发生在三个具体场景，每个场景的原因不同。

第一个场景是 P1 外化。原因是外化按长度阈值触发，不看相关性；一条又长又关键的工具结果超了阈值就会被外化，正文移到磁盘，上下文里只剩预览和路径。它没有被删，原文还在，但如果模型没有主动读回，这一轮就相当于看不到了。所以这里的原因是“按长度不按相关性触发”，加上“回读靠引导不是系统强制”。外化判据是长度不是相关性，所以又长又关键的信息会被移出

第一个场景是 P4 摘要替换旧消息。原因是你保留段的判据是最近 6 轮，关键信息如果不在最近 6 轮里，就会进待摘要段，被压成一条摘要；能不能在摘要里活下来，取决于摘要模型有没有把它写进某一轮的意图/结果/依据。保留判据是时间不是重要性，所以久远但关键的信息会进入待摘要段

第三个是摘要输入又是逐消息只取前 500 字，放在消息后部的信息根本进不了摘要模型。所以这里是两层原因叠加：保留判据是时间不是重要性，加上摘要输入截断。

方法：外化不删除，留预览和路径，配合读取工具可回读；摘要前落完整快照，不可逆之前有可回放的备份；切分点前移到配对完整处，孤立工具结果先外化、路径写进摘要；加了独立的约束、禁止项、未完成 todo 栏目，让跨轮硬约束有专属归宿，不塞进逐轮摘要。
```
### 5. 长上下文导致模型忽略用户真实意图怎么办

```
我先说为什么会这样，再说我怎么处理。

**为什么长上下文会忽略用户真实意图，有四个叠加原因**：第一，**注意力稀释**——上下文越长，模型对每个 token 的注意力越分散，而且有 lost in the middle，中间的内容容易被淹没，用户意图如果出现在中间轮次就危险；第二，**近因效应**——多轮工具调用后，最近几步占注意力大头，最初那句“我要解决什么”被后续过程覆盖，模型容易跟着最近一步走；第三，**信噪比下降**——长上下文混入大量工具返回和试错，噪声里找意图容易抓错；第四，**意图本身会漂移**——用户中途改需求，模型如果只记早期意图，就会按旧目标执行。另外如果摘要没把意图作为固定字段，压缩后意图也会淡。

**怎么处理，我分检测和治理两层。**

**检测层**：把用户真实意图作为**固定锚点**放在上下文显眼位置，每轮可见，而不是埋在历史里；做**意图漂移检测**，每隔几轮比对当前执行方向和原始意图，偏离到阈值就提醒或回注；把“当前目标、未完成项、硬约束”单独列成栏目，模型每轮看到的是“我要干什么”，不用从长历史里自己找。

**治理层**：意图锚点放**开头或结尾**，利用首因和近因，不放中间；**压缩时固定保留“用户真实意图”字段**，我的约束栏目是同类思路，可以再加一个“当前目标”栏；检测到话题切换就**重新提取并前置当前意图**，旧话题降级；探索性、噪声大的工作放**子 Agent 隔离**，主 Agent 只拿意图加摘要结果；长任务**每隔 N 轮回注意图加进度**，防漂移。

所以准确说：**忽略意图是注意力稀释、近因效应、信噪比下降、意图漂移、压缩丢失叠加的结果；处理上不是单点，是“意图锚点前置 + 漂移检测 + 压缩保意图栏 + 话题切换重锚定 + 子 Agent 隔离 + 周期回注”一套组合。** 我当前做到了一部分——约束栏目、子 Agent 隔离、摘要结构化有基础，但意图锚点前置、漂移检测、周期回注还没系统做，这是下一步。
```

#### 5.1. 意图锚点放在上下文显眼位置，具体放哪、怎么防它自己占 token

```
就是**把意图放在一个固定的锚点位置**，而不是让它散在历史里。具体落地我分三点说：

**第一，锚点放哪：每一轮对话的**消息流内，不放最前面。** 锚点放在消息流里的固定位置（比如每轮 user 消息前带一个精简锚点，或者一条独立的“当前目标”消息）。

**第二，锚点放什么：只放“当前目标一句话 + 当前进度一句话 + 未完成项”，不放全文、不放历史。** 锚点的作用是“提醒模型现在要干什么”，不是“复述所有上下文”，所以它必须精简，否则自己就成了新的膨胀源。具体的 plan 计划，在历史上下文中存在。

**第三，更新：**周期回注，不是每轮重写。** 锚点内容稳定时，每轮带同一份精简版；检测到任务转向或漂移时，才更新锚点。这样既每轮可见，又不会因为每轮改写而破坏缓存或膨胀 token。

所以准确说：**意图锚点就是放一个固定位置——系统提示固定段或独立“当前目标”栏，只放目标/进度/未完成项，走独立通道不参与压缩、有长度上限、周期回注更新。** 这样它每轮可见、不漂移，也不会因为每轮重复而自己占爆 token。
```

#### 5.2. 意图漂移检测怎么判“偏离”，你用什么信号

```
**我当前没有专门的意图漂移检测**，`<goal>` 是初始研究问题、渲染进上下文，只在用户发起会话时更新意图，llm 走到某一轮时没有“当前方向 vs 原始意图”的比对机制。如果要做，我不会一上来就用 LLM judge 每几轮判一次——那样成本和误判都不可控。我会分三层：

**第一层，便宜信号粗筛，不调 LLM。** 我项目里已经有几个现成的间接信号：**todo 的完成度和未完成项**——如果长期没有 todo 推进，可能跑偏；**反思中间件的充分性判断**——它本来就在判断“证据够不够”；**停滞检测**——如果连续多轮没有新工具调用或新信息，可能是漂移或卡住；再加上**当前 query 和原始意图的 embedding 相似度**。这些信号便宜、每轮可算，用来**粗筛“可能漂移”的轮次**，而不是每轮都判。

**第二层，只有粗筛异常才上 LLM judge 精判。** 比如 todo 长期不推进 + 停滞检测触发 + 相似度骤降，这几个同时异常，才把“原始意图 + 最近几轮执行摘要”送一次 LLM judge，问“当前执行是否偏离原始意图”。**这样 LLM 调用是事件触发的、不是周期性的**，次数是个位数级别，成本可控。

**第三层，判错不直接纠偏，低置信不强制。** LLM judge 判“偏离”时，我不直接改任务方向，而是**在上下文里插一条提示**：“当前执行可能偏离原始意图，请确认是否回到 X”，让模型自检；judge 置信度低时**只记录不干预**。这样即使判错，也不会把正确执行强行拉偏——**误判的代价是“多一条提示”，不是“改错方向”**。

所以准确说：**漂移检测不是“每几轮 LLM judge”，而是每一轮开始时“便宜信号粗筛（todo/反思/停滞/embedding）→ 异常才 LLM 精判 → 判错只提示不强制、低置信不干预”**。这样成本是事件触发而非周期性的，误判也不会造成硬伤害。当前我只有这些信号本身，还没把它们串成漂移检测，这是下一步。
```

#### 5.3. 你怎么验证“意图没被忽略”

```
先诚实说：**我没有专门评测“意图是否被忽略”**。我的评测判的是**最终产物和标准答案是否全字段一致**，加上完成率、token、轮次——**完成率不等于意图保真**，一个任务可能中间方向偏了又绕回来、碰巧做对，或者模型把意图理解成别的但产物恰好通过，**我没法从完成率反推“过程有没有跑偏”**。这是我评测的一个缺口。

如果要验证意图没被忽略，我会从三个层面设计：

**第一，构造“意图漂移”的 case。** 不是固定标准答案的普通任务，而是专门设计：**真实意图放在中间轮次**（前面有闲聊或干扰）、**中途改需求**（从 A 改到 B）、**有强干扰项**（上下文里混入和意图无关但看起来相关的内容）。看模型在这些场景下**最终产物是否还对**，以及**中间是否回到意图**。

**第二，加“意图锚点对照”的过程判分。** 不只判最终产物，还在**中间轮次**检查“当前执行方向是否和意图锚点一致”——可以用轻量方式：把每轮的工具调用/推理摘要和意图锚点做比对，看有没有明显偏离。这比只看最终完成率更能暴露“过程跑偏”。

**第三，把现有间接信号串起来做归因。** 我已经有 todo 完成度、反思充分性、停滞检测、compaction 日志、trace，这些**单独看不是意图保真指标，但串起来能判断“这次任务有没有出现长时间不推进、反复回退、方向跳变”**——这些是意图漂移的间接信号。我可以先做“漂移信号统计”，再看它和最终失败的相关性。

所以准确说：**当前我没有专门的意图保真评测，完成率不能证明意图没被忽略；要验证，得构造“意图在中间/中途改需求/强干扰”的 case，加中间过程的意图锚点对照判分，并把 todo/反思/停滞/trace 这些间接信号串起来做归因。** 这是下一步要补的。
```

### 6. 压缩阈值

#### 6.1. Compaction 触发的 Token 阈值怎么定的？阈值太大或太小会怎样？

```
我的阈值是分阶段的，不是单一比例。默认 40% 触发外化、80% 触发摘要、90% 触发收尾。fraction 是当前消息的 token 数除以模型窗口，窗口优先取配置，没有配置就按模型解析。这些数字可以被配置覆盖。

为什么分阶段而不是一个阈值：因为不同压缩手段的代价不一样。外化是可逆的，早触发没关系；摘要是不可逆的，要晚触发、而且触发前先落快照；收尾是熔断，要在接近上限时才触发。如果只用一个 80%，外化就没有机会在更早、更便宜的时候发生，收尾也没有独立触发点。

阈值太大或太小会怎样：太大，压缩触发太晚，上下文已经接近窗口上限，模型效果可能已经下降，压缩时能操作的空间也小，而且可能来不及做快照和配对保护；太小，压缩太频繁，可逆操作被反复触发，摘要次数上升，信息损失累积，token 省了但轮次和成本上去了。我的中任务观察是，有了 40% 这一档之后，进入 80% 摘要的频次更少，说明早触发可逆操作能推迟不可逆操作。
```

#### 6.2. Context 在什么比例下输出效果最好？80% 是固定比例吗？（被质疑）80% 的阈值设计合理吗？

```
80%不是我实验出来的最优值，它是短上下文测试下的一个权衡结果。因为我的测试阶段使用的短上下文来对比压缩与不压缩的效果。窗口只有 16K 的时候，留 20% 的余量是为了给摘要本身、快照写盘、以及压缩后那一轮模型调用留空间。如果阈值定得太晚，比如 95%，压缩还没做完上下文就可能已经顶到窗口上限；如果定得太早，比如 60%，摘要会触发得太频繁，不可逆的信息损失累积，轮次也上去了。所以在 16K 这个短窗口下，80% 是一个“来得及压缩、又不至于压太频繁”的折中点。我的长任务在 P4 触发时 fraction 在 0.84 左右，压缩后降到 0.47 左右，说明这个切点在实际运行里是可用的。

但它不是普适最优。第一，它是经验值，我没有做过阈值消融，没有比较过 70%、80%、90% 下完成率、token 占用和关键事实保留率的差异。第二，它和窗口大小强相关，16K 下的 80% 和 128K 下的 80% 不是一回事，窗口越大，20% 的余量绝对值越大，80% 这个比例是否还合适需要重新看。第三，我的评测里 P5 的 90% 一次都没触发过，说明在短上下文里 80% 之后基本没有继续上升的机会，这既是 80% 够用的证据，也说明我没有验证过“再晚一点压”会怎样。

```

### 7. 会话恢复与上下文重建
