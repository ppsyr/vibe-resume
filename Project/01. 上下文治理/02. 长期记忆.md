### 1. L1、L2、L3 三层记忆分别用于什么样的场景，怎么存储，存的是什么，在什么时候加载

```
我的长期记忆分三种类型：情景记忆、语义记忆、程序记忆，对应“发生过什么、提炼出的事实、怎么做一件事”。

存储上，我目前三种类型都写在同一个 Markdown 文件里作为 truth source，内存里建 BM25 倒排索引，按 type 字段区分类型，没有分库分表。所以存储介质上没有分层，分层是在内容和操作上。

内容上，情景记忆是具体发生的事件记录，语义记忆是从多次情景里提炼合并后的事实，程序记忆是程序性知识。我的 consolidate 操作做的就是“把多条情景记忆合并成一条语义记忆，旧的标为 forgotten”，所以情景到语义的转换是有的。

加载时机上，我目前只有一条路径：每轮对话开始前，取最后一条用户消息作为 query，去记忆检索器里按 BM25 加记忆强度做复合排序，按 token 预算裁剪，注入成一条记忆召回消息。这条路径对所有类型一视同仁，没有按类型区分加载时机。
```

#### 1.1. memory 和当前 query 不相关怎么办

```
我的记忆召回 LLM 根据需要设置 query，去 BM25 检索，按相似度加权加记忆强度做复合排序，设了相关性阈值，低于阈值的不注入，过时的记忆会被删掉，最后按 token 预算裁剪注入。所以低分和过期这两类不相关，我是处理了的。

剩下的缺口是词面高分但语义不相关。因为检索是纯 BM25，分数高只代表词面重合，不代表语义相关。用户问苹果怎么保存，一条讲苹果公司财报的记忆可能因为都含苹果而拿到不低的词面分、过了阈值被召回。阈值拦的是低分，过时删除管的是时效，都拦不住这种词面像、语义不像的误召回。

补法分两层。第一层加语义检索，用 embedding 算语义相似度，和 BM25 做混合排序，让语义相关但词面不同的记忆能召回、词面相关但语义不同的被压下去。第二层加召回后重排，把 BM25 和语义分都靠前的候选交给模型做一次相关性判断，剔掉语义不相关的。第一层解决召回不全和词面误导，第二层解决最后一道语义把关。我当前只做了阈值和过时删除，这两层还没做，是下一步。
```

### 2. 三层记忆的区别、差异在哪

```
我的三种记忆在内容上有明确差异。情景记忆是具体发生过的事件，带情境；语义记忆是从多次情景里提炼合并后的事实和概念，去掉了具体情境；程序记忆是怎么做一件事的流程性知识，不依赖具体情境。

在系统行为上，差异主要体现在两处。第一是 consolidate，我把多条情景记忆合并成一条语义记忆，旧的标为 forgotten，所以情景到语义是有转换关系的，程序记忆不参与这个合并。第二是衰减参数，我的衰减常量里有按类型区分的结构，可以给不同类型设不同的衰减速度，虽然当前我没有按类型调。
```

### 3. 记忆提取是怎么做的，怎么让大模型生成记忆，有冲突或者要更新的怎么处理

```
我的记忆写入是异步的。记忆沉淀中间件每 N 个用户轮次，把最近的消息构造成一个任务，丢给后台 worker，worker 在后台做抽取和编码，调用管理器的 encode 落库，必要时调用 consolidate 把多条情景记忆合并成一条语义记忆，旧的标为 forgotten。worker 构造时接收了模型参数，设计上是用模型做抽取的。

怎么让模型生成记忆：这一步我给 worker 传了模型，让它把消息格式化成文本后交给模型抽。但我要诚实说，抽取提示词和输出字段在我这里还没有做成强 schema，模型输出什么就落什么，没有逐字段校验。这是我要补的，应该让模型按“内容、类型、重要性、来源”结构化输出，再做解析和校验。

冲突和更新怎么处理：encode 有幂等检查，先按 id 查，存在就不重复加；store 的 add 在 id 冲突时抛冲突异常，不会静默覆盖。更新走 reconsolidate，用新内容替换旧内容并记操作日志。合并走 consolidate，把多条情景合并成语义、旧的标 forgotten。但我要说清边界：这些是幂等、合并、显式更新，不是自动的矛盾消解。我没有让模型判断“这两条记忆矛盾、该信哪条”，冲突处理目前是“同 id 报错、不同 id 合并标旧”，不是语义级的矛盾解决。

所以准确说：写入是中间件每 N 轮触发、worker 异步用模型抽取、encode 幂等落库、consolidate 合并情景成语义、reconsolidate 显式更新；冲突靠幂等和合并标旧，不是模型做矛盾消解；抽取的结构化提示词和校验还没做，是下一步。
```

#### 3.1. 怎么判断哪些是关键信息，哪些需要舍弃
```
我当前没有在写入时主动判断“哪些是关键信息、哪些该舍弃”。worker 用模型抽取，但抽什么、给什么重要性，没有明确判据；encode 落库时抽到就存，不做重要性筛选；真正做淘汰的是事后的 Ebbinghaus 衰减和遗忘策略，判据是时间和访问强度，不是内容重要性。所以我的“舍弃”是事后按时间和强度淘汰，不是写入时按关键性筛选。
```
