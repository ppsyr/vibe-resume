### 1. 可恢复运行状态这一块是怎么去实现恢复机制的？

```
我的恢复机制分三层。

第一层是 state 持久化。checkpointer 从 LangGraph 默认的的内存版换成了 SQLite 版，默认库在用户目录下，异步 graph 用兼容的异步 saver。恢复的是框架完整的 checkpoint，包括状态、版本和待处理写入，不是自己另建一张聊天记录表。连接覆盖 graph 使用期，正常退出、初始化失败和重建路径上都会释放；保存失败会明确报错，不会静默退回内存还声称持久化成功。

第二层是 thread 元数据持久化。每个会话一个 JSON，存在用户目录下，记 thread_id、标题、创建时间、更新时间，时间用带时区的 ISO 8601，写入用临时文件加原子替换，单条损坏不影响其他会话列出，thread ID 做路径穿越校验。这一层管的是“有哪些会话、叫什么、什么时候用过”。

第三层是运行时恢复。切换会话时用目标 thread ID 取 state，不复制源会话历史，不向恢复后的 graph 追加已经保存过的历史消息；runtime 重建时先成功创建目标上下文再替换引用，失败时原会话还能用；同时刷新 CLI 持有的 runtime 和服务引用，避免界面显示新会话、实际调用旧会话；会话级状态隔离，新会话不继承旧会话的消息、待处理工具调用和 todo。

边界我也说清：我不恢复内存对象、连接、凭据、沙箱进程、未完成工具和子 Agent；不支持多进程同时管理同一个会话；不声称强杀后能保留还没提交的写入。所以准确说，我恢复的是“最后成功落盘的 checkpoint 加元数据”，跨进程成立，但运行中的外部资源不恢复。
```

### 2. 他的工具调用的缓存可以恢复吗？

```
这个问题要拆成三件事，答案不一样。

第一，已经提交进 checkpoint 的工具调用消息，能恢复。我的 checkpointer 保存的是框架完整 checkpoint，包括状态、版本和待处理写入，恢复的是最后成功落盘的那份。所以如果工具结果已经写进去了，恢复后能看到这条工具消息和它的内容。

第二，还没提交的、进行中的工具调用，不保证恢复。我的材料明确不声称强杀后能保留尚未完成的 checkpoint 写入。所以如果进程在工具执行中途被强杀，这次调用可能既没结果、也没记录，恢复后不会自动重跑，也不会自动补一个结果。

第三，工具的外部副作用和进行中的执行，不恢复也不重放。材料明确不恢复未完成工具、子 Agent、后台任务和外部进程，也不承诺恢复内存对象、连接、凭据、沙箱进程。所以一个工具如果已经改了文件、发了请求，恢复不会回滚它；如果它执行到一半，恢复也不会接着跑。恢复只保证“最后提交的状态能读回来”，不保证“执行中的动作能续上”。

所以准确说：已提交进 checkpoint 的工具消息能恢复，未提交的进行中调用不保证，工具的外部副作用和进行中执行不恢复、不重放。这是当前明确的边界。
```

### 3. 如果要做数据迁移，哪部分数据对用户来说是有迁移必要的？

```
必须迁移的，是用户资产。第一是 checkpoint state，也就是每个 thread 的会话状态，删了就恢复不了对话；第二是 thread 元数据，包括 thread_id、标题、创建时间、更新时间，尤其是用户手动改过的标题，删了就找不回来。这两样是恢复会话的最小集合，缺一个会话就不完整。

建议迁移的，是会话的附属数据。第一是长期记忆，也就是 traces.md，它是跨会话积累的用户偏好和事实，重建成不了；第二是 journal 和 report，是运行记录和最终产物，用户可能还要回看；第三是 artifact，是生成的文件。这些不属于“恢复会话”的最小集合，但属于用户资产，丢了是损失。

可不迁移的，是可重建或可再生成的。第一是快照和外化文件，它们是从消息里衍生出来的，只要 checkpoint 在，理论上可以重新生成；第二是标题，如果用户没手动改过，可以从首句重新生成，但手动改过的必须迁移；第三是缓存类数据，比如检索索引，可以从 traces.md 重建。
```

### 4. 如果一些操作是一次性的，比如调用的工具是修改东西，你没有收到工具返回，但它其实已经执行了，有什么办法解决？

```
要解决这类问题，通用做法有四层。

第一层，工具分级。不是所有工具都要同样处理。只读工具，重跑一次没有副作用，可以直接重放；有副作用的修改类工具，不能盲目重放，必须做去重。所以先把工具按“是否幂等”分类，只对非幂等工具做特殊处理。

第二层，执行前记录意图。在工具执行之前，先把“准备调用什么工具、参数是什么、调用 id 是什么”写进 journal 或 checkpoint，这样崩溃后能知道“有个调用发起了、但没看到结果”。这就是把未提交窗口里的信息尽量落盘。

第三层，幂等键和结果查询。给每次工具调用一个唯一 id，作为幂等键；工具侧如果支持，执行后把结果按这个 id 存下来；恢复时先查“这个 id 有没有结果”，有就直接用，没有才决定重试还是询问用户。没有幂等键的话，至少要做到“恢复时发现未完成调用，先向用户确认，而不是自动重跑”。

第四层，恢复时的不确定态提示。如果既没有结果、也无法查询，就标记为“不确定是否已执行”，提示用户确认，而不是假装成功或假装失败。
```

### 5. 重复执行怎么优化？文件读取失败在你本地为什么会出现

```
模型反复读同一个文件、反复调同一个工具，我当前没有去重机制，靠模型自己收敛。

优化方向有几个。第一，恢复或补一个循环检测，识别“同一工具、同一参数、短时间内重复调用”，命中就提示模型或阻断。第二，工具结果缓存，同一个调用 id 或同一组参数的结果缓存起来，重复调用直接返回缓存，不真的再执行。第三，把“已经读过这个文件、结果是什么”显式放进上下文，让模型知道不用再读。第四，外化要配合，如果文件被外化、模型只看到预览，它可能以为没读到而重复读，所以外化时要留足够提示，告诉模型原文在哪、不用重读。

文件读取失败在我本地有几个原因。第一，沙箱对文件工具统一做路径校验和读写权限检查，路径越界会被拦，这是主动拒绝不是失败。第二，本地安全守卫和 Docker 路径守卫会拒绝非法路径。第三，会话绑定项目目录，切换会话后可访问范围同步更新，旧路径可能不再可访问。第四，文件本身不存在，或者已经被外化移到磁盘、原位置取不到。第五，Docker 和本地之间有路径转换器做映射，映射失败也会读不到。
```

### 6. 大模型反复读同一个代码块的不同区间，怎么处理？ （追问）能完全避免吗

```
先分清两种情况。一种是真重复，同一文件同一区间反复读，这通常是上下文里看不到之前的结果，或者结果被截断、外化后模型以为没读到。另一种是合理分段，模型要读一个文件的不同区间来拼完整内容，这不是重复，是正常行为。所以不能一律按“同文件同区间”去拦，否则会误伤分段读。

处理上分几层。第一层，区间级记录。文件读取工具记录“这个文件读过哪些区间、结果是什么”，在上下文里显式告诉模型“你已读过 1 到 200 行，结果是……”，让它知道不用再读同一段。第二层，循环检测。同一文件同一区间在短时间内重复读，命中就提示或阻断。第三层，外化配合。外化之后要留足够提示，告诉模型原文在哪、已经读过什么，避免它因为只看到预览而重读。第四层，读全策略。与其让模型反复读不同区间，不如一次性把文件读到合理上限、或者提供一个“读整个文件”的能力，减少分段读的次数。

能完全避免吗：不能。原因是模型不知道上下文里已经有什么，除非你显式告诉它；分段读本身有合理性，不能一刀切拦；外化和截断会让模型误以为没读到；而且模型的行为有随机性，同一任务两次运行可能读法不同。所以能做到的是“减少重复、显式告知已读区间、对真重复拦截”，做不到“完全避免”。我的项目当前连区间级记录和循环检测都还没做，这是下一步。
```
