### 1. 如果让你做 bad case 分析，你有哪些思路？结合一个实际例子说说怎么定位问题

```
做 bad case 分析，我的思路分五步。

第一步，先确认这个 case 是不是真的失败。检查判分脚本、预期答案、测试环境有没有问题，排除“判分本身错了”的情况，否则后面全是白工。

第二步，看 trace 定位行为从哪一步开始偏离预期。不是看最终输出，而是看每一步的工具调用、参数、返回、token，找到第一个和预期不一样的步骤，而不是最后一个报错的地方。

第三步，做归因，区分是模型问题还是 harness 问题。方法有两个：固定 harness 只换模型，换强模型后失败率没改善，说明瓶颈在 harness；或者问“人拿到同样的上下文和工具能不能完成”，人也完不成，说明信息或工具本身不够。同时看失败是不是确定性的，三个任务都在同一位置、同一错误类型失败，更可能是 harness 的代码或 schema 问题，因为模型行为有随机性。

第四步，落到具体修复入口。意图错了改提示词，参数错了加 schema 校验，上下文截断改压缩策略，工具不可用修工具集成。每个诊断要对应一个可测试的修改。

第五步，修完重跑同一批 case 验证，而不是靠一次观察下结论。

举个我实际遇到的例子。长任务评测最初 0/3 通过，标准答案是全字段比对，失败现象是最终产物里审计编号变成了 null。我先确认判分没错，业务金额汇总是对的，判分确实判对了。然后看压缩日志和 trace，发现两个偏离点：摘要请求的输入里没有待压缩的历史文本，后续主模型请求里带 summary 标记的消息被跳过了。这里失败是确定性的，三个任务都在同一位置失败，换模型不会变，所以是 harness 问题不是模型问题。修复是补模板占位符、改 state 读取路径。验证时做了隔离复测：只修模板时三个摘要都正确生成了审计编号，但后续主模型请求里还是没有，证明两处问题是独立的；两处都修完才 3/3 通过，163 项单测过。这个例子的价值不是“找到一个 bug”，而是用复测证明“修到什么程度才够”。
```

### 2. 判断它能否完成任务是怎么判断的？

```
我判断任务是否完成，不看模型自己说完成了没有，看最终产物和标准答案。

具体分两层。第一层是结果比对：每个案例有预先固定的标准答案，判分时和标准答案全字段比对，字段不对就不算完成。第二层是执行验证：Python 产物不是看模型说跑通了，而是实际执行断言和边界测试，跑过才算完成。所以模型回复里写“已完成”不构成判分依据，产物对字段、执行过断言才算。

举个实际例子。长任务修复前，业务金额汇总是对的，但审计编号变成了 null。如果只看“任务大概做完了”，可能就放过了；但全字段比对不通过，所以判失败。这正是硬判分的价值：它不放过局部正确但整体不完整的结果。

边界我也说清：我的案例是研究型任务，产物可以结构化比对，所以硬判分成立。如果换成开放式任务、没有固定标准答案，就需要 LLM Judge 加 Rubric，那套我目前没有系统做。另外判分脚本本身也要验证，对空白状态必须失败、对标准答案必须通过，防止判分器本身在说谎。
```

#### 2.1. 测试通过但效率不好，这种问题怎么沉淀？

```
我当前判分只看终态和标准答案，测试通过就算通过，**没有效率判据**，所以“测试通过但效率不好”不会被判成失败，也不会自动沉淀成 bad case。我有的轮次、token、回读次数是汇总指标，不是单案例的效率判据，而且每组只跑一次，没有同任务多次运行的效率方差可比。

如果要把这类问题沉淀下来，我会分三步。

第一步，定义什么叫效率不好。不能只看绝对轮次，要和基线比。同一个任务，取历史成功运行的轮次中位数或最优步数作为基线，实际轮次超过基线的某个倍数，或者重复调用、回读次数明显偏高，就标记为效率异常。这样判的是相对效率，不是绝对步数。

第二步，沉淀成单独的“效率 bad case”类别，不和“失败 bad case”混。失败 bad case 是产物不对，效率 bad case 是产物对但过程差。沉淀时保留完整 trace，记录轮次、token、工具调用序列、重复调用次数、回读次数，以及和基线的差值。这样后续可以看效率差是集中在某类任务、某个工具、还是某个模型。

第三步，把效率异常变成可回归的判据。修完之后，同一批 case 不只判终态，也判“轮次是否回到基线范围内”，防止修了正确性、又把效率改坏了。

所以准确说：我当前没有效率 bad case 的沉淀，因为判分只看终态；要沉淀，得先定义相对基线的效率异常、单独归类并保留 trace、再把效率判据加进回归，让“测试通过但效率差”也能被记录和防止复发。
```

### 3. 测试没有通过时，怎么判断是 agent 的错误并沉淀为 bad case？

```
测试没过，我不会直接把它当 agent 的错误沉淀，而是先排除三类问题。

第一，排除判分本身错了。检查标准答案、判分脚本、测试环境有没有问题。如果判分脚本写错了，agent 其实是对的，沉淀下来就是脏数据。

第二，排除环境和外部依赖问题。工具不可用、网络挂了、沙箱启动失败，这些不是 agent 的错。

第三，排除任务本身有歧义。如果任务描述本身有歧义，agent 按另一种合理理解做了，失败是任务定义的问题，不是 agent 能力问题。

排除完这三类，剩下的才看是不是 agent 行为导致的失败。判断方法看 trace：失败位置是不是 agent 的决策点、同任务换强模型后失败位置变不变、失败是不是确定性复现。如果失败确定性复现、换强模型不改善、trace 里是 agent 选错工具或漏调工具，才沉淀成 agent bad case；如果 trace 里是上下文没给到、工具 schema 错了、状态没传进去，那是 harness 问题，沉淀成 harness bad case，不混在一起。

沉淀时保留 trace、失败现象、归因结论和修复假设。P4 那次就是先确认判分没错，再看 trace 定位到模板占位符缺失和 state 读取路径错误，归因是确定性的、三个任务同一位置失败、换模型不会变，所以是 harness 问题不是 agent 错误，修复后隔离复测 3/3 通过。

边界我也说清：我当前的失败归属是人工做的，没有自动化分类；每组只跑一次，单次失败可能是偶发，需要重复跑确认是否复现；agent 错误和 harness 错误我没有分开沉淀，这是下一步要补的。
```
