### 1. 你了解的 Agent 评测覆盖哪些方面？

```
Agent 评测我理解为一套分层的工程系统，不是给最终回答打一个分。

第一层是硬约束，测越权、泄漏、破坏性动作，用确定性规则做门禁。第二层是任务结果，看 Task Success Rate 和最终环境状态，能用代码断言就不用 LLM 打分。第三层是过程质量，看工具选择、参数正确性、步骤效率、有没有循环，这是 Agent 评测区别于传统模型评测的核心。第四层是可靠性，单次跑通不算数，要看多次运行的方差和 pass^k。第五层是效率成本，Token、调用数、延迟。再往上是业务价值，解决率、转人工率这些。

方法上，确定性断言优先，LLM Judge 只用在主观判断上，轨迹评估不要求黄金路径，约束关键工具和最终状态就够了。评测集上，能力评测和回归评测分开建，能力评测找上限，回归评测防退化。

归因上，靠完整 Trace 加控制变量，换模型、换 harness 变量看失败模式怎么变，单次 bad case 不直接下结论。
```

#### 1.1. 你 Coding Agent 项目里的评测思路是怎样的？整个评测流程包含哪些？

```
Coding Agent 的评测流程，核心是“执行结果驱动”，不是“文本相似度驱动”。

第一步是任务定义。每个任务是一份结构化配置：初始 prompt、用哪个 Agent、沙箱怎么配、成功判据是什么。判据通常是可执行的检查项，比如文件是否存在、命令退出码是否为 0、测试是否通过，而不是让 LLM 去读回答打分。

第二步是隔离环境。每个任务在干净沙箱里跑，防止污染和任务间干扰。跑之前通常要先验证 checker 本身是对的：对空白工作区必须失败，对标准答案必须通过，否则判分脚本本身就在说谎。

第三步是 Agent 执行。在沙箱里启动 coding agent，给它工具权限，让它自由改代码、跑命令、产生文件。

第四步是判分。对执行后的环境跑预设检查。这里有个业界已经踩过的坑：SWE-bench 式的做法只用 PR 附带的测试来验证，但研究发现约 7.8% 被标记通过的 patch 其实过不了项目全量测试，近 30% 的“正确”patch 行为和开发者参考实现不同。所以严格的流程要跑全量测试或做差分检查，不能只信局部测试。

第五步是记录和归因。每次运行记 Agent、模型、任务、trial、是否成功、token、轮次。失败时要能区分是 Agent 的问题、环境的问题、还是判分脚本的问题。

变体方面，有些评测关注迭代进化能力，让 Agent 在多轮里根据反馈持续改进；有些关注长任务，单任务平均 90 次工具调用、百万 token。但骨架都是上面五步。
```

#### 1.2. 如果让你做 bad case 分析，你有哪些思路？结合一个实际例子说说怎么定位问题

```
做 bad case 分析，我的思路是四步。

第一步，先确认这个 case 是不是真的失败。检查判分脚本、预期答案、测试环境有没有问题。业界把失败归因分成评估设置问题、Agent 设置问题和平台限制三类，先排除第一类，否则改了半天是在修判分脚本。

第二步，看 trace 定位行为从哪一步开始偏离预期。不是看最终输出，是看每一步的工具调用、参数、返回、token。找到第一个和预期不一样的 span，而不是最后一个报错的地方。

第三步，区分是模型问题还是 harness 问题。方法有两个：一是模型替换实验，固定 harness 只换模型，换强模型分数不涨说明瓶颈在 harness；二是问“人拿到同样的上下文和工具能不能完成”，人也完不成说明问题在信息或工具缺失，不在模型。

第四步，落到具体修复入口，修完重跑同一批 case 确认。

举个我实际遇到的例子。长任务评测最初 0/3 通过，标准答案是全字段比对。看 trace 发现两个偏离点：摘要请求的输入里没有待压缩的历史文本，后续主模型请求里带 summary 标记的消息被跳过了。这里失败是确定性的、三个任务都在同一位置失败，换模型不会变，所以是 harness 问题不是模型问题。隔离复测证明两处问题是独立的：只修模板时摘要能生成，但后续请求还是拿不到；两处都修完才 3/3 通过。这个例子的价值不是“找到一个 bug”，是用复测证明“修到什么程度才够”。
```

#### 1.3.  从结果导向分析，怎么判断一个结果是 Harness 层问题还是模型问题？
```
判断是 Harness 问题还是模型问题，我不看失败现象直接下结论，而是用控制变量把两者拆开。

第一，固定 Harness 只换模型。换一个明显更强的模型，如果失败率没改善，瓶颈就在 Harness——工具没给对、上下文缺了、权限拦了、状态没传进去；如果换强模型后分数明显涨，说明主要受模型能力影响。但单次结果可能是偶发，要重复跑看失败模式是否稳定复现。

第二，把人放进同样的条件。把 Agent 收到的上下文、工具、返回结果原样给一个人，人也完不成，说明 Harness 提供的信息或工具本身不够；人能完成，说明信息和工具是够的，问题更可能在模型使用能力上。

第三，看失败是否确定性。三个任务都在同一环节、同一错误类型失败，更可能是 Harness 的代码或 schema 问题，因为模型行为有随机性，不太可能三次精确地在同一行出错；失败位置分散、错误多样，更可能是模型策略问题。

第四，看错误类型指向哪一层。参数 schema 错误、上下文缺关键信息、工具返回解析失败，偏 Harness；循环调用、过早宣布完成、推理跳步，偏模型，但要用前两组判据交叉验证。

最后，归因要落成一个可测试的修复假设：换强模型不涨、人也完不成、失败确定性复现，修 Harness；换强模型明显涨、人能完成、失败分散，修模型侧。然后重跑同一批 case 验证，而不是靠一次观察下结论。
```

### 2. 你了解过哪些公开的评测集？

```
我了解的公开评测集，按 Agent 的能力域来分，主要有这几类。

综合/通用 Agent 能力：AgentBench 是较早的通用框架，把 LLM 放在操作系统、数据库、知识图谱等不同环境里测多任务能力。Agentick 更偏向顺序决策，覆盖 RL、LLM、VLM 等多种 Agent 范式，用统一接口比较不同方法在规划、记忆等能力上的差异。TheAgentCompany 模拟一个小型软件公司的数字员工环境，让 Agent 浏览网页、写代码、运行程序、和同事通信，测的是接近真实工作的端到端任务，最强 Agent 自主完成率约 30%。

Web / 计算机操作：WebArena 是 realistic web 环境的代表，VisualWebArena 扩展到了多模态视觉网页任务。OSWorld 测的是真实操作系统里的开放式任务。ClawBench 比较新，用 Docker 加 Chromium 隔离环境跑日常在线任务，特点是五层录制（视频、截图、HTTP、浏览器动作、Agent 消息）加 rubric 判分，而且支持切换不同的 harness（OpenClaw、Hermes、Claude Code 等）来对比 scaffold 的影响。

软件工程 / Coding：SWE-bench 是仓库级 issue 修复的标杆，用真实测试套件验证 patch 是否修好问题。Multi-SWE-bench 扩展到了多语言。DevBench 覆盖软件开发生命周期的多个阶段。这一类的核心判据是执行结果，不是文本相似度。

长程 / 交互式：UltraHorizon 专门测超长程场景，标准配置下轨迹就超过 35k token、60 次以上工具调用，最重设置到 200k token、400+ 次调用，结果发现 SOTA 模型在这些场景下持续低于人类，而且简单加预算解决不了，失败模式被归因到“in-context locking”和基础能力缺口。TRIP-Bench 用旅行规划场景测长程多轮交互，最多 15 轮用户对话、150+ 次工具调用、20 万 token 上下文，hard split 上先进模型成功率掉到 10% 以下。

工具调用 / API：Live API Bench 把 NL2SQL 数据集转成交互式 API 环境，覆盖 11 个数据库、2500+ 可调用工具，测的是参数生成、顺序推理、错误处理、响应解析这些工具使用核心能力，10 个 LLM 加 4 个 ReAct Agent 的任务完成率只有 7% 到 47%。
```

#### 2.1. 你自己构建评测集有什么思路？

```
构建评测集，我先定目标再选案例，不是先收集任务再想怎么打分。

第一步，明确这批评测回答什么问题。是测能力上限，还是防回归？这两类要分开建，能力评测用最难最有代表性的任务，回归评测覆盖已知边界和出过问题的路径，混在一起是最常见的错误。

第二步，案例分三类来源。真实失败案例，从日志和 bad case 里抽，最有诊断价值；人工构造的边界案例，针对已知风险设计，比如关键约束放后部、连续多次压缩、工具结果超长；公开 benchmark 改编，借任务形态但换成自己的判据，做外部参照。

第三步，判据确定性优先。任务结果看最终环境状态，文件、数据库、测试是否通过，能用代码断言就不用 LLM 打分；过程看关键工具是否调用、禁止工具是否避开、步数是否超限；LLM Judge 只用在主观判断上，要有 Rubric，关键案例人工复核。构建时还要做判据极性验证：空白状态必须失败，标准答案必须通过，防止判分脚本本身在说谎。

第四步，控制变量和分层。每个案例能开/关某个机制做对照，按短中长任务分层，短任务验证行为不变，中任务验证可逆操作，长任务验证不可逆压缩和恢复，每层单独看指标。

第五步，规模从 100 条左右高价值用例开始，覆盖最重要的几个业务目标，每个案例跑多次看方差，记录模型、harness、trial、token、轮次，失败保留 trace 便于归因。
```

### 3. 路径级评测怎么做？

```
路径级评测我不要求 Agent 走一条标准路径，而是把轨迹当评测单元，看它在关键节点上是否合理。

如果手上有参考解法，我不做整条路径的精确匹配，因为合法但顺序不同的路径会被误判。更合理的做法是约束关键节点：关键工具是否调用、禁止工具是否避开、参数是否合理、最终状态是否正确、步数是否超限。Arize 的实践是拆成三个评估器：结果相关性、决策路径合理性、推理是否有工具结果支撑。

如果没有参考路径，就用无参考的维度化评估。AgentDiagnose 的做法是从轨迹里诊断回溯能力、任务分解、观察读取、自我验证这些通用维度，不需要预定义正确序列。TRACE 用证据银行累积每步事实，评估效率、幻觉、对工具失败的适应性。这类方法能发现“结果对了但过程很差”的情况。

指标上确定性优先。工具准确率、轨迹效率、重复调用率、错误恢复率这些都可以用规则算，不需要 LLM 打分，可以放进 CI 做门禁。轨迹效率就是最优步数比实际步数，错误恢复率就是工具报错后下一步成功恢复的比例。

最后，路径级评测要输出失败分类，不只是分数。是选错工具、漏调工具、参数错、循环、还是没完成，修复方向完全不同。
```

#### 3.1. 路径非常多的时候，怎么整体评估 agent 在决策层面的准确率？

```
路径非常多的时候，决策准确率不能靠匹配某条标准路径来算，因为合法路径太多，逐条标注不现实，还会把顺序不同但同样正确的路径误判成错。我的思路是四层。

第一层，用终态等价性代替路径匹配。不看中间走了哪条路，只看执行后的环境状态是否和目标等价。比如任务要求产出某个文件、某个数据库状态，就断言终态，不管 Agent 是先搜再读还是先读再搜。这是路径爆炸时最可靠的判分方式。

第二层，如果没有明确的终态可查，就用参考无关的轨迹质量评估。从轨迹里诊断效率、有没有绕路、陈述有没有证据支撑、工具失败后能不能恢复，这些维度不需要标准路径，评的是决策过程的质量，不是是否走了某条特定路径。

第三层，必须约束决策时只约束关键节点，不约束全路径。该调的工具调了没有、禁止工具避开没有、参数是否合理、步数是否超限，接受 unordered 匹配，不要求顺序一致。

第四层，路径多到连关键节点都难穷举时，用多次运行的统计可靠性代替单次判定。单次走对可能是碰巧，用 k 次全部成功的 pass^k 加置信区间来衡量，而不是一次跑对就下结论。

对照我的项目：我当前是结果导向评测，标准答案全字段比对加产物执行断言，实际上已经在用终态等价的朴素版本，但没有过程质量维度和多次运行稳定性统计。如果补，我会走“终态等价加关键节点约束”，再对长任务补多次运行看方差。
```
