### 1. 你理解的 Harness 层包含哪些内容？

```
我理解的 harness 是模型之外的那一整层运行时，Anthropic 和 OpenAI 的定义基本一致：模型负责推理，harness 负责给它工具、管它看到的上下文、在边界内执行、必要时请求审批、把状态持久化下来。

拆开看，我理解包含几个子系统。第一是 Agent Loop，驱动收集上下文、执行动作、验证结果的循环。第二是工具系统，工具怎么暴露、schema 怎么定义、权限怎么分级、结果怎么回填。第三是上下文管理，压缩、记忆、会话状态维护，这是 harness 里最重的一块。第四是安全与审批，沙箱边界、危险操作拦截、人工审批流。第五是会话持久化，状态怎么存、跨进程怎么恢复。第六是可观测，trace、日志、评估信号。

对照我自己的项目：Agent Loop 是 LangGraph 建图加 ReAct 循环，工具系统有内置工具、沙箱工具、专家工具、MCP 接入，上下文管理是最重的部分，有分级外化、快照加摘要、长期记忆读写，安全有沙箱双后端加守卫，持久化从内存 saver 换到了 SQLite，可观测有 journal 和压缩日志。
```

#### 1.1. 你 Harness 的整体架构设计思路是什么？

```
我的 harness 不是从零设计的，是基于 LangGraph 的图骨架装配出来的，所以我先讲为什么选它、用它什么、补了什么。

为什么选 LangGraph。我需要的是一个能表达 ReAct 循环、能挂中间件、能做状态持久化和恢复的运行时。LangGraph 提供了 `create_agent` 的固定骨架，`START → agent ⇄ tools → END`，有 checkpointer 做状态持久化，有 middleware 协议可以在模型调用前后插入逻辑。自己写循环当然可以，但要自己实现状态管理、恢复、中断、流式输出，成本远高于用现成骨架。这是我选它的核心理由：**它把循环和状态这两件最容易写错的事标准化了，我可以把精力放在治理逻辑上**。

把“装配”和“运行”分开，把“治理”做成可插拔的链，把“持久化”和“外部资源”挡在运行层之外。

第一，装配和运行分离。启动时 bootstrap 同步装配出一个 AppRuntime，配置、模型路由、能力注册、沙箱、记忆、专家、checkpointer 都在这一步装好；主循环拿到的是装好的 runtime，只消费不重建。好处是运行期没有装配开销和装配错误，切换 expert 模式或模型时是重建 runtime 再替换引用，失败时原 runtime 还能用。

第二，治理做成中间件链，而不是写死在主循环里。LangGraph 建图给出 `agent ⇄ tools` 的骨架，20 个中间件按固定顺序挂在 before_model、after_model、wrap_model_call、wrap_tool_call 这些钩子上，各自负责上下文治理、技能注入、沙箱绑定、记忆召回、多 Agent 派活、反思、报告。这样每个治理能力是独立可插拔的，加一个能力是加一个中间件，不是改主循环。代价是顺序有耦合，挂载顺序错了行为就错，所以顺序是固定写死的。

第三，上下文治理分阶段。核心取舍是“可逆操作早触发、不可逆操作晚触发、收尾是熔断”。40% 外化是可逆的，早做；80% 摘要不可逆，先落快照再做；90% 剥工具调用是防超窗的熔断，不是压缩。这样不同代价的动作不在同一个阈值上挤。

第四，持久化和外部资源挡在运行层之外。checkpointer 负责 state，元数据负责会话清单，运行层不关心存哪、怎么存；沙箱、专家、MCP 各自有独立边界，专家调用有独立上下文，沙箱有路径和权限守卫，运行层不直接碰外部进程和凭证。
```

#### 1.2. 说说你对 harness 的理解？业界有哪些好的 agent 框架？

```
我对 harness 的理解，最凝练的一句话是：Agent 等于模型加 harness。模型负责推理和决策，harness 是包裹在模型外面、让推理能变成真实操作的那一整套系统——工具怎么暴露、上下文怎么管、状态怎么持久化、权限怎么拦、失败怎么恢复、结果怎么反馈给下一轮。

业界有一个数据我印象很深：Claude Code 泄露的源码里，约 98.4% 的代码是 harness 基础设施，AI 决策逻辑只占 1.6%。这说明真正难的不是让模型“想”，是让它“想完之后能可靠地做”。

业界我关注过几个框架，取向差别很大。

Claude Code 是“运行时越笨，架构越稳定”的代表。它的 TAOR 循环只负责驱动、执行、观察，所有推理和停止判断都交给模型，工具只给 Read、Write、Execute、Connect 四种原语，Bash 作为通用适配器。它把复杂度放在上下文工程和权限层，而不是编排逻辑里。

Codex 的哲学是“仓库即事实来源”，harness 开源，核心是一个 Rust 实现的 agent loop，管会话状态、流式执行、工具调用、沙箱和审批策略。它证明了 harness 设计能实质改变结果：在 ARC-AGI-3 上，只加保留推理和上下文压缩两项，GPT-5.6 Sol 的得分从 13.3% 提到 38.3%，输出 token 还少了六倍。

Pi 走极简路线，默认只给 read、write、edit、bash 四个工具，系统提示词加工具定义不到 1000 token，赌的是前沿模型已经天生知道怎么当 coding agent，脚手架应该薄而不是厚。

Claude Code 让我看到循环要“笨”、治理要“厚”；Codex 让我看到 harness 的默认设置本身就能改变模型表现；Pi 让我看到工具不是越多越好，选择成本也是成本。
```

#### 1.3. 你觉得 harness 最重要的能力是什么？

```
我认为 harness 最重要的能力，不是工具调用、不是记忆管理、不是沙箱，是执行控制——让循环知道什么时候该停、什么时候该重试、什么时候该放弃、什么时候该等人。

理由很简单：工具调用准不准，影响的是完成率；记忆管得好不好，影响的是能跑多久；沙箱严不严，影响的是部署风险。但执行控制管的是整个系统会不会失控。一个 harness 如果没有有界的循环终止、没有失败止损、没有超时和重试上限，工具再准、记忆再好，agent 照样会陷入死循环、在一个已经坏掉的状态上继续烧 token、或者无限重试直到账单爆炸。

Claude Code 有一个很典型的例子：有人在线上数据里发现，连续自动压缩失败的会话每天浪费约 25 万次 API 调用，于是加了一条规则，连续失败 3 次就停。这就是执行控制的价值——知道什么时候该放弃，比知道怎么继续更重要。Martin Fowler 把 harness 拆成 Guides 和 Sensors，Sensors 的核心作用就是让循环知道“当前状态是否还值得继续”。
```

### 2. 你参考 Pi 的这个设计，对它最重要的设计思想有什么理解？

```
Pi 的三层，自下而上是 ai、agent、coding-agent。

ai 层管模型提供商抽象，统一不同厂商的流式接口。agent 层是核心循环，只做一件事：模型输出、提取工具调用、执行工具、结果回填、下一轮。coding-agent 层在循环之上叠产品能力：会话持久化、上下文压缩、扩展系统、工具集、资源加载。

我理解它最重要的设计思想是：循环是内核，其余都是外挂。agent 层刻意保持无状态、不关心会话怎么存、压缩怎么触发、扩展怎么加载；这些全部推到 coding-agent 层。这样内核的职责边界极窄，只保证循环正确；上层可以随意替换扩展、替换压缩策略，不动循环本身。

对照我的项目：我的 LangGraph 建图和 ReAct 循环对应 Pi 的 agent 层，bootstrap 装配出的 AppRuntime 对应 coding-agent 层，ModelRouter 对应 ai 层的 provider 抽象。但取向不同：Pi 的循环和运行时是切开的，运行时往循环上叠；我的 20 个中间件是在建图阶段和循环一起装配的，治理和循环是编织在一起的。Pi 赌强模型加极简循环，灵活性靠 extension；我赌长任务研究需要可控的治理链，确定性靠中间件固定顺序。这是可控性优先和灵活性优先的取舍。
```

### 3. 能用一个简单例子介绍一下这个 harness 的整体执行流程吗？比如我想查一个项目里的 bug，它是怎么进行的？

```
可以，我用“查一个项目里的 bug”这个例子走一遍。

第一步，请求进来。用户在 CLI 里输入“帮我查一下这个项目里登录失败的 bug”。主循环先过意图树，判断这不是斜杠命令也不是报告类意图，是普通任务，于是进入流式研究。

第二步，创建运行。RunManager 建一个 RunContext、RunRecord、RunJournal，把 record 落盘，标记状态为 running，事件写进 journal。这一步保证这次运行可追溯、可恢复。

第三步，驱动图。PoirotStreamClient 拿着图和配置，调 graph.astream，开三种流模式：custom 收自定义事件，messages 收 token 增量，values 收状态快照。

第四步，图内第一轮。进入 agent 节点，先走 before_model 钩子链：系统上下文注入、技能注入、沙箱绑定、记忆召回，这些中间件依次把该准备的上下文准备好。然后 wrap_model_call 洋葱依次包住模型调用，真正调模型。模型第一轮通常会返回一个 tool_call，比如让工具去读登录相关的代码文件。

第五步，工具执行。因为模型返回了 tool_calls，图跳到 tools 节点，wrap_tool_call 洋葱正序执行：沙箱中间件做路径校验和权限检查，工具调用中间件真正执行读文件，结果回填。POST 阶段反序回来，如果结果超长，外化中间件会把它搬到磁盘、留预览和路径。

第六步，回到 agent 循环。工具结果作为 ToolMessage 回到 agent 节点，再走一轮 before_model、调模型、after_model。模型可能再要读别的文件、跑测试、搜索代码，每一轮都是“调模型、有工具调用就执行、结果回填、再调模型”的 ReAct 循环。期间 after_model 钩子链会做 token 追踪、阶段标记、必要时触发压缩或收尾。

第七步，收尾。模型认为找到 bug 了，不再返回 tool_calls，图走到 END。after_agent 钩子链做记忆沉淀、技能指标、报告合成。RunManager 标记 success，记完成时间、token 用量，journal 记 run.finished。renderer 逐事件渲染，用户看到流式的思考、工具调用、最终回答。

如果中途工具报错或循环卡住，停滞检测和悬空工具调用中间件会介入；如果用户中断，异常分支标记 failed 为 interrupted。整个过程装配阶段只跑一次，运行阶段每次请求跑一遍这个循环。
```

#### 3.1. 具体是谁来执行工具？工具执行的结果是怎么给到下一轮模型的？

```
执行工具的不是模型，模型只输出 tool_calls。真正执行的是 LangGraph 图里的 tools 节点，在 tools 节点里由 wrap_tool_call 洋葱链执行：沙箱中间件先做路径校验和权限检查，工具调用中间件负责调度，MCP 审计中间件做审计，最内层调工具本身。所以是模型发起、tools 节点执行、中间件层层包裹。

结果怎么给到下一轮模型，不是工具直接推给模型，是写进 state 再读出来。工具返回一个 ToolMessage，LangGraph 把它追加到 state.messages 里。图从 tools 节点回到 agent 节点，下一轮调模型之前，before_model 钩子链先跑，然后把 state.messages 里的内容连同这条 ToolMessage 一起组装成请求送给模型。所以工具结果是通过 state 这个载体，在下一轮模型调用时随上下文一起送进去的。

这里有个细节：如果工具结果超长，wrap_tool_call 的 POST 阶段会触发外化，把正文搬到磁盘、留预览和路径，所以下一轮模型看到的是预览加路径，不是全文。这也是工具结果进入下一轮的方式之一，只是被治理过。
```

### 4. ReAct

#### 4.1. 了解哪些 Agent 范式？

```
Agent 范式我按"推理与行动怎么组织"来理解，有一条比较清晰的演进线：从纯思考（CoT），到思考与行动交替（ReAct），再到先规划后执行（Plan-Execute），以及执行后的自我修正（Reflection/Reflexion）。

CoT（Chain-of-Thought）是纯推理范式，让模型在给出答案前显式写出中间步骤，适合多步推理任务，但它不和外部世界交互，不调工具。

ReAct 是把"思考"和"行动"交织起来的范式，也是最小可行 Agent 的基线。它的循环是：模型先输出 Thought 说明当前判断，再输出 Action 选择要调的工具和参数，工具执行后拿到 Observation，模型基于 Observation 继续下一轮 Thought，直到任务完成。这个"思考、行动、观察、再思考"的交替循环，是 Agent 区别于单次 LLM 调用的本质。ReAct 的优点是边走边看，每一步都能根据工具返回调整策略，适合信息不完整、需要探索的任务；代价是每一轮都要调一次模型，轮次多、token 消耗大，而且如果循环没有终止控制，容易陷入重复调用或死循环。我的 Poirot 主循环就是 ReAct 的变体，LangGraph 建图 agent 和 tools 交替，模型输出 tool_calls、tools 节点执行、结果回填、再调模型。

Plan-Execute 是先让模型输出完整计划，也就是可执行的步骤列表，经审核后逐步执行。它和 ReAct 的区别在于：ReAct 是边走边看，Plan-Execute 是先想清楚再动手。它适合步骤依赖关系明确、计划可预先确定的场景；不适合中途需要根据观察结果改变策略的任务。

Reflection / Reflexion 是在产出结果后做自我评估，发现不足就修正再交。它通常不单独使用，而是叠加在 ReAct 或 Plan-Execute 之上，作为质量兜底层。Reflexion 在 HumanEval 编码基准上曾达到约 90% 的水平，是这类范式的代表。

Multi-Agent 不是单一推理范式，而是组织范式：把任务拆给多个专家 Agent，各自有独立上下文，结果汇总回主 Agent。它解决的是单 Agent 上下文膨胀和工具过多导致性能下降的问题。
```

#### 4.2. Function Calling 和 Tool Use 是什么

```
Function Calling 和 Tool Use 经常被混用，但严格说，它们是一个协议的两个层面。

Function Calling 是底层机制：模型不再只输出文本，而是输出结构化的调用请求，声明要调哪个函数、参数是什么。模型本身不执行，执行由应用程序完成，结果再回传给模型，模型基于结果继续推理或给最终回答。它解决的是“模型怎么结构化地表达它想做什么”这个问题。

Tool Use 在 Anthropic 的文档里被等同于 Function Calling，但从工程演进看，它涵盖的范围更大。当工具数量膨胀到几十个时，全量塞进上下文会导致 token 成本和选择困难，所以出现了 Tool Search、Programmatic Tool Calling 这些机制，让模型先搜索再加载工具，或者写代码一次性编排多个调用。所以 Function Calling 是协议，Tool Use 是协议之上处理工具规模、编排、执行位置的那套能力。

对照我的项目：Function Calling 是底层，模型输出 tool_calls、tools 节点执行、结果回填 state、下一轮随上下文送进去。Tool Use 层面，我有按组过滤工具、去重、沙箱和 MCP 分开注册、专家独立工具集这些设计，但没有 Tool Search 的懒加载，也没有程序化编排多工具的能力，工具调用还是逐次往返。
```

#### 4.3. 大模型自己怎么判断调用哪个

```
模型判断调哪个工具，分两层看。

模型内部没有显式规则匹配，它靠的是工具名、描述、参数 schema 和当前任务意图做语义匹配。工具描述写得清不清楚，直接决定它选得准不准——描述模糊的工具，模型会选错或反复犹豫。所以第一层答案是：模型靠工具描述和任务意图的语义匹配来判断，描述质量决定判断质量。

第二层是工程上怎么影响这个判断。常见手段有几种：控制一次性暴露的工具数量，工具太多模型选择困难；优化工具命名和描述，名字自解释、说清什么时候用什么时候不用；按领域分组，减少选择范围；用 tool_choice 强制模型必须调某个工具；允许并行调用，无依赖的工具一次输出多个。还有一点容易被忽略：模型要能判断“不调工具”，当前问题靠已有知识就能答，这个能力同样依赖提示词里对工具适用边界的描述。

对照我的项目：工具按组过滤后注册，expert 模式才加载 deferred 组，这控制了暴露数量；专家工具用 delegate 前缀命名，名字自解释；MCP 工具有描述扫描守卫。但我没有 Tool Search 的懒加载，工具多了选择困难没有专门处理；没有 tool_choice 强制选择；工具描述靠手工写，没有系统性优化或测试。
```
