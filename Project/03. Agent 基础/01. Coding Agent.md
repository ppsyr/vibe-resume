### 1. 遇到幻觉或 Bug 怎么甄别和驱动

```
coding agent 的幻觉和 bug，我首先默认它们一定会发生，不指望模型不犯错，而是让错误尽早、尽量自动地暴露出来。

甄别上，我不看模型说“已完成”或“测试通过”，只看可执行的结果。幻觉常见的形态是声称改了文件其实没改、调用不存在的 API、报告测试通过其实没跑，这些用文件状态断言、真实执行、退出码就能戳穿。bug 是代码写了但逻辑错，靠测试、类型检查、lint 和边界用例暴露。核心原则是：模型的自述不是证据，执行结果才是证据。

驱动修复上，TDD 是我认为最有效的驱动方式。原因有三。第一，它把需求先变成可执行的失败用例，模型在写实现之前就知道“什么算对”，减少它自由发挥的空间。第二，红绿循环给出明确的反馈信号：测试失败就是下一轮要解决的问题，测试通过才算完成，模型不能靠“我觉得对”蒙混。第三，测试本身是可回归的资产，修完一个 bug 加一个用例，防止同一个问题复发。

具体驱动流程是：先写失败测试，确认它真的失败，再让 agent 写实现，跑测试，失败就把失败信息喂回去让它改，通过后再补边界用例和回归。这里有个关键点要防：模型可能改测试来让它通过，所以测试的修改要受控，不能让 agent 随意改断言。

所以准确说，甄别靠可执行验证而不是模型自述，驱动靠 TDD 的红绿循环把失败信号变成下一轮输入，同时要防 agent 改测试作弊、要保留回归用例防复发。
```

#### 1.1. 产生的代码质量怎么保证？有没有设计？

```
代码质量保证我不会指望模型自己保证，而是设计一套让它“写不好就过不去”的机制。这套机制分三层。

输入侧，用项目规则和约束文件限定边界。让 agent 在动手之前就知道哪些模块不能碰、用什么语言和框架、命名和注释规范是什么。Claude Code 的 CLAUDE.md、Codex 的 AGENTS.md 就是这一层，它把“我以为对”变成“项目规定的对”。

执行侧，用权限层和钩子拦截危险操作。限制可写目录、禁止执行某些命令、文件写入前按 schema 校验，不合格就阻断并返回结构化错误。这一层的作用是把概率性的模型行为，在关键决策点上变成确定性的拦截。

输出侧，用确定性门禁做验证，这是最核心的一层。测试、类型检查、lint、静态分析，其中测试最重要，因为它是可执行、可回归的。TDD 之所以有效，就是先写失败测试，让 agent 的目标变成“通过测试”而不是“我觉得写完了”，测试通过才算完成，失败信息直接变成下一轮的输入。

这里有一个必须防的点：agent 可能为了让测试通过而改测试、删断言。所以基线测试要做校验，agent 对测试文件的修改要受控，不能让“测试通过”变成“测试被改到通过”。
```

### 2. 你对 Claude Code 的记忆系统了解多少？

```
Claude Code 的记忆系统是两套互补机制：`CLAUDE.md` 和自动记忆。`CLAUDE.md` 是用户手写的，分组织、用户、项目、本地四级，按路径从宽到窄拼接加载，放编码标准和项目规则。自动记忆是 Claude 自己写的，存在每个项目独立的 `memory/` 目录下，`MEMORY.md` 是索引，每次会话只加载前 200 行或 25KB，详细内容按需读取。两套都在会话开始时加载，但都是软上下文不是硬约束，真要拦截操作得用 hook。

我印象比较深的设计是压缩后的重注入：`/compact` 之后，`CLAUDE.md` 和自动记忆从磁盘重新加载，最近修改的最多 5 个文件也重新读，skill body 也重新注入但有 token 上限。这个“摘要之外留一条从磁盘找回的路”，和我对上下文治理的理解是一致的——摘要不可逆，但关键内容要能回来。

另外自动记忆的按需加载机制也值得注意：`MEMORY.md` 只有 200 行/25KB 的预算，超出的细节移到主题文件里，Claude 需要时自己按路径读。这和我项目里“外化留预览和路径、按需回读”的思路是同一个方向——把窗口容量问题转化成检索问题。
```
