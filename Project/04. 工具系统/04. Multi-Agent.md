### 1. Sub-Agent

#### 1.1. Skill 懒加载和 SubAgent 怎么被 Agent 感知；怎么定义需要子 agent

```
Skill 懒加载和 SubAgent 的感知，本质是同一个问题：怎么让模型知道存在一个它还没加载的能力，又不把全部内容塞进上下文。

Skill 懒加载走渐进式披露。启动时上下文里只放每个技能的名字和一句话描述，正文和附带文件不加载。模型判断需要某个技能时，主动调用加载工具把正文拉进来。这样常驻的只是索引，不是全文。Anthropic 的 Agent Skills 就是这个模式，SKILL.md 的 frontmatter 给名称和描述，正文按需加载。

SubAgent 的感知类似。主 Agent 看到的是一个派活工具的定义，里面说明这个工具可以把任务委派给某个子 Agent，子 Agent 有独立上下文。模型决定派活时调用这个工具，子 Agent 在自己的上下文里执行，结果摘要回主 Agent。主 Agent 不需要知道子 Agent 内部用了什么工具、走了什么步骤，只需要知道有这么个专家、它能干什么。

怎么定义需要子 Agent，我看几条判据：任务可以独立拆出去、不需要主 Agent 的完整上下文；任务是探索性的、会产生大量中间噪声，放子 Agent 里不污染主上下文；任务需要不同工具集或不同权限；任务可以并行。反过来说，和主流程强耦合、需要频繁往返的任务就不该拆。

对照我的项目：Skill 这边，我启动时 load_startup 扫描 SKILL.md 做发现，SkillSelector 按 query 选技能，SkillInjectionMiddleware 在 before_model 里注入，skill_search 作为 core 工具让模型主动搜。我的感知路径是发现加选择加注入加搜索兜底。但我要说清一个边界：如果注入的是完整正文，那就不是懒加载，是启动即加载；如果注入的是名称加描述、正文按需拉，才是真正的懒加载，这个粒度我需要对照代码确认。SubAgent 这边，我通过 MCP 接入 Pi、Codex、Claude，delegate_to 工具是主 Agent 看到的入口，专家在独立上下文执行，结果摘要回来，specialist_registry 管注册，每个专家有独立的 context 和 result summarizer，这和业界模式一致。缺口是 Skill 的渐进式披露如果没做到，常驻上下文的是正文不是索引；SubAgent 的派活判据靠模型自己判断，没有显式规则告诉它什么任务该给哪个专家。
```

#### 1.2. SubAgent 用完释放吗？

```
我的子 Agent 有两种，压缩策略的答案不一样。

第一种是 self-copy 子 Agent，本质是主 Agent 的复制体，走同一套建图和中间件链。这种情况下压缩策略是继承的，P1 外化、P4 快照加摘要、P5 收尾，这些中间件在 self-copy 子 Agent 的上下文里同样生效。但压缩发生在子 Agent 自己的上下文里，主 Agent 看到的是子 Agent 回传的结果摘要，不会看到子 Agent 的压缩过程和中间状态。

第二种是外部专家，Pi、Codex、Claude 这些。它们通过 MCP 或 delegate 工具接入，在自己的运行时和上下文里执行，有自己的上下文管理机制。我的 P1、P4、P5 压缩中间件不在它们的执行路径上，所以管不到它们内部。它们的上下文怎么压、压到什么程度，是它们自己运行时的事。我能控制的是调用前给它们什么输入、调用后拿回什么摘要。

所以准确说：压缩策略对 self-copy 子 Agent 是继承的，对外部专家不适用。self-copy 的压缩在自己的上下文里发生，主 Agent 只拿摘要；外部专家的压缩在它们自己的运行时里，我只管输入和结果摘要。

如果面试官追问“self-copy 子 Agent 的压缩会不会和主 Agent 冲突”，答案是会话级状态隔离，self-copy 有独立上下文，压缩只影响它自己的消息，不回写主 Agent 的状态。
```

### 2. Multi-Agent

#### 2.1. Single Agent 和 Multi-Agent 的差异是什么？

```
Single Agent 和 Multi-Agent 的差异，核心不在能力上限，在架构形态和协调成本。

Single Agent 把逻辑集中在一个 Agent 里，上下文、推理、工具调用、最终回答都在同一个工作流内。优势是协调开销低、调用次数少、延迟低、工程简单、上下文集中，不需要在多个 Agent 之间序列化状态。代价是责任集中，规划、执行、验证都依赖同一个推理过程，一个环节错了后面可能跟着错，没有独立组件去挑战原始假设。

Multi-Agent 把责任分给多个专业化 Agent，优势是模块化、关注点分离、可并行、有冗余和容错。代价是协调复杂度高，每个交接点引入延迟，需要显式状态管理和错误处理，成本上升，因为每个 Agent 都处理冗余上下文，通信开销随 Agent 数量倍增。

关键是 Multi-Agent 不是普遍更优。有研究在受控 token 预算下发现，Single Agent 在信息论上至少不会比 Multi-Agent 差，因为 Multi-Agent 的中间消息是原始上下文的压缩或变换，不会增加与真实答案的互信息；只有在 Single Agent 的上下文利用严重退化时，Multi-Agent 的结构化分解才可能变得有竞争力。所以架构选择看任务，不是把 Multi-Agent 当默认升级。

什么时候该用 Multi-Agent，我看几条硬判据：跨安全或合规边界、多个团队管理不同知识域、未来有明确的扩展规划。如果只是角色不同，比如 planner、reviewer、executor，不一定需要多个 Agent，一个 Agent 用 persona 切换和条件提示词可能就够了。

对照我的项目：Poirot 是 Single Agent 为主、Multi-Agent 为辅。主 Agent 是 LangGraph 加 22 个中间件，上下文治理、记忆、技能、沙箱、反思都在主链上，这是集中式架构。Multi-Agent 是通过 MCP 接入 Pi、Codex、Claude，主 Agent 用 delegate 工具派活，专家独立上下文执行，结果摘要回来。我没有把主流程拆成多个 Agent，因为研究型长任务需要连续上下文和治理链，拆开协调开销大于收益；只在需要外部专家能力或上下文隔离时才派活。缺口是派活判据没有显式定义，靠模型自己判断，没有写什么任务该给哪个专家的规则。
```

#### 2.2. Multi-Agent 的本质是什么；它们的核心共同点是什么

```
我理解 Multi-Agent 的本质不是“有多个 Agent 在跑”，而是“把任务和上下文切开，让每个 Agent 只面对自己那部分复杂度”。

拆开说有三层。第一层是任务分解，一个大任务被切成若干子任务，每个子任务有明确的输入输出边界。第二层是上下文隔离，每个 Agent 有自己的上下文，不共享主 Agent 的全部历史，这样单 Agent 的上下文膨胀问题被分摊了。第三层是结果聚合，子 Agent 的执行结果经过摘要或结构化回传，主 Agent 基于聚合结果继续决策。所以 Multi-Agent 的本质是“分而治之加上下文隔离”，不是简单的数量增加。

它们的核心共同点，我看有几条。第一，都有某种形式的任务派发机制，主 Agent 决定把什么任务给谁。第二，都有独立的执行上下文，子 Agent 不在主 Agent 的历史里跑。第三，都有结果回传和聚合，不管是摘要、结构化结果还是直接返回。第四，都有边界定义，哪个 Agent 负责什么、有哪些工具、能访问什么资源。第五，都需要协调成本，派发、回传、聚合、失败处理，这些开销是 Multi-Agent 相比 Single Agent 必须付的代价。

对照我的项目：主 Agent 用 delegate 工具把任务派给 Pi、Codex、Claude 专家，专家在独立上下文执行，结果摘要回主 Agent，specialist_registry 管注册，每个专家有独立的 context 和 result summarizer。这五条共同点我都对应得上。self-copy 子 Agent 也是同样逻辑，上下文隔离、结果回传，区别是它复用主 Agent 的能力，不是专业化分工。

所以准确说：Multi-Agent 的本质是任务分解加上下文隔离加结果聚合，共同点是派发机制、独立上下文、结果回传、边界定义、协调成本。我的项目里这些都有真实落点，缺口是派发判据没有显式规则，靠模型自己判断。
```
