### 1. 你加载的是 skill.md 文件，还是会把 skill 下所有的文件都加载？

```
我加载的是 SKILL.md，不是整个技能目录。

启动时 store.discover 调用 parser.parse_skill_file 解析 SKILL.md，技能目录下的脚本、模板、参考资料不会主动加载。这和业界 Agent Skills 的模式一致：SKILL.md 是唯一入口，frontmatter 给名称和描述，正文写操作指令，附带文件通过相对路径引用，模型需要时再按路径去读。

为什么要这样，因为加载粒度要可控。一个技能目录里可能有脚本、模板、示例，如果全量加载，一个技能就能把上下文撑爆。渐进式披露分三层：第一层只放名称和描述，第二层加载 SKILL.md 正文，第三层才是按需读附带文件。

对照我的项目：我加载入口是 SKILL.md，这一点是对的。但有两个边界我要说清。第一，注入到上下文的是 SKILL.md 全文还是只取 frontmatter 加正文，材料里没展开，如果注入全文，至少没有加载整个目录，但比只注入名称和描述的渐进式披露重。第二，SKILL.md 里引用的附带文件，模型能不能按需读，取决于有没有读取技能资源的工具。我的 skill_search 是搜技能的，不是读技能文件的，所以这一步可能靠通用文件读取工具兜底，前提是文件在可访问路径内。这两点是我可以确认并优化的地方。
```

### 2. 如果要加载 skill，怎么把完整 Skill.md 放进上下文

```
把完整 SKILL.md 放进上下文，我看三种放法，我的项目介于中间。

第一种是预加载，启动时把所有选中技能的 SKILL.md 全文一次性塞进上下文。简单直接，但技能多了上下文会膨胀，而且很多技能这一轮根本用不到，属于浪费。

第二种是按需加载，上下文里只放名称和一句话描述，模型判断需要时调用一个加载工具，完整 SKILL.md 作为工具结果回填。这是渐进式披露的标准做法，Anthropic 的 Agent Skills 就是这个模式。好处是常驻上下文轻，坏处是多一次工具调用往返，而且依赖模型判断准不准。

第三种是搜索加读取两段式，模型先用 skill_search 搜到技能名和路径，再用读取工具按路径读 SKILL.md 正文。skill_search 负责发现，读取工具负责加载，职责分开。

对照我的项目：我的加载入口是 SKILL.md，由 SkillSelector 选、SkillInjectionMiddleware 在 before_model 注入，所以至少有一部分是中间件主动注入，不是纯靠模型调工具拉。如果我注入的是 SKILL.md 全文，那就是预加载模式，上下文开销比渐进式披露大；如果我注入的是名称和描述，正文靠 skill_search 加读取工具按需拉，那就是按需加载。这个粒度我要对照代码确认。

如果要优化，我会往第二种靠：启动时只注入名称和描述，加一个显式的加载工具，模型判断需要时把完整 SKILL.md 作为工具结果回填，同时保留 skill_search 做发现。这样常驻上下文轻，加载由模型按需触发，和业界渐进式披露一致。代价是多一次工具往返，所以要在提示词里说清什么时候该加载，避免模型该加载时不加载、或者不该加载时乱加载。
```

### 3. Skill 懒加载具体怎么实现

```
Skill 懒加载本质是渐进式披露，不是启动时把所有技能文档塞进上下文，而是分三层按需加载。

第一层是元数据，只放 name 和 description，常驻上下文但成本极低，一个技能一行索引可能就几十 token，全部正文可能几百上千 token。第二层是指令，模型判断某个技能和当前任务相关时，才加载 SKILL.md 正文。第三层是资源，技能目录下的脚本、参考资料、模板不主动加载，SKILL.md 里用路径引用，模型需要时再用文件读取工具去读。

具体实现有两种主流模式。一种是工具加载式，提供一个 load_skill 工具，模型调用时返回完整 SKILL.md 内容，作为工具结果进入对话。另一种是通用读取式，catalog 里只列技能名、描述和路径，模型直接用普通 Read 工具读那个文件。共同点是加载由模型按需触发，不是启动时全量注入。关键细节是 description 的质量，L1 只有这一行信息供模型判断，描述写得模糊就会漏加载，它是路由条件不是摘要。

对照我的项目：我的感知层有，load_startup 扫描 SKILL.md，SkillSelector 按 query 和阈值选，skill_search 是 core 工具。但我的加载层形态介于两种模式之间，我用 SkillInjectionMiddleware 在 before_model 主动注入，加载决策主要由 selector 匹配做，不是模型主动调工具拉。如果注入的是 SKILL.md 全文，那是 selector 匹配后预加载，不是严格懒加载；如果注入的是名称加描述、正文靠 skill_search 或文件工具按需读，才接近懒加载。这个粒度我要对照代码确认。资源层我是缺的，skill_search 搜的是技能不是技能附带文件，模型读脚本或参考资料只能靠通用文件工具兜底。另外 selector 用的是关键词匹配还是 LLM 判断，材料里没展开，如果是关键词，描述写得不够精确就会漏加载，这和业界提醒的 description 路由风险是同一个问题。
```
