
### 1. 工具注入

#### 1.1. 工具怎么暴露给大模型？所有工具都注入吗？

```
工具暴露给模型，暴露的是工具名、描述、参数 schema 这三样，模型靠这三样判断该调哪个、参数怎么填。工具代码本身模型看不到，它只输出结构化的调用请求，执行在工具节点。

是不是所有工具都注入，我的答案是明确不应该。原因有三个：token 成本，工具定义本身占上下文，几十个工具能吃掉几万 token；选择困难，工具越多模型越容易选错选漏；干扰，不相关工具的描述会污染判断。业界做法是按场景分组、按需检索、按权限过滤、命名空间隔离，核心都是控制一次性暴露的工具数量和相关性。

对照我的项目：我不是全量注入，是按组过滤加去重。core 和 deferred 分开，default 模式只加载 core 组，expert 模式才加载 deferred 组，这是按模式控制暴露范围。工具来源分内置、沙箱、专家三类，MCP 工具有描述扫描守卫。但我只有 core 和 deferred 两档，粒度比较粗，没有按任务类型动态检索，没有 Tool Search 那种先搜再加载的机制，工具描述也是手工写、没有质量校验。这是我工具系统下一步要补的。
```

#### 1.2. 工具怎么抽象、不同环境怎么适配；你现在的工具抽象够不够

```
我的工具抽象是接口层统一，环境靠沙箱适配。

接口层，所有工具落到统一的工具协议上，模型看到的是工具名、描述、参数 schema，不管是内置的搜索和快照读取、沙箱的文件读写和 bash、专家的 delegate 工具，还是 MCP 接入的工具，对模型来说都是同一种调用形态。环境适配上，Local 和 Docker 两种沙箱后端，路径转换器做本地和容器之间的路径映射，工具执行时按当前后端走对应运行时。

够不够，我分四层看。

第一层，调用接口，够了。模型不用关心工具背后是本地还是容器，统一按 schema 调，执行在工具节点。

第二层，风险等级，不够。工具应该自带风险元数据，比如这个工具是否只读、是否有副作用、是否可逆、是否高危，审批和拦截可以按元数据自动分级。我现在没有这一层，危险识别散在沙箱守卫里，不是工具自描述的。

第三层，执行语义，不够。只读工具和写工具走同一条调用路径，没有按幂等性和副作用分类。这导致重试策略、审批策略、缓存策略都没法按工具类型区分。

第四层，治理一致性，不够。MCP 工具有描述扫描和凭证脱敏，内置工具没有对等的守卫，两种来源的治理强度不一样，抽象没统一到治理层。

所以准确说：我的工具抽象在调用接口这一层是够的，模型侧统一；但风险等级、执行语义、环境自描述、治理一致性这四层没有抽象出来。如果补，我会给工具加风险元数据和执行语义标签，把治理从沙箱守卫上移到工具元数据层，让审批、重试、拦截都能按工具类型自动走，而不是散在各处。
```

### 2. 工具执行

#### 2.1. ReAct 循环中工具抛异常怎么处理；什么情况继续运行、什么情况中断；死循环了怎么中断

```
工具抛异常，我不会一律中断，也不会静默吞掉，按三步处理。

第一步，分类。瞬时异常，比如网络抖动、超时、临时不可用，可以重试或回填给模型换方案；参数错误，比如 schema 不匹配、路径不存在，回填错误信息让模型修正参数；权限拒绝，沙箱拦截了越界操作，回填拒绝原因，让模型知道这条路走不通；致命异常，比如沙箱崩溃、序列化失败，直接中断并标记失败。

第二步，决定继续还是中断。继续的条件是：异常可恢复、还没超过重试上限、任务核心没受影响。中断的条件是：异常连续出现、重试耗尽、涉及安全风险、或者循环已经无法推进。我的悬空工具调用中间件处理调用没有配对结果的情况，停滞检测中间件判断连续多轮有没有新进展，这两个是继续和中断的判断依据。

第三步，死循环中断。判据是重复和停滞：同一工具同一参数在短时间内反复调用、连续多轮没有新信息、步数或 token 超过上限。终止手段分软硬两层：软的是 P5 的 90% 收尾，剥掉 tool_calls、插收尾提示、强制模型收敛，不是硬断；硬的是超过 recursion_limit 或步数上限直接终止，标记失败。我的 P5 是软终止，RunManager 的异常分支是硬终止。

对照我的项目：我有悬空工具调用处理、停滞检测、P5 软收尾、异常分支区分中断和普通失败，但循环检测中间件已移除，没有专门的同参数重复调用检测；异常没有按类型分级，没有明确的“哪些回填继续、哪些中断”的策略；工具超时和重试上限也没看到。这三块是缺口。
```

### 3. 格式与校验

#### 3.1. 大模型输出的数据格式，你是让它以什么样的结构来输出的？（特别是工具调用时参数的格式）

```
在 LangGraph 标准格式下，模型输出工具调用的结构是挂在 `AIMessage` 上的 `tool_calls` 列表。每个调用包含三个字段：`name` 是工具名，`args` 是结构化参数字典，`id` 是唯一标识符。模型不执行工具，它只输出这个结构，执行由 tools 节点完成。执行结果包装成 `ToolMessage`，`tool_call_id` 对应回 `id`，追加到 `state.messages`，下一轮模型调用时随上下文送进去。

`args` 的格式受工具 schema 约束。工具定义时声明参数 JSON Schema，模型生成 `args` 时按这个 schema 填。如果开了严格模式，模型输出会被约束到完全匹配 schema；如果参数不合法，错误信息可以作为 `ToolMessage` 回填给模型，让它修正参数后重试。

对照我的项目：我用的是 LangGraph 的标准格式，`tool_calls` 的 `name`、`args`、`id` 三个字段，`ToolMessage` 回填，`id` 配对。流式客户端里也是按 `id` 去重、跳过空 `name`。但我的工具参数 schema 有没有开严格校验、模型输出参数不合法时是不是先回填错误再重试，材料里没有明确，这是我可以确认并补上的一个点。
```

#### 3.2. 如果部署的模型本身能力很差，生成的 JSON 老是格式不正确、或者没达到参数格式的要求，怎么优化？

```
模型能力差导致 JSON 格式不对或参数不合规，我不会只靠换模型解决，而是按三层加固。

第一层，生成侧用约束解码，从源头降低出错概率。业界有 constrained decoding 机制，在模型逐 token 生成时用 grammar 把不合法的 token 直接 mask 掉，比如 JSON 的引号、括号、枚举值，模型物理上无法输出非法格式 。llama.cpp 的 GBNF、AWS Nova 的 tool use 都内置了这类能力 。但这一层依赖推理引擎支持，如果你的 provider 不支持约束解码，就只能退到第二层。

第二层，校验侧在工具网关做 schema 校验，参数不合法就不放行。用 Pydantic 或 JSON Schema 定义工具的契约，模型输出的 `args` 先过校验，合法才进真实工具，不合法就拦截 。这一层的关键是**错误信息要结构化**，不能只回一句 “Bad Request” 或 “Argument parsing failed” 。要明确告诉模型：哪个字段错了、期望什么类型或枚举值、缺了哪个必填项。微软 agent-framework 的一个 issue 就记录了这个坑：默认错误信息不包含字段名和期望值，模型收到后原样重试了四次，因为它没有任何可纠正的线索 。你的 Poirot 如果回填的是原始异常堆栈或空泛错误，模型同样改不对。

第三层，反馈侧让错误可自愈，加重复失败熔断。结构化错误回填给模型后，模型有机会自己修正参数重试 。但必须加一道保护：**同一个工具、同一组参数、同一种校验错误，重复 N 次就熔断**，不再无限重试 。能力差的模型最容易陷入“改一个值、再错、再改”的循环，没有熔断就是烧 token。

对照我的项目：Poirot 用的是 LangGraph 标准 `tool_calls` 格式，`args` 有 schema，但材料里没有明确说是否开了严格校验、错误是否结构化回填。所以我当前可能只做到了“有 schema 定义”，没做到“校验失败后把字段级错误喂回给模型让它改”。如果补，我会在 `tool_calls` 执行前加一道 Pydantic 校验层，校验失败返回 `{“error”: “invalid_params”, “field”: “status”, “expected”: [...], “received”: “...”}` 这样的结构化结果，而不是抛异常或静默失败；同时加一个同参数重复失败计数，超过阈值就中断当前工具链，提示模型换方案或转人工。约束解码那一层取决于 provider 能力，我当前不假设有，作为可选的优化项。
```
