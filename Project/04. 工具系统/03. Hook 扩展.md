### 1. 怎么通过 hook 接入扩展能力的，接了哪些扩展能力；比如接入 MCP、skill 要怎么做

```
我的扩展接入走的是 LangGraph 中间件体系。中间件有两类 hook：Node-style 的 before_model、after_model 这些按顺序跑，Wrap-style 的 wrap_tool_call 形成洋葱，第一个中间件在最外层包住后面所有。

MCP 接入分三步。第一步，McpManager 管生命周期，负责发现和连接 MCP 服务器。第二步，mcp_metadata 给 MCP 工具打标，用 poirot_mcp 这个 metadata key 区分来源，去重时 builtin 优先。第三步，MCP 审计中间件挂在链上，做凭证脱敏、描述扫描、环境变量过滤这些守卫。MCP 工具最终和内置工具一起汇聚成 BaseTool 列表交给 Agent。所以 MCP 的接入是 Manager 管连接、中间件管治理、工具列表统一暴露。

Skill 接入也是三步。第一步，build_skill_manager 在 bootstrap 里装配，SQLiteSkillStore 管存储，load_startup 扫描 SKILL.md 做发现。第二步，SkillSelector 按 query 和阈值选技能。第三步，SkillInjectionMiddleware 在 before_model 里把选中的技能注入上下文，SkillMetricsMiddleware 打点。同时 skill_search 作为 core 工具让模型能主动搜。

我要说清两个边界。第一，MCP 这边 include_mcp 是保留参数，实际 MCP 工具走 McpManager 另一条路，不在 get_available_tools 的 builtin 链里。第二，Skill 注入的粒度——业界做法是系统提示只放技能名和一句话描述，正文按需加载，我的 SkillInjectionMiddleware 具体注入多少材料里没展开，如果注入的是完整正文，那上下文开销会比渐进式披露大。这是我可以确认并优化的点。
```

### 2. Extension Hook 是什么；为什么做成可插拔的形式；结构是 Python 的装饰器吗；是否支持修改输入输出

```
Extension Hook 就是 LangChain/LangGraph 中间件体系提供的扩展点。中间件可以挂载在 agent 生命周期的不同位置，按用途分两类。Node-style 的 before_model、after_model 这些，在模型调用前后执行，按注册顺序正序、反序跑；Wrap-style 的 wrap_model_call、wrap_tool_call 形成嵌套洋葱，第一个中间件在最外层，包住后面所有 。我的 22 个中间件就是挂在这些 hook 上，before_model 链里跑 skill 注入、记忆召回、沙箱绑定，wrap_tool_call 洋葱里做路径校验和工具执行。

为什么做成可插拔，原因有三个。第一是职责分离，每个中间件只做一件事，加一个治理能力是加一个中间件，不改主循环。第二是顺序可控，before 正序、after 反序、wrap 嵌套，这个顺序是确定的，行为可预测 。第三是复用，LangChain 本身就提供了 Summarization、HumanInTheLoop、ToolCallLimit 这些内置中间件，可以直接用或者组合 。

结构上，LangChain 支持两种写法：类式中间件和装饰器式。装饰器式用 @before_model、@wrap_model_call 这些装饰器包一个函数，适合单 hook 的简单场景；类式中间件继承 AgentMiddleware，可以定义多个 hook、扩展 state schema、注册额外工具 。我的 22 个中间件是类式，因为每个中间件往往要同时管 before 和 after、或者 wrap 和 state，单装饰器不够用。

是否支持修改输入输出，要看 hook 类型。Wrap-style 的 wrap_model_call 能拿到 ModelRequest 和 handler，可以用 request.override() 改 system_message、改 model、改 tools，也能在 handler 返回后改 response 。wrap_tool_call 同理，能改工具参数、能短路返回缓存结果、能改工具返回的 ToolMessage 。Node-style 的 before_model 只能返回 state 更新，不能直接改 request；after_model 能改 state，也能用 jump_to 控制流转 。我的 skill 注入、记忆召回用的是 before_model，只能往 state 里加消息，不能改 request 本身；沙箱路径校验如果是在 wrap_tool_call 里，就能改工具参数或者短路拒绝。所以“能不能改输入输出”的准确答案是：Wrap-style 能改 request 和 response，Node-style 只能改 state 和控制流转。

对照我的项目：我的中间件是类式，挂在 before_model、after_model、wrap_model_call、wrap_tool_call 上。MCP 审计和沙箱校验如果在 wrap_tool_call 里，就具备改工具参数和短路拒绝的能力；skill 注入和记忆召回在 before_model 里，只能往 state 加消息。我要确认的一点是：我的中间件具体用了哪些 hook，材料里列了挂载顺序但没标每个中间件的 hook 类型，这决定了哪些中间件能改输入输出、哪些只能改 state。这是面试前可以对照代码确认的。
```
