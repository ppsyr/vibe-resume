### 1. 危险命令 / 高风险操作的识别与拦截

#### 1.1. 危险命令怎么定义？举例？有哪些？

1. 文件删除与破坏。 `rm -rf`、`rm -r`、`rmdir /s`、`del /f`。递归或强制删除是最常见的一类，因为用户说“清理临时文件”，Agent 可能删了整个项目。
2. 磁盘与文件系统操作。 `mkfs`、`dd if=`、`format`、`diskpart`、直接写 `/dev/sd*`。这类命令一旦执行，数据不可恢复。
3. 系统关机与进程管理。 `shutdown`、`reboot`、`poweroff`、`kill -9 -1`、fork 炸弹 `:(){ :|:& };:`。影响的是整个系统而不是单个任务。
4. 远程脚本执行。 `curl ... | bash`、`wget ... | sh`。把网络内容直接管道给 shell 执行，攻击面不可控。
5. SQL 破坏性操作。`DROP TABLE`、`DROP DATABASE`、`TRUNCATE TABLE`、无 WHERE 的 `DELETE FROM`。数据库层面的不可逆操作。
6. 权限与所有权变更。`chmod -R 777`、`chown -R`。扩大访问范围，可能造成安全暴露。

```
危险命令的定义，我按“后果是否可逆、影响范围是否超出用户意图”来理解。不是所有 shell 命令都危险，`ls` 和 `rm -rf` 不在一个量级。业界通常先把工具按风险分级，bash 因为能执行任意操作、后果不可预测，被归为最高风险等级。

具体危险命令覆盖几类。文件删除类，`rm -rf`、`rm -r`、`rmdir /s`。磁盘操作类，`mkfs`、`dd if=`、`format`。系统关机类，`shutdown`、`reboot`、fork 炸弹。远程脚本执行类，`curl ... | bash`、`wget ... | sh`。SQL 破坏类，`DROP TABLE`、`TRUNCATE TABLE`、无 WHERE 的 DELETE。权限变更类，`chmod -R 777`、`chown -R`。Claude Code 还单独把 `curl`、`wget` 这类网络命令默认设为不自动批准。
```

#### 1.2. 用户让 Agent 删除 .log 文件，怎么设计安全机制？

```
用户让删 .log 文件，我会按五步设计安全机制。

第一，定义风险。删 .log 本身不是危险命令，危险的是删除方式：递归删除、通配符删除、删除范围超出当前目录、删除系统目录或项目根目录下的文件。所以风险不在“删”这个动作，在“删的范围和方式”。

第二，识别命令模式。在工具执行前解析命令，识别几类模式：`rm -rf`、`rm -r`、带通配符的 `rm`、`find ... -delete`、`xargs rm`。同时解析目标路径，判断是否包含通配符、是否指向目录而不是文件、是否在项目根目录或用户目录这些敏感位置。

第三，分级处理。不是所有删除都拦。只删当前目录下明确列出的几个 .log 文件，属于低风险，可以放行或记日志；带通配符删除、递归删除、删除范围超出当前任务目录，属于高风险，需要拦截或审批；删除系统目录、项目根目录、用户主目录下的内容，属于最高风险，直接拒绝。

第四，拦截加提示。高风险命令不直接执行，返回结构化拒绝信息给模型，说明“这条命令删除了 X 个文件、其中 Y 个不在任务范围内、建议改成明确列出要删的文件”。让模型有机会改成更精确的命令，而不是硬拒。

第五，可恢复。删除前对目标文件做备份或移到回收目录，而不是直接 `rm`。这样即使模型误删，也能恢复。这一层是兜底，前四层都失效时的最后保障。
```

#### 1.3. 命令执行边界怎么限制，Bash 怎么处理？

```
Bash 的边界限制，我会分五层做。

第一层，执行隔离。Bash 不在宿主机上跑，在容器或受限环境里跑，文件系统只挂载任务需要的目录，网络默认关闭或只允许白名单域名。这样即使命令有破坏性，影响范围被限制在沙箱内，不会波及宿主机。这是我的 Docker 沙箱已经在做的，但本地沙箱的隔离强度不如容器。

第二层，命令白名单或黑名单。不是所有命令都允许执行。按任务类型给一组允许的命令，或者维护一份危险命令黑名单，命中就拦。白名单更安全但灵活性差，黑名单更灵活但容易漏。实际做法通常是“常用只读命令放行、写操作命令需要审批、危险模式直接拒绝”。

第三层，命令解析。Bash 的危险性在于它可以组合：管道、重定向、子 shell、命令替换。`curl ... | bash` 是管道把网络内容喂给 shell，`$(rm -rf /)` 是命令替换，`bash -c "..."` 是嵌套执行。光匹配字符串拦不住这些，要解析命令结构，识别管道、重定向、子 shell 这些组合模式。

第四层，审批。高风险命令不直接执行，先暂停，把命令内容、影响范围展示给用户，等确认再执行。Claude Code 和 Codex 都有这一层，Codex 的 app-server 用反向 RPC 支持 turn 暂停等回答。我的沙箱目前是拦截式，不合规直接拒绝，没有可恢复的审批暂停，这是缺口。

第五层，超时和资源限制。Bash 命令可能挂起、可能无限输出、可能吃满 CPU 和内存。要设执行超时、输出上限、资源配额，超了就终止。这一层防的是“命令合法但行为失控”。
```

### 2. 审批记录与类似命令复用

#### 2.1. 假设有个命令 a 之前问过你，比如 curl 一个网址，你放行了，下一次他 curl 另外一个网址，agent 怎么判断是需要再找人确认还是可以直接使用？

```
这个问题的关键是粒度，不是“放行过就都放行”。

上一次放行 curl 一个网址，我批准的是“访问这个具体地址”，不是“curl 这个工具”。所以下一次 curl 另一个网址，默认应该重新确认，因为目标变了，风险可能完全不同——上次是公开文档，这次可能是内网地址。

判断要不要再问，我分三步。

第一步，解析命令结构。提取工具名、子命令、参数、目标，比如 curl 的 URL、方法、是否带数据上传。同样一条 curl，GET 一个公开页面和 POST 一个内部接口，风险不一样。

第二步，和批准记录做粒度匹配。批准记录不是存一条字符串，是结构化存“工具、操作类型、目标范围”。匹配时看这次命令命中哪一档：完全相同的命令，命中精确匹配，直接放行；同域名下的只读请求，命中模式匹配，可以放行；换域名、换方法、带上传数据，不在已批准范围内，重新确认。

第三步，分级决定。低风险且命中已批准模式，直接放行并记日志；中风险，比如同类操作但目标不同，提示用户确认并说明差异；高风险，比如方法从 GET 变 POST、目标变成内网地址，强制确认，不给“记住选择”的选项。

对照我的项目：PlugAgent 的 MySQL 插件有“按操作类型分级”的思路，只读约束四层落地，但它是拦截式，没有“记住上次批准、下次类似命令复用”的审批记忆。Poirot 沙箱有路径校验，MCP 有审计，但也没有粒度化的批准记录和相似命令匹配。所以这题我当前没有实现，如果做，会按“结构化批准记录、粒度匹配、分级决定”这三步来设计。
```
